Connect 치트시트

Connect 운영은 대부분 REST API로 합니다. 엔드포인트 전체 목록과 curl 예시, 내장 SMT 목록, 커넥터 상태 코드의 의미와 대응을 정리했습니다. 엔드포인트 목록은 Apache Kafka 4.3.1 배포판의 OpenAPI 정의에서 추출했습니다.

장애 대응 시 3단계

  • GET /connectors/{name}/status — 커넥터와 태스크의 상태·trace 확인.
  • Connect는 실패한 태스크를 자동 재시작하지 않습니다. POST /connectors/{name}/restart?includeTasks=true&onlyFailed=true.
  • 409가 오면 리밸런스 중입니다. 기다리세요 — 리밸런스 자체가 태스크를 재시작합니다.

REST API 전체 표

$CW를 http://localhost:8083으로 읽으세요. 워커의 REST 리스너 기본값은 http://:8083입니다.

409 Conflict의 원인

공식 문서는 리밸런스가 진행 중일 때 태스크 재시작을 요청하면 Connect가 409 (Conflict)를 반환한다고 명시합니다. 그리고 재시도가 필요하지 않을 수도 있습니다 — 리밸런스 자체가 클러스터의 모든 커넥터·태스크를 사실상 재시작하기 때문입니다.

409를 보면 먼저 GET /connectors/{name}/status로 이미 RUNNING이 되었는지 확인하세요. 자동화 스크립트라면 409를 재시도 대상으로 두되 백오프를 충분히 주고, 매번 상태를 다시 확인하도록 만들어야 합니다.

409 Conflict의 원인 3가지
원인어떤 요청에서확인대응
① 리밸런스 진행 중 태스크·커넥터 재시작 워커 로그의 rebalance 메시지. GET /connectors?expand=status로 담당 워커 변화 확인 완료를 기다린 뒤 상태를 재확인하세요. 리밸런스 자체가 태스크를 재시작하므로 재시도가 불필요할 수 있습니다(공식 문서 명시)
② 같은 이름의 커넥터가 이미 존재 POST /connectors GET /connectors로 이름 중복 확인 멱등하게 만들려면 POST 대신 PUT /connectors/{name}/config를 쓰세요. 배포 스크립트에서 특히 중요합니다
③ 리더 워커로의 요청 전달 실패 쓰기 성격의 모든 요청 rest.advertised.host.name · rest.advertised.port가 다른 워커에서 도달 가능한지 Connect는 쓰기 요청을 리더 워커로 전달(forward)합니다. 광고 주소가 잘못되면 전달이 실패합니다 — 컨테이너 환경의 흔한 원인

워커 롤링 재시작과 커넥터 조작을 동시에 하지 마세요. 워커가 합류·이탈할 때마다 리밸런스가 일어나고, scheduled.rebalance.max.delay.ms(기본 5분)만큼 재배치가 지연될 수 있습니다. 커넥터를 대량 생성·삭제할 때도 각 변경이 리밸런스를 유발하므로 간격을 두세요.

SMT (Single Message Transform)

Apache Kafka에 내장된 SMT 목록입니다. 대부분 $Key와 $Value 두 변형을 가지며, 레코드의 키에 적용할지 값에 적용할지를 클래스명으로 구분합니다 (예: org.apache.kafka.connect.transforms.Cast$Value).

SMT는 이름 그대로 레코드 하나를 변환합니다. 따라서 집계 · 조인 · 윈도 · 여러 레코드를 합치기는 불가능합니다. 그런 처리는 Kafka Streams 또는 ksqlDB의 영역입니다.

그리고 SMT 체인이 길어지면 디버깅이 급격히 어려워집니다. 변환 중간 결과를 볼 방법이 없기 때문입니다. 네 개를 넘어가면 Streams로 전처리 토픽을 만드는 편을 검토하세요.

내부 토픽 3개

분산 모드 워커는 세 개의 내부 토픽에 상태를 저장합니다. 이 토픽들의 설정을 잘못 두는 것이 Connect 운영 사고의 가장 흔한 원인입니다.

Connect 내부 토픽 — 기본값은 Apache Kafka 4.3.1 Connect 설정 문서 기준
설정 파티션 기본값 RF 기본값 필수 조건
config.storage.topic 반드시 1개 (설정 항목 없음) config.storage.replication.factor = 3 파티션 1개 + cleanup.policy=compact. 순서가 의미를 가지므로 파티션을 늘리면 설정이 깨집니다
offset.storage.topic offset.storage.partitions = 25 offset.storage.replication.factor = 3 cleanup.policy=compact. source 커넥터 전용입니다
status.storage.topic status.storage.partitions = 5 status.storage.replication.factor = 3 cleanup.policy=compact. 활성 토픽 추적 정보도 여기 들어갑니다

1) 브로커가 3대 미만인데 RF 기본값 3을 그대로 두었습니다. 내부 토픽 생성이 InvalidReplicationFactorException으로 실패하고 워커가 기동하지 않습니다. 개발 환경에서는 세 개의 *.replication.factor를 모두 1로 낮추세요.

2) config.storage.topic의 파티션이 1이 아닙니다. 이 토픽은 순서에 의존하므로 파티션이 여러 개면 설정 변경이 유실되거나 뒤바뀝니다. 자동 생성에 맡기지 말고 직접 만드는 편이 안전합니다.

errors.tolerance=all은 변환·컨버터·sink 전달 단계의 오류를 흡수합니다. 그러나 대상 시스템이 완전히 다운된 경우는 흡수 대상이 아닙니다 — 모든 레코드가 DLQ로 흘러 들어가 원본을 그대로 복사하게 됩니다. DLQ 유입량에 알림을 걸어 두세요.

그리고 DLQ는 sink 커넥터에만 있습니다. source 커넥터의 오류는 DLQ로 가지 않습니다.

자주 걸리는 지점

Connect는 실패한 태스크를 자동으로 재시작하지 않습니다. 공식 문서에 명시된 동작입니다. FAILED 태스크는 사람이 재시작해야 하므로 상태 감시와 알림이 필수입니다.

PUT /connectors/{name}/config는 설정 전체를 대체합니다. 일부 키만 보내면 나머지가 기본값으로 돌아갑니다. 부분 변경은 PATCH를 쓰세요.

커넥터가 GET /connector-plugins에 안 보입니다. plugin.path에 없거나 디렉터리 구조가 잘못된 것입니다. 플러그인은 plugin.path 아래에 각자 디렉터리를 가져야 하며, 워커 재시작이 필요합니다.

tasks.max를 늘렸는데 태스크가 안 늘어납니다. sink는 파티션 수, source는 커넥터가 정의한 분할 단위가 상한입니다. tasks.max.enforce가 true(기본값)이면 초과 생성이 차단됩니다.

JSON 컨버터에서 스키마 관련 오류가 납니다. JsonConverter의 schemas.enable 기본값은 true이므로 (JsonConverterConfig.java 확인) {"schema": …, "payload": …} 봉투를 기대합니다. 평범한 JSON을 다루려면 key.converter.schemas.enable=false와 value.converter.schemas.enable=false를 함께 설정해야 합니다. 한쪽만 끄면 다른 쪽에서 계속 실패합니다.

그리고 내장 컨버터 클래스는 connect-runtime 아티팩트에 있습니다 (org.apache.kafka.connect.converters.*, org.apache.kafka.connect.json.JsonConverter). connect-api에 있다고 오해해 의존성만 connect-api로 두면 클래스를 찾지 못합니다.

워커가 컨테이너에서 서로를 찾지 못합니다. Connect는 REST 요청을 리더 워커로 전달(forward)합니다. rest.advertised.host.name·rest.advertised.port가 다른 워커가 도달할 수 있는 주소여야 합니다. 브로커의 advertised.listeners와 같은 종류의 문제입니다 (리스너 패턴).
