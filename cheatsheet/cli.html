CLI 치트시트

도구 이름이 아니라 하고 싶은 일로 찾도록 구성했습니다. 아래 검색창에 "lag", "오프셋", "리더" 같은 말을 넣으면 해당 행만 남습니다. 모든 명령은 --bootstrap-server 기준이며, 이 페이지의 명령은 Apache Kafka 4.3.1 공식 문서와 bin/ 스크립트로 확인했습니다.

이 페이지 쓰는 법

  • 목적별 명령 표에서 검색 → 짧은 형태를 확인 → 아래 복붙용 블록으로 이동.
  • 장애 대응 중이면 원라이너 20개부터 보세요.
  • 도구 이름을 이미 아는 경우 도구 색인을 쓰세요.

시작 전 — 배포 파일명 읽는 법

현행 배포 파일은 kafka_2.13-4.3.1.tgz 하나뿐입니다. 앞의 2.13은 이 배포판이 컴파일된 Scala 버전이고, Kafka 버전은 뒤쪽 4.3.1입니다. Kafka 2.13이라는 버전은 존재하지 않습니다 — Kafka는 2.8 다음이 3.0입니다.

Scala를 직접 쓰지 않는다면 고민할 것 없이 _2.13을 고르면 됩니다. 브로커는 JVM 바이너리로 동작하므로 Java만 있으면 되고, Java 17 · 21 · 25가 완전 지원됩니다(Java 8은 4.0에서 제거). 상세는 부록 · 버전 표기와 레거시에 있습니다.

--zookeeper 옵션은 Kafka 4.0에서 제거되었습니다. 3.x 이전 문서·블로그의 명령을 그대로 붙이면 동작하지 않습니다. 모든 CLI는 --bootstrap-server(브로커 엔드포인트) 또는 --bootstrap-controller(컨트롤러 엔드포인트)를 씁니다.

$BS는 localhost:9092(브로커), $BC는 localhost:9093(컨트롤러)로 읽으세요. 전체 명령은 각 분류 아래의 복붙용 블록에 있습니다.

자주 쓰는 원라이너 20개

장애 대응 중 그대로 붙여 쓸 수 있는 형태입니다. BS=localhost:9092를 먼저 export해 두면 편합니다.

--reset-offsets … --execute, --delete --topic, kafka-delete-records.sh, --election-type unclean은 되돌릴 수 없습니다. 오프셋 리셋은 실행 전 반드시 --dry-run(또는 --execute 없이)으로 확인하고, 기존 오프셋을 --describe 출력으로 남겨 두세요.

그리고 --reset-offsets는 그룹에 활성 멤버가 없을 때만 동작합니다. 컨슈머를 먼저 내려야 합니다.

--bootstrap-server vs --bootstrap-controller

KRaft에서는 엔드포인트가 두 종류입니다. 대부분의 명령은 브로커로 보내면 되고, 브로커가 전부 죽었거나 컨트롤러 자체를 다뤄야 할 때 컨트롤러 엔드포인트를 씁니다. 두 옵션을 동시에 쓸 수는 없습니다.

KRaft 클러스터 부트스트랩 전체 순서

KRaft 클러스터는 UUID 생성 → 로그 디렉터리 포맷 → 기동 순서입니다. 포맷 단계를 건너뛰면 브로커가 기동하지 않습니다. 그리고 컨트롤러 수는 3 또는 5(홀수)를 씁니다 — N개 컨트롤러는 (N−1)/2대까지의 장애를 견딥니다. 배경은 3장 KRaft와 클러스터 메타데이터에 있습니다.

파티션 재할당 3단계

--verify를 생략하면 토픽에 leader.replication.throttled.replicas와 follower.replication.throttled.replicas가 남습니다. 그 결과 재할당이 끝난 뒤에도 복제가 느려 URP가 잘 사라지지 않습니다. kafka-configs.sh --describe --entity-type topics --entity-name T로 확인하세요.

자주 걸리는 지점

오프셋 리셋이 "Assignments can only be reset if the group is inactive" 로 실패 — 그룹에 활성 멤버가 남아 있습니다. 컨슈머를 전부 내린 뒤 다시 실행하세요. --describe --group G --members로 남아 있는 멤버를 확인할 수 있습니다.

파티션 수는 늘릴 수만 있고 줄일 수 없습니다. 그리고 늘리면 기존 키의 해시 분배가 바뀌어 같은 키가 다른 파티션으로 갑니다 — 파티션 단위 순서 보장이 그 시점에 깨집니다. 비용과 부작용은 케이스 5에서 다룹니다.

--describe의 LAG가 -로 나옵니다 — 해당 파티션에 커밋된 오프셋이 없다는 뜻입니다. 새 그룹이거나 offsets.retention.minutes가 지나 커밋이 만료된 상태입니다. 이 상황에서 컨슈머를 붙이면 auto.offset.reset이 발동합니다 (케이스 1).

토픽 설정을 바꿨는데 디스크가 줄지 않습니다 — 리텐션 삭제는 세그먼트 단위이고 log.retention.check.interval.ms 주기로만 검사합니다. 활성 세그먼트는 삭제되지 않으므로 segment.ms·segment.bytes도 함께 봐야 합니다 (7장 스토리지·리텐션·컴팩션).

보안이 켜진 클러스터에서 CLI가 타임아웃으로 죽습니다 — --command-config를 빼먹었을 때의 전형적인 증상입니다. 인증 실패가 명확한 에러로 나오지 않고 요청 타임아웃으로 보이는 경우가 많습니다.
