보안 치트시트

복사해서 값만 바꾸면 동작하는 설정 스니펫과, 운영자가 가장 많이 틀리는 listeners / advertised.listeners / listener.security.protocol.map 조합 패턴 5가지를 정리했습니다. KRaft 기준이며 모든 설정명·기본값은 Apache Kafka 4.3.1 공식 문서에서 확인했습니다.

4계층으로 나눠 생각하세요

  • 암호화 — 전송 구간 TLS. SSL 또는 SASL_SSL.
  • 인증(authentication) — 누구인가. mTLS 인증서 또는 SASL.
  • 인가(authorization) — 무엇을 할 수 있는가. ACL.
  • 감사 — 누가 무엇을 했는가. kafka-authorizer.log.

보안 프로토콜 4종

listener.security.protocol.map에 쓸 수 있는 값은 아래 4개뿐입니다 (대소문자 구분 없음). 브로커의 기본 listener.security.protocol.map 값은 SASL_SSL:SASL_SSL,PLAINTEXT:PLAINTEXT,SSL:SSL,SASL_PLAINTEXT:SASL_PLAINTEXT이므로, 리스너 이름을 프로토콜 이름과 같게 지으면 이 설정을 생략할 수 있습니다.

TLS (SSL) 설정

단방향 TLS — 암호화만, 클라이언트 인증 없음

양방향 TLS (mTLS) — 인증서로 인증까지

JKS 대신 PEM을 쓸 수 있습니다. 이 경우 ssl.keystore.password와 ssl.truststore.password는 사용되지 않습니다. 개인키가 암호화되어 있다면 ssl.key.password에만 비밀번호를 줍니다. 문자열로 직접 넣으려면 ssl.keystore.key, ssl.keystore.certificate.chain, ssl.truststore.certificates를 씁니다.

SASL 설정

SASL_SSL + SCRAM-SHA-512 (운영 권장)

Kafka 4.x의 SCRAM 자격 증명은 메타데이터 로그(KRaft)에 저장됩니다. 3.x 이전 ZooKeeper 모드에서는 ZooKeeper에 저장되었고 --zookeeper 옵션으로 조작했습니다 — 그 옵션은 4.0에서 제거되었으므로 옛 문서의 명령은 동작하지 않습니다. 공식 문서는 이 저장 방식이 "KRaft 컨트롤러가 안전하고 사설망에 있는 설치 환경"에 적합하다고 명시합니다.

SASL_PLAINTEXT + SCRAM (내부망 전용)

SCRAM은 비밀번호를 평문으로 보내지 않으므로 TLS 없이도 비밀번호 자체는 노출되지 않습니다. 하지만 메시지 본문은 평문으로 흐릅니다. 그리고 공식 문서는 SCRAM 교환 가로채기(dictionary·brute force) 방지를 위해 TLS와 함께 쓸 것을 권고합니다. PLAIN 메커니즘을 SASL_PLAINTEXT와 조합하면 비밀번호가 그대로 네트워크를 흐릅니다 — 절대 하지 마세요.

SASL_SSL + PLAIN

사용자를 추가하려면 브로커 설정을 바꾸고 재시작해야 합니다. 동적 사용자 관리가 필요하면 SCRAM을 쓰거나 sasl.server.callback.handler.class로 외부 인증 서버를 연결해야 합니다.

리스너 조합 패턴 5가지

운영자가 가장 많이 틀리는 부분입니다. 세 설정의 역할을 먼저 분리하세요.

세 설정의 역할
설정누가 쓰는가무엇을 정하는가
listeners 브로커 자신 어디에 바인딩할지. 이름://호스트:포트. 호스트를 비우면 모든 인터페이스
advertised.listeners 클라이언트 메타데이터 응답으로 클라이언트에게 알릴 주소. 클라이언트가 실제로 접속할 주소여야 합니다
listener.security.protocol.map 브로커 리스너 이름 → 보안 프로토콜 매핑. 이름을 프로토콜과 다르게 지었으면 필수

클라이언트는 bootstrap.servers로 한 번 연결하고, 그 다음부터는 메타데이터로 받은 advertised.listeners 주소로 접속합니다. Docker·K8s에서 컨테이너 내부 주소가 광고되면 부트스트랩은 성공하고 실제 produce/fetch만 실패합니다. "연결은 되는데 타임아웃이 난다"의 거의 모든 원인이 이것입니다.

패턴 1 — 단일 리스너 (로컬 개발)

패턴 2 — 내부 / 외부 분리 (사내망 + 외부 클라이언트)

listener.name.{리스너이름소문자}.{설정} 형태로 리스너마다 다른 값을 줄 수 있습니다. 예를 들어 외부 리스너만 mTLS를 요구하려면 listener.name.external.ssl.client.auth=required를 씁니다.

패턴 3 — 브로커 전용 노드 (역할 분리)

controller.listener.names는 inter.broker.listener.name과 같은 값을 쓸 수 없습니다. 그리고 controller.quorum.bootstrap.servers의 호스트·포트는 실제로 노출된 컨트롤러 리스너로 라우팅되어야 합니다.

패턴 4 — Docker Compose

컨테이너 안의 클라이언트는 kafka-1:9092로 접속해야 하고, 호스트의 클라이언트는 localhost:19092로 접속해야 합니다. 하나의 advertised.listeners 값으로 둘을 만족시킬 수 없습니다. 그래서 리스너를 두 개 두고 각각 다른 주소를 광고합니다. 동작하는 3노드 구성은 예제 1에 있습니다.

패턴 5 — Kubernetes (StatefulSet + 파드별 외부 노출)

단일 Service로 모든 브로커를 노출하면 동작하지 않습니다. 클라이언트는 특정 파티션의 리더 브로커에 직접 접속해야 하는데, 로드밸런서가 임의의 브로커로 보내면 NotLeaderOrFollowerException이 반복됩니다. 브로커마다 개별 주소가 필요합니다 (파드별 Service, 또는 브로커 ID를 SNI/포트로 구분).

그리고 TLS 인증서의 SAN에 광고하는 모든 호스트명이 들어가야 합니다. 내부 DNS 이름과 외부 도메인을 함께 광고하면 둘 다 필요합니다.

ACL

Authorizer 켜기

super.users와 allow.everyone.if.no.acl.found는 브로커 ConfigDef가 아니라 Authorizer 구현이 읽는 설정이라 공식 설정 표에 기본값이 실려 있지 않습니다. StandardAuthorizer 소스 확인 결과 super.users는 미설정 시 빈 집합, allow.everyone.if.no.acl.found는 미설정 시 DENIED(=false와 동일)입니다.

인증(authentication)과 인가(authorization)를 구분하는 문항이 반복됩니다. 접속은 되는데 특정 작업만 실패하면 인가(ACL) 문제입니다. 접속 자체가 안 되면 인증 또는 TLS 문제입니다.

그리고 컨슈머에게 토픽 READ만 주고 그룹 READ를 빼먹으면 GroupAuthorizationException이 발생합니다. --consumer 편의 옵션은 이 둘을 함께 부여하므로 "가장 적절한 명령"을 고르는 문항에서 정답이 되기 쉽습니다.

ssl.endpoint.identification.algorithm의 기본값은 https이고, 빈 문자열로 두면 검증을 끕니다. 공식 문서에도 이 방법이 나오지만, 이는 중간자 공격을 허용하는 것입니다. 운영에서 이 값을 비우기 전에 인증서 SAN을 고치는 쪽을 먼저 검토하세요.
