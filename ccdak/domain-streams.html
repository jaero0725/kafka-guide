Kafka Streams

Streams는 별도 클러스터가 아니라 애플리케이션에 넣는 라이브러리입니다. 출제는 API 전체를 묻지 않고 세 가지 판단에 집중됩니다 — 이 데이터는 KStream인가 KTable인가, 이 연산은 상태를 갖는가 그리고 리파티션을 유발하는가, 이 조인은 co-partitioning이 필요한가.

이 도메인의 학습 목표

  • KStream · KTable · GlobalKTable의 의미론 차이를 데이터 성격으로 판단할 수 있습니다.
  • stateless / stateful 연산을 분류하고, 리파티션을 유발하는 연산을 골라낼 수 있습니다.
  • 조인 4종의 윈도우 필요 여부와 co-partitioning 요구사항을 말할 수 있습니다.
  • 윈도우 4종의 차이와 grace period의 역할을 설명할 수 있습니다.
  • 태스크·스레드 병렬성과 exactly_once_v2의 전제를 알 수 있습니다.

이 도메인이 묻는 것

참고 챕터는 10장 Kafka Streams와 ksqlDB입니다. Streams는 표준 Kafka 프로듀서·컨슈머 위에 올라간 라이브러리이므로, Application Development 도메인의 지식이 그대로 적용됩니다. Streams 애플리케이션의 병렬성은 결국 입력 토픽의 파티션 수이고, 상태 저장소는 결국 Kafka의 컴팩션 토픽(changelog)입니다. 이 두 연결을 잡고 있으면 문제 대부분이 풀립니다.

"이 데이터를 KStream으로 읽어야 하는가 KTable로 읽어야 하는가" 유형의 판단 기준은 "같은 키가 반복될 때 두 값이 모두 의미가 있는가"입니다.

  • 결제 이벤트 — 같은 사용자가 두 번 결제하면 둘 다 사실이므로 KStream입니다.
  • 사용자 주소 — 같은 사용자의 새 주소가 오면 이전 주소는 무효이므로 KTable입니다.

결제 이벤트를 KTable로 읽으면 이전 결제가 조용히 덮어써져 합계가 틀립니다. 이것이 이 도메인의 대표적 시나리오 문항입니다.

핵심 개념 (2) stateless · stateful · 리파티션

이 절의 표가 이 도메인 최다 출제 지점입니다. 연산을 세 축으로 분류해야 합니다 — 상태를 갖는가, 리파티션을 유발하는가, 그리고 키를 바꾸는가.

DSL 연산 분류 — 리파티션 유발 여부가 실무·시험에서 가장 중요합니다

map은 리파티션을 유발하고 mapValues는 유발하지 않습니다. 이유는 하나입니다 — map은 키를 바꿀 수 있고, 키가 바뀌면 같은 키가 같은 파티션에 있다는 보장이 깨지기 때문입니다. mapValues는 값만 바꾸므로 키 기반 배치가 유지되고 리파티션이 필요 없습니다. 이 문항은 거의 매번 출제됩니다.

정확히 말하면 map·selectKey·flatMap은 스트림을 "리파티션 필요"로 표시할 뿐이고, 실제 리파티션 토픽은 그 뒤에 키 기반 연산(집계·조인)이 올 때 생성됩니다. map 뒤에 바로 to()만 있으면 리파티션 토픽이 만들어지지 않습니다. "값만 바꾸면 되는데 map을 썼다"가 성능 문제의 흔한 원인입니다 — mapValues로 바꾸는 것이 정답입니다.

상태 저장소와 changelog

  • stateful 연산은 로컬 상태 저장소(기본 RocksDB)를 만듭니다.
  • 같은 내용이 changelog 토픽({application.id}-{store}-changelog)에 기록됩니다. 이 토픽은 cleanup.policy=compact입니다.
  • 인스턴스가 죽으면 다른 인스턴스가 changelog를 재생해 상태를 복구합니다. 상태가 크면 복구가 오래 걸리므로 num.standby.replicas(기본 0)를 올려 따뜻한 예비 사본을 유지합니다.
  • 리파티션 토픽은 {application.id}-{name}-repartition이며 cleanup.policy=delete입니다 (중간 데이터이므로).

changelog 토픽을 사람이 지우면 상태를 복구할 수 없습니다. 그리고 cleanup.policy를 delete로 바꾸면 오래된 키의 상태가 사라져 복구 시 데이터가 누락됩니다 (케이스 8).

co-partitioning 요건 — 공식 요건은 2개입니다

공식 문서(streams/developer-guide/dsl-api)가 co-partitioning 요구사항으로 열거하는 것은 두 개입니다. 키가 같아야 한다는 것은 요건이 아니라 equi-join 자체의 전제로 별도 서술됩니다.

  • 전제 — 양쪽 입력의 키가 같은 의미여야 합니다 (equi-join이 키 기준으로 수행되므로 leftKey == rightKey).
  • 요건 ① — 양쪽 입력 토픽의 파티션 수가 같아야 합니다. Streams가 런타임에 검증하는 유일한 항목입니다.
  • 요건 ② — 양쪽에 쓰는 모든 애플리케이션이 같은 파티셔닝 전략을 써야 합니다 (같은 partitioner.class 또는 같은 StreamPartitioner). 검증되지 않으므로 어긋나면 예외 없이 조인이 조용히 누락됩니다.

Kafka Streams는 co-partitioning을 부분적으로만 검증합니다. 런타임의 파티션 할당 단계에서 양쪽 파티션 수가 다르면 TopologyBuilderException을 던집니다. 그러나 파티셔닝 전략이 다른 것은 감지하지 못합니다 — 이 경우 예외 없이 조용히 조인이 누락됩니다. "조인 결과가 일부만 나온다"의 원인이 여기입니다.

해결은 파티션 수가 적은 쪽을 repartition()으로 맞추는 것입니다. 공식 문서는 병목을 피하기 위해 적은 쪽을 많은 쪽에 맞추라고 권합니다. KStream-KTable 조인이면 KStream을 리파티션하는 편이 낫습니다 (KTable을 리파티션하면 상태 저장소가 하나 더 생깁니다).

그리고 GlobalKTable 조인은 co-partitioning이 필요 없습니다. 모든 인스턴스가 전체 사본을 갖기 때문이고, KeyValueMapper로 키가 아닌 값으로도 조인할 수 있습니다. KTable-KTable 외래키(FK) 조인도 Streams가 내부적으로 co-partitioning을 처리합니다.

Tumbling은 Hopping의 특수한 경우입니다 — advance = size이면 겹치지 않으므로 tumbling이 됩니다. "10분 크기, 5분 advance인 hopping 윈도우에서 한 레코드는 몇 개 윈도우에 속하는가?" → 2개입니다.

Session 윈도우만 크기가 고정되지 않습니다. gap 안에 이벤트가 계속 오면 세션이 계속 늘어나고, 늦게 도착한 이벤트가 두 세션 사이를 메우면 두 세션이 하나로 병합됩니다. "사용자 활동 구간을 묶으려면?" → session 윈도우입니다.

시간 개념과 grace period

  • event time — 레코드에 기록된 타임스탬프. Streams의 기본 기준입니다.
  • ingestion time — 브로커가 로그에 쓴 시각 (토픽 message.timestamp.type=LogAppendTime).
  • processing time — 처리하는 순간의 벽시계 시각.

타임스탬프 추출기의 기본값은 FailOnInvalidTimestamp이며, 음수(무효) 타임스탬프를 만나면 예외를 던집니다. 레거시 데이터를 다룰 때는 LogAndSkipOnInvalidTimestamp나 WallclockTimestampExtractor로 바꾸는 선택지를 씁니다.

grace period는 윈도우가 닫힌 뒤에도 늦게 온 레코드를 받아 주는 유예 기간입니다. …WithNoGrace(…)를 쓰면 유예가 0이므로 지연 도착 레코드가 버려집니다. grace를 크게 주면 정확도가 오르지만 결과 확정이 늦어지고 상태가 커집니다. 중간 결과를 억제하고 최종 결과만 내보내려면 suppress()를 씁니다.

핵심 개념 (5) 병렬성과 exactly-once

  • 태스크 수 = 입력 토픽의 파티션 수입니다 (sub-topology별로 계산). 파티션이 6개면 태스크는 6개이고, 그 이상으로는 병렬 처리가 늘지 않습니다.
  • num.stream.threads(기본 1)는 한 인스턴스가 돌리는 스레드 수입니다. 태스크는 스레드에 배분됩니다.
  • 인스턴스를 늘리면 태스크가 인스턴스 사이로 재배분됩니다. 인스턴스 × 스레드 > 태스크 수가 되면 남는 스레드는 유휴 상태입니다.
  • Streams는 내부적으로 컨슈머 그룹을 쓰며, 그룹 ID는 application.id입니다. 그래서 application.id를 바꾸면 처음부터 다시 읽습니다.

processing.guarantee의 기본값은 at_least_once입니다. EOS를 쓰려면 exactly_once_v2로 명시해야 하며, 공식 문서는 브로커 3대 이상을 기본 전제로 명시합니다 (transaction.state.log.replication.factor=3, transaction.state.log.min.isr=2이기 때문입니다). 단일 브로커 개발 환경에서는 이 두 브로커 설정을 1로 낮춰야 동작합니다.

그리고 Streams의 EOS도 Kafka 경계 안에서만 성립합니다. foreach에서 외부 API를 호출하면 그 호출은 트랜잭션에 포함되지 않습니다.

인터랙티브 쿼리와 ksqlDB

상태 저장소는 KafkaStreams.store(...)로 직접 조회할 수 있습니다. 인스턴스가 여러 대면 키가 어느 인스턴스에 있는지 메타데이터로 찾아 그 인스턴스에 요청을 전달해야 합니다 (내장 RPC는 없고 애플리케이션이 구현합니다).

ksqlDB는 Kafka Streams 위에 올라간 SQL 계층이며, Apache Kafka 본체가 아니라 Confluent 컴포넌트입니다. CREATE STREAM / CREATE TABLE이 각각 KStream / KTable에 대응합니다. Java 코드 없이 스트림 처리를 하고 싶을 때 쓰고, 복잡한 로직·커스텀 상태가 필요하면 Streams로 갑니다.

Streams 전용 리밸런스 프로토콜(KIP-1071)은 Kafka 4.1에서 Early Access로 도입되어 4.2에서 production-ready가 되었습니다. 신규 4.2+ 클러스터에서는 브로커 쪽 그룹 타입이 기본 활성입니다.

단, 클라이언트 기본값은 다릅니다 — group.protocol의 기본값은 여전히 classic이고, 새 프로토콜을 쓰려면 group.protocol=streams로 명시적으로 옵트인해야 합니다. “4.2부터 기본 활성”을 클라이언트 기본값이 바뀐 것으로 읽으면 틀립니다.

코드 읽기 문제 대비

스니펫 1 — 리파티션 토픽이 몇 개 생기는가

리파티션 토픽은 1개입니다. (A) mapValues는 키를 바꾸지 않으므로 리파티션을 표시하지 않습니다. (B) selectKey가 키를 바꿔 "리파티션 필요"로 표시하고, 그 뒤의 groupByKey().count()가 키 기반 연산이므로 그 지점에서 리파티션 토픽 하나가 생성됩니다. filter는 아무 영향이 없습니다.

스니펫 2 — 이 조인은 동작하는가

실패합니다. KStream-KTable 조인은 co-partitioning이 필요한데 파티션 수가 12과 3으로 다릅니다. 런타임의 파티션 할당 단계에서 TopologyBuilderException이 발생합니다.

해결 방법은 두 가지입니다.

  • customers를 GlobalKTable로 읽는다 — co-partitioning 불필요. 참조 데이터가 작으면 이 편이 가장 간단합니다.
  • customers 토픽을 12 파티션으로 리파티션한다 — 공식 문서 권고는 적은 쪽을 많은 쪽에 맞추는 것입니다.

"윈도우를 추가한다"는 선택지는 오답입니다 — KStream-KTable 조인에는 윈도우가 없습니다.

스니펫 3 — 이 설정으로 EOS가 동작하는가

동작하지 않습니다. exactly_once_v2는 __transaction_state 토픽을 쓰는데, 그 토픽의 기본 설정이 transaction.state.log.replication.factor=3, transaction.state.log.min.isr=2입니다. 브로커가 1대면 토픽 생성 또는 트랜잭션 초기화가 실패합니다.

개발 환경에서는 브로커 쪽 두 설정을 1로 낮춰야 합니다. "Streams 설정을 바꾼다"는 선택지는 오답입니다 — 브로커 설정 문제입니다. 프로덕션에서는 브로커 3대 이상이 정답입니다.
