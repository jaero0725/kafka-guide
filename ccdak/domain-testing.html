Application Testing

가장 작은 도메인이지만 가성비가 가장 높습니다. 범위가 좁고 출제 형태가 뻔합니다 — "이 상황에서 어떤 테스트 도구를 쓰는가"와 "이 도구는 브로커가 필요한가". 아래 선택 기준표 하나를 확실히 외우면 이 도메인은 거의 끝납니다.

이 도메인의 학습 목표

  • Kafka 테스트 도구를 단위 / 통합 / 성능 / 데이터 생성 네 갈래로 분류할 수 있습니다.
  • TopologyTestDriver가 왜 브로커 없이 동작하는지 설명할 수 있습니다.
  • MockProducer / MockConsumer의 용도와 한계를 알 수 있습니다.
  • 성능 측정 스크립트 이름과 주요 옵션을 말할 수 있습니다 (4.3에서 바뀐 옵션 포함).
  • 테스트 가능한 Kafka 코드로 설계하는 원칙을 적용할 수 있습니다.

이 도메인이 묻는 것

출제 형태는 사실상 두 가지입니다.

  1. 도구 선택 — "Streams 토폴로지 로직만 빠르게 검증하려면?", "실제 브로커 동작까지 확인하려면?" → matching 유형(도구 ↔ 용도)으로도 자주 나옵니다.
  2. 도구의 성질 — 브로커가 필요한지, 시간을 제어할 수 있는지, 무엇을 검증할 수 없는지.

참고 챕터는 10장의 테스트 유틸 절과 예제 9·예제 12입니다.

"브로커 없이 Kafka Streams 토폴로지를 테스트하는 도구는?" → TopologyTestDriver입니다. 이 문항이 이 도메인에서 가장 자주 나옵니다.

함정 선택지는 EmbeddedKafkaCluster와 Testcontainers입니다. 둘은 실제 브로커를 띄웁니다 — 통합 테스트용이지 단위 테스트용이 아닙니다. MockProducer/MockConsumer도 브로커가 필요 없지만 Streams 토폴로지를 실행할 수는 없습니다.

핵심 개념 (2) TopologyTestDriver

kafka-streams-test-utils 아티팩트에 들어 있습니다. Streams 런타임을 시뮬레이션해서, 실제 브로커·컨슈머·프로듀서 없이 토폴로지를 그대로 통과시켜 봅니다.

TopologyTestDriver의 성질 네 가지가 그대로 출제됩니다.

  • 브로커가 필요 없습니다. 그래서 CI에서 초 단위로 돌립니다.
  • createInputTopic에는 serializer, createOutputTopic에는 deserializer를 줍니다. 방향을 바꿔 놓은 선택지가 나옵니다.
  • event-time punctuation은 레코드 타임스탬프로 자동 발동하고, wall-clock punctuation은 advanceWallClockTime()으로 직접 전진시켜야 발동합니다.
  • 상태 저장소를 테스트 전에 미리 채우거나(pre-populate) 후에 검증할 수 있습니다.

검증할 수 없는 것도 알아 두세요 — 실제 리밸런스, 실제 파티션 할당, 브로커 장애, 네트워크 지연, 다중 인스턴스 병렬성입니다. 이런 것은 통합 테스트로 가야 합니다.

핵심 개념 (3) MockProducer · MockConsumer

둘 다 kafka-clients에 포함되어 있고 각각 Producer / Consumer 인터페이스의 구현체입니다. 따라서 프로덕션 코드가 인터페이스에 의존해야 갈아끼울 수 있습니다.

Mock은 인메모리 시뮬레이션입니다. 다음을 검증할 수 없습니다.

  • 실제 직렬화 호환성과 Schema Registry 연동
  • 리밸런스와 ConsumerRebalanceListener 동작 (수동으로 흉내낼 수는 있음)
  • acks · min.insync.replicas처럼 브로커가 판정하는 것
  • 배치·압축·linger.ms 같은 실제 전송 파이프라인 동작

MockConsumer는 updateBeginningOffsets()(또는 updateEndOffsets())를 호출하지 않으면 poll이 동작하지 않습니다 — 이 점이 실습형 함정으로 나옵니다.

핵심 개념 (4) 통합 테스트

통합 테스트 선택지
방법특징언제 쓰나
Testcontainers Docker로 실제 브로커 이미지를 띄움. 프로덕션과 가장 가까움. Schema Registry·Connect도 함께 띄울 수 있음 직렬화·트랜잭션·보안·리밸런스까지 확인해야 할 때
EmbeddedKafkaCluster 같은 JVM에서 브로커를 기동. Docker 불필요. Apache Kafka의 Streams 통합 테스트에서 쓰는 유틸리티 Docker를 쓸 수 없는 CI, Streams 통합 테스트
Spring @EmbeddedKafka spring-kafka-test가 제공. 테스트 클래스에 애노테이션 하나로 브로커 기동 Spring Boot 애플리케이션의 리스너·템플릿 검증

단일 브로커 테스트 환경에서는 아래를 낮춰야 트랜잭션·EOS가 동작합니다. 기본값이 각각 3과 2이기 때문입니다.

"테스트에서만 EOS가 실패한다"의 원인이 거의 항상 이것입니다. Streams 도메인의 같은 함정과 이어집니다.

"통합 테스트에서 Docker를 쓸 수 없다. 무엇을 쓰는가?" → 같은 JVM에서 브로커를 띄우는 방식(EmbeddedKafkaCluster, Spring @EmbeddedKafka)입니다. Testcontainers는 Docker가 전제입니다.

그리고 통합 테스트를 반복 실행할 때 결과가 달라지는 원인은 남아 있는 상태입니다 — __consumer_offsets의 커밋 오프셋, 로컬 state.dir, changelog·repartition 토픽. Streams 애플리케이션은 kafka-streams-application-reset.sh와 KafkaStreams#cleanUp()으로 초기화합니다. "테스트 순서를 바꾸면 통과한다"는 증상은 거의 항상 이 문제입니다.

테스트 가능한 설계 원칙

  • 클라이언트를 직접 new하지 말고 인터페이스로 주입하세요. Producer<K,V> / Consumer<K,V> 타입을 받으면 Mock으로 교체할 수 있습니다.
  • poll 루프와 처리 로직을 분리하세요. 처리 함수를 따로 두면 Kafka 없이 순수 단위 테스트가 됩니다.
  • 토폴로지 구성 코드를 재사용 가능한 메서드로 빼세요. TopologyTestDriver가 프로덕션과 같은 토폴로지를 테스트할 수 있습니다.
  • 테스트 피라미드를 지키세요. 단위(빠름, 다수) → 통합(느림, 소수) → 성능(별도 파이프라인). 통합 테스트로 전부 덮으려 하면 CI가 무너집니다.

kafka-producer-perf-test.sh에는 --bootstrap-server와 --reporting-interval 옵션이 새로 추가되었습니다. kafka-consumer-perf-test.sh에는 --topic 대신 정규식으로 여러 토픽을 지정하는 --include 옵션이 추가되었습니다.

성능 측정에서 자주 나오는 판단 문항입니다.

  • --throughput -1로 최대 처리량을 재고, 값을 지정해 지연을 재는 것이 정석입니다. 무제한으로 돌리면서 지연을 측정하면 큐 대기 시간이 섞여 의미가 없습니다.
  • 지연은 평균이 아니라 99th·99.9th 백분위로 판단합니다.
  • 단일 노드에서 프로듀서와 브로커를 같이 돌리면 CPU·디스크 경쟁으로 수치가 왜곡됩니다.
  • end-to-end 지연은 kafka-e2e-latency.sh로 재며, 프로듀서 지연 + 복제 + 컨슈머 지연이 모두 포함됩니다.

목 데이터 생성

  • Datagen 소스 커넥터 — Confluent가 제공하는 kafka-connect-datagen. Avro 스키마 정의로 임의 데이터를 지속 생성합니다. Connect 워커에 올려서 씁니다.
  • ksqlDB의 datagen — 같은 목적의 ksqlDB 쪽 도구입니다.
  • kafka-verifiable-producer.sh / kafka-verifiable-consumer.sh — Apache Kafka에 포함. 순번이 있는 레코드를 보내고 받아서 유실·중복·순서 이탈을 검증합니다. 장애 주입 테스트와 함께 씁니다.

Datagen 커넥터와 ksqlDB는 Confluent 생태계 도구이고, kafka-verifiable-*는 Apache Kafka 배포판에 포함된 스크립트입니다. 시험에서 "Apache Kafka가 제공하는 것"과 "Confluent가 제공하는 것"을 구분해 묻는 경우가 있습니다.

스니펫 1 — 이 테스트는 무엇을 놓치는가

Schema Registry 연동과 스키마 호환성을 검증하지 못합니다. MockProducer는 브로커에도, 레지스트리에도 붙지 않습니다. Avro 직렬화기가 실제로 스키마를 등록하고 id를 붙이는 경로는 통합 테스트에서만 검증됩니다. 또한 autoComplete=true이므로 재시도·타임아웃 경로도 검증되지 않습니다 (false로 만들고 errorNext()를 써야 합니다).

스니펫 2 — 이 테스트가 실패하는 이유

세 레코드가 같은 타임스탬프(테스트 드라이버의 기본 시각)로 들어가 윈도우가 아직 닫히지 않았거나, 캐시 때문에 중간 결과가 하위로 흐르지 않은 상태입니다. 해결은 두 가지입니다.

  • pipeInput(key, value, timestamp)로 타임스탬프를 명시해 윈도우를 넘기는 이벤트를 하나 더 넣습니다.
  • statestore.cache.max.bytes=0으로 두어 모든 갱신이 즉시 흐르게 합니다 (테스트에서 흔히 쓰는 방법).

advanceWallClockTime()은 event-time 윈도우를 닫아 주지 않습니다 — 그것은 wall-clock punctuation 전용입니다. 이 구분이 함정입니다.

스니펫 3 — 이 성능 측정의 문제

이 지연 수치를 SLA 근거로 쓸 수 없습니다. --throughput -1로 무제한 부하를 걸었으므로, 평균 1.8초라는 값은 대부분 프로듀서 버퍼 대기 시간입니다. 최대 처리량(412K records/sec)만 유효한 정보입니다.

지연을 재려면 예상 부하(예: --throughput 100000)를 지정해 다시 측정해야 합니다. 또한 localhost이므로 프로듀서와 브로커가 자원을 다투는 환경이고, 실제 네트워크 왕복이 빠져 있습니다.
