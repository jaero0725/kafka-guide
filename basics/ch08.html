기본개념 · 8장

스키마와 직렬화

Kafka는 바이트 배열만 주고받습니다. 그 바이트를 무엇으로 해석할지에 대한 합의가 스키마이고, 그 합의를 시간에 걸쳐 안전하게 바꾸는 규칙이 호환성 모드입니다. 이 장의 핵심 산출물은 어떤 스키마 변경이 어떤 모드에서 허용되고 거부되는지의 매트릭스, 그리고 그 매트릭스에서 곧바로 따라 나오는 배포 순서입니다 — BACKWARD면 컨슈머 먼저, FORWARD면 프로듀서 먼저입니다.

학습 목표

  • JSON · Avro · Protobuf · JSON Schema를 스키마 진화·크기·도구 관점에서 비교해 선택할 수 있습니다.
  • Schema Registry의 subject · version · schema id 관계와 wire format 바이트 레이아웃을 설명할 수 있습니다.
  • subject naming strategy 3종이 만드는 subject 이름을 계산할 수 있습니다.
  • 호환성 모드 7종이 각각 어느 방향으로 무엇을 비교하는지 말하고, 변경 유형별 허용/거부를 판정할 수 있습니다.
  • 배포 순서를 모드에서 유도할 수 있고, 뒤바꿨을 때 무엇이 깨지는지 설명할 수 있습니다.
  • auto.register.schemas가 프로덕션에서 위험한 이유를 설명할 수 있습니다.

Schema Registry는 Apache Kafka 본체가 아니라 Confluent가 제공하는 별도 컴포넌트입니다. 1장에서 짚었듯 CCDAK 출제 범위에는 포함되므로 이 장에서 다룹니다. 이 장의 사실 확인은 Confluent Schema Registry와 Apache Avro의 공개 소스에서 했고, 각 항목의 확인 근거를 공식 문서 출처에 명시했습니다.

직렬화 형식 비교

Kafka의 Serializer/Deserializer는 무엇이든 될 수 있습니다. 선택 기준은 스키마 진화를 감당할 수 있는가와 페이로드 크기, 그리고 팀이 쓰는 언어 생태계입니다.

스키마 없는 JSON은 시작이 가장 쉽지만 대가가 미뤄집니다. 프로듀서가 필드를 하나 지우면 컨슈머는 배포될 때까지 그 사실을 모릅니다. Kafka는 보관 기간 동안 데이터를 유지하므로, 과거 형식의 데이터를 새 코드가 읽어야 하는 상황이 반드시 옵니다. Schema Registry의 가치는 저장 공간 절약보다 호환되지 않는 변경을 배포 전에 거부하는 것에 있습니다.

Schema Registry 아키텍처

Schema Registry는 스키마를 중앙에 보관하고 정수 ID를 발급하는 HTTP 서비스입니다. 핵심 흐름은 네 단계입니다.

  1. 프로듀서가 직렬화 시점에 스키마를 subject 아래로 등록합니다. Registry가 schema id를 돌려줍니다.
  2. 프로듀서는 메시지 앞에 그 id를 붙여 Kafka에 씁니다. 스키마 본문은 붙이지 않습니다.
  3. 컨슈머는 메시지 앞의 id를 읽어 Registry에 스키마를 조회합니다(그리고 캐시합니다).
  4. 조회한 writer 스키마와 컨슈머가 가진 reader 스키마로 역직렬화합니다.

subject · version · schema id

세 가지 식별자의 관계
개념무엇인가범위
subject 스키마가 진화하는 이름 공간. 호환성 규칙이 적용되는 단위 기본 전략에서는 <topic>-key / <topic>-value
version subject 안에서 1부터 증가하는 순번. 호환성 검사의 비교 대상을 정할 때 씁니다 subject 내부에서만 의미가 있습니다
schema id 스키마 본문에 부여되는 정수 ID. 메시지에 실려 나갑니다 Registry 전역. 같은 스키마는 여러 subject에서 같은 id를 공유합니다

version은 subject 안의 순번이고, schema id는 Registry 전역 식별자입니다. 메시지에 실려 나가는 것은 schema id입니다 — version이 아닙니다. 그래서 subject를 지우고 다시 만들어도 같은 스키마 본문은 같은 id를 받습니다. 반대로 version 3의 스키마가 다른 subject에서는 version 1일 수 있습니다. "메시지에 version이 들어 있다"는 선택지는 오답입니다.

wire format 바이트 레이아웃

직렬화된 메시지의 앞부분은 고정된 구조를 갖습니다. Confluent 직렬화기의 소스에서 확인한 값은 MAGIC_BYTE_V0 = 0x0, ID_SIZE = 4입니다.

magic byte 0x1 — GUID 형식

최근 Schema Registry 소스에는 MAGIC_BYTE_V1 = 0x1이 추가되어 있습니다. 이 형식은 4바이트 정수 id 대신 16바이트 UUID(schema GUID)를 실어 레지스트리 인스턴스 사이에서 id 충돌 없이 스키마를 참조할 수 있게 합니다. 직렬화기의 기본 동작은 여전히 0x0 + 4바이트 id이며 (PrefixSchemaIdSerializer가 idToBytes()를 사용), 역직렬화기는 두 형식을 모두 인식합니다. 알 수 없는 magic byte를 만나면 Unknown magic byte!로 실패합니다.

시험 대비로는 0x0 + 4바이트 schema id를 외우면 됩니다.

wire format은 숫자 자체를 묻는 문항으로 나옵니다. magic byte 1바이트(0x0) + schema id 4바이트 + payload, 즉 payload 앞에 5바이트가 붙습니다. 그래서 Kafka CLI의 kafka-console-consumer로 Avro 토픽을 그냥 읽으면 앞에 알 수 없는 바이트가 붙은 깨진 문자열이 보입니다 — Avro 콘솔 컨슈머나 적절한 deserializer를 써야 합니다.

subject naming strategy 3종

subject 이름을 어떻게 만들지가 호환성 검사의 단위를 결정합니다. Confluent 직렬화기 소스에서 확인한 세 전략의 산출 규칙입니다.

subject naming strategy — 소스에서 확인한 산출 규칙
전략 subject 이름 호환성 검사 단위 쓰는 곳
TopicNameStrategy
기본 동작		 <topic>-key / <topic>-value 토픽마다 독립 한 토픽에 한 종류의 레코드. 대부분의 경우
RecordNameStrategy 레코드의 fully-qualified 이름 (예: com.example.OrderCreated) 레코드 타입마다 독립. 토픽과 무관 여러 토픽에 같은 타입이 흐르고, 그 타입의 진화를 한 곳에서 관리하고 싶을 때
TopicRecordNameStrategy <topic>-<레코드 이름> 토픽 × 레코드 타입 한 토픽에 여러 이벤트 타입을 섞어 보내면서 토픽별로 다른 진화를 허용할 때

TopicNameStrategy(기본)에서는 토픽 하나에 subject 하나입니다. 그 토픽에 서로 다른 레코드 타입을 보내면, 두 번째 타입을 등록할 때 첫 번째 타입과의 호환성 검사에 걸려 거부됩니다. 완전히 다른 스키마이므로 통과할 수 없습니다.

해결은 두 가지입니다 — Avro union 타입 하나로 감싸서 subject를 하나로 유지하거나, TopicRecordNameStrategy로 전환해 타입마다 subject를 갖게 하는 것입니다. 후자는 토픽 안에서 타입별 진화를 독립적으로 관리할 수 있습니다.

호환성 모드 7종 — 무엇을 어느 방향으로 비교하는가

모드가 하는 일은 두 개의 축으로 완전히 결정됩니다. ① 검사 방향(누가 reader이고 누가 writer인지)과 ② 비교 범위(직전 버전만인지 모든 버전인지)입니다. Confluent Schema Registry의 CompatibilityChecker 소스가 이를 명시적으로 정의합니다.

방향을 외우는 가장 확실한 방법은 이름을 "무엇에 대한 호환인가"로 읽는 것입니다.

  • BACKWARD = 과거 데이터에 대한 호환. 새 코드(reader)가 뒤(과거)를 볼 수 있어야 합니다.
  • FORWARD = 미래 데이터에 대한 호환. 옛 코드(reader)가 앞(미래)을 볼 수 있어야 합니다.

그리고 *_TRANSITIVE는 "직전 버전이 아니라 모든 이전 버전과 대조"한다는 뜻일 뿐, 방향은 바뀌지 않습니다.

비-TRANSITIVE 모드는 직전 버전만 봅니다. 그래서 v1 → v2 → v3가 각 단계에서는 호환이지만 v1과 v3는 호환되지 않는 상황이 만들어질 수 있습니다.

예: BACKWARD에서 v2가 필드 a를 지우고, v3가 a를 다시 default 없이 추가한다고 하면 — v3 대 v2 검사에서는 reader(v3)에 있고 writer(v2)에 없는 필드가 default가 없으므로 거부됩니다. 그러나 타입 변경처럼 각 단계는 통과하면서 누적되면 어긋나는 조합은 실제로 존재합니다. 보관 기간이 길어 옛 데이터를 계속 읽어야 하는 토픽이라면 BACKWARD_TRANSITIVE가 더 안전한 선택입니다.

Avro 스키마 해석 규칙 — 매트릭스의 근거

허용/거부는 임의로 정해진 것이 아닙니다. Confluent의 AvroSchema.isBackwardCompatible()은 Avro의 SchemaCompatibility.checkReaderWriterCompatibility(reader, writer)를 직접 호출합니다. 따라서 매트릭스의 모든 칸은 Avro의 해석 규칙에서 유도됩니다.

호환성 매트릭스 — 이 장의 핵심 산출물

위의 두 표를 결합하면 매트릭스가 계산됩니다. 각 칸의 판정 방법은 항상 같습니다 — BACKWARD는 reader=새 스키마, FORWARD는 reader=옛 스키마로 두고 Avro 해석 규칙을 적용합니다.

*_TRANSITIVE 모드는 위 표의 판정을 직전 버전 대신 모든 이전 버전에 대해 반복합니다. 한 버전이라도 거부되면 전체가 거부됩니다. 즉 비-TRANSITIVE에서 ✕인 것은 TRANSITIVE에서도 ✕이고, 비-TRANSITIVE에서 ✓라도 TRANSITIVE에서는 ✕일 수 있습니다.

매트릭스에서 가장 위험한 행은 "필드 이름 변경 + 양쪽 모두 default 있음"입니다. 모든 모드에서 ✓로 통과합니다. 그런데 실제로 일어나는 일은 이렇습니다 — reader가 자신의 필드 이름으로 writer 필드를 찾지 못하므로 default 값을 채워 넣습니다. 원래 필드에 들어 있던 값은 사라집니다.

호환성 검사는 "역직렬화가 예외 없이 끝나는가"만 봅니다. "의미가 보존되는가"는 보지 않습니다. 필드 이름을 바꿔야 한다면 새 필드를 default와 함께 추가하고, 양쪽을 모두 채워 쓰다가, 컨슈머가 전부 전환된 뒤에 옛 필드를 지우는 3단계로 진행하세요. 또는 Avro aliases를 쓰되 alias는 reader 쪽만 유효하다는 제약을 고려하세요.

매트릭스에서 반드시 외워야 할 4칸입니다. 나머지는 여기서 유도됩니다.

BACKWARD필드 삭제 OK · default 있는 필드 추가 OK · default 없는 필드 추가는 거부
FORWARD필드 추가 OK · default 있는 필드 삭제 OK · default 없는 필드 삭제는 거부
FULLdefault 있는 필드의 추가/삭제만 OK
NONE전부 통과 — 검사를 하지 않습니다

그리고 필드 이름 변경은 어느 모드에서도 위험합니다 — 거부되거나, 통과하더라도 값이 유실됩니다.

배포 순서 — 매트릭스에서 곧바로 나옵니다

BACKWARD → 컨슈머 먼저. FORWARD → 프로듀서 먼저.

이것은 암기 사항이 아니라 모드의 정의에서 논리적으로 따라 나오는 결론입니다. 각 모드가 무엇을 보장하는지 다시 보면 순서가 자동으로 정해집니다.

BACKWARD면 왜 컨슈머 먼저인가

BACKWARD가 보장하는 것은 "새 스키마가 옛 스키마로 생산된 데이터를 읽을 수 있다"입니다. 보장되지 않는 것은 그 반대 — 옛 스키마가 새 데이터를 읽는 것입니다.

따라서 새 코드는 옛 데이터를 안전하게 읽을 수 있고, 옛 코드는 새 데이터를 못 읽습니다. 새 스키마의 데이터가 토픽에 나타나기 전에 컨슈머를 모두 새 버전으로 올려야 합니다. 컨슈머를 먼저 배포하면, 전환 기간 동안 새 컨슈머가 옛 데이터를 읽습니다 — 이것이 BACKWARD가 보장하는 방향입니다.

순서를 뒤바꿔 프로듀서를 먼저 배포하면, 아직 옛 스키마를 쓰는 컨슈머가 새 스키마의 데이터를 만나 역직렬화에 실패합니다. 예를 들어 v2에서 default 있는 필드를 추가했다면(BACKWARD ✓, FORWARD도 ✓라 안전하지만), v2에서 default 없는 필드를 추가한 경우 BACKWARD에서는 애초에 거부되고, 필드를 삭제한 경우(BACKWARD ✓, FORWARD ✕) 옛 컨슈머는 자신이 요구하는 필드를 새 데이터에서 찾지 못해 실패합니다.

FORWARD면 왜 프로듀서 먼저인가

FORWARD가 보장하는 것은 "새 스키마로 생산된 데이터를 옛 스키마가 읽을 수 있다"입니다. 즉 옛 컨슈머가 새 데이터를 안전하게 읽습니다.

그래서 프로듀서를 먼저 올려도 됩니다. 컨슈머는 아직 옛 버전이지만 새 데이터를 문제없이 처리합니다. 컨슈머는 여유를 두고 나중에 전환합니다.

순서를 뒤바꿔 컨슈머를 먼저 배포하면, 새 컨슈머가 아직 옛 스키마로 생산되는 데이터를 읽어야 합니다. 그런데 FORWARD는 그 방향(새 reader ← 옛 writer)을 보장하지 않습니다. v2에서 default 없는 필드를 추가한 경우(FORWARD ✓, BACKWARD ✕), 새 컨슈머는 옛 데이터에서 그 필드를 찾지 못하고 default도 없어 실패합니다.

모드별 배포 순서와 뒤바꿨을 때의 결과
모드 보장하는 방향 배포 순서 뒤바꾸면

BACKWARD_TRANSITIVE		 새 코드 → 옛 데이터 읽기 컨슈머 먼저 → 프로듀서 옛 컨슈머가 새 데이터를 만나 역직렬화 실패

BACKWARD → 컨슈머 먼저 / FORWARD → 프로듀서 먼저. 이 두 줄이 CCDAK Fundamentals의 스키마 항목에서 가장 자주 나옵니다. 선택지가 뒤바뀐 형태로 반드시 제시되므로 정의에서 유도하는 훈련을 해 두세요.

유도 방법을 한 문장으로: "보장되지 않는 조합이 전환 기간에 나타나지 않도록, 보장되는 쪽을 먼저 배치한다." BACKWARD는 새 reader가 옛 데이터를 읽는 것이 보장되므로 그 조합이 나타나도록 컨슈머(reader)를 먼저 올립니다. FORWARD는 옛 reader가 새 데이터를 읽는 것이 보장되므로 그 조합이 나타나도록 프로듀서(writer)를 먼저 올립니다.

그리고 FULL은 순서가 무관하지만 허용되는 변경이 가장 좁다는 점, NONE은 검사 자체를 하지 않는다는 점도 함께 물어봅니다. 실제 사고 사례는 케이스 9에서 다룹니다.

  • 의도하지 않은 버전이 계속 늘어납니다. 빌드마다 필드 순서나 doc 문자열이 미세하게 달라져도 새 버전이 생깁니다 (normalize.schemas=true가 일부 완화합니다).

흔한 오해

"BACKWARD 호환이면 옛 컨슈머가 새 데이터를 읽을 수 있다" — 정확히 반대입니다. BACKWARD가 보장하는 것은 새 스키마(reader)가 옛 데이터(writer)를 읽는 것입니다. 옛 컨슈머가 새 데이터를 읽는 것은 FORWARD가 보장합니다. 이 혼동이 곧바로 배포 순서를 뒤바꾸는 사고로 이어집니다. BACKWARD → 컨슈머 먼저, FORWARD → 프로듀서 먼저입니다.

"호환성 검사를 통과했으니 데이터가 안전하다" — 검사는 역직렬화가 예외 없이 끝나는지만 봅니다. 의미가 보존되는지는 보지 않습니다. 대표적인 예가 필드 이름 변경 + 양쪽에 default가 있는 경우입니다 — 모든 모드에서 통과하지만, reader가 이름으로 필드를 찾지 못해 default 값을 채워 넣고 원래 값은 사라집니다. 호환성 검사는 안전망이지 정합성 보증이 아닙니다.

"메시지에 스키마가 들어 있다" — 아닙니다. 메시지에 실려 나가는 것은 magic byte 1바이트 + schema id 4바이트, 총 5바이트뿐입니다. 스키마 본문은 Registry에 있습니다. 그래서 두 가지 결과가 따라옵니다.

  • Registry가 죽으면 캐시에 없는 새 스키마 id를 만난 컨슈머는 역직렬화에 실패합니다. Registry는 가용성이 필요한 컴포넌트입니다.
  • kafka-console-consumer로 Avro 토픽을 그냥 읽으면 깨져 보입니다. 앞 5바이트가 텍스트가 아니고 본문도 바이너리이기 때문입니다. 적절한 deserializer를 쓰는 도구가 필요합니다.

"schema id와 version은 같은 것이다" — version은 subject 안의 순번이고 schema id는 Registry 전역 식별자입니다. 같은 스키마 본문은 여러 subject에서 같은 id를 공유하고, 같은 id가 subject마다 다른 version일 수 있습니다. 그리고 메시지에 실리는 것은 id입니다. "version 3을 지웠으니 그 데이터를 못 읽는다"는 판단도 틀립니다 — 컨슈머는 id로 조회하기 때문입니다.

시험 포인트 요약

8장 범위의 출제 지점을 한 곳에 모았습니다.

  • wire format = magic byte 0x0(1바이트) + schema id(4바이트, big-endian) + payload. 앞에 5바이트가 붙습니다
  • 메시지에는 schema id가 실립니다. 스키마 본문도, version도 아닙니다
  • subject는 호환성 규칙의 단위, version은 subject 내 순번, schema id는 Registry 전역
  • subject naming: TopicNameStrategy(<topic>-key/-value, 기본) / RecordNameStrategy(레코드 FQN) / TopicRecordNameStrategy(<topic>-<record>)
  • 호환성 모드 7종: NONE, BACKWARD, BACKWARD_TRANSITIVE, FORWARD, FORWARD_TRANSITIVE, FULL, FULL_TRANSITIVE. Registry 기본값은 BACKWARD
  • BACKWARD: 필드 삭제 OK, default 있는 필드 추가 OK → 컨슈머 먼저 배포
  • FORWARD: 필드 추가 OK, default 있는 필드 삭제 OK → 프로듀서 먼저 배포
  • FULL: default 있는 필드의 추가/삭제만 OK. 배포 순서 무관
  • *_TRANSITIVE는 모든 이전 버전과 대조합니다. 방향은 바뀌지 않습니다
  • 필드 이름 변경은 어느 모드에서도 위험합니다. Avro aliases는 reader 쪽만 유효합니다
  • 타입 승격 방향: long ← int, float ← int/long, double ← int/long/float, bytes ↔ string
  • auto.register.schemas 기본값은 true. 프로덕션에서는 false로 두고 CI/CD에서 등록합니다
  • 배포 전 검증: POST /compatibility/subjects/{subject}/versions/{version}

코드 판독 문항에서 나오는 조합입니다.

  • value.serializer=io.confluent.kafka.serializers.KafkaAvroSerializer와 schema.registry.url이 함께 있어야 합니다. URL 없이 직렬화기만 지정한 코드는 실패합니다.
  • specific.avro.reader 기본값은 false여서 역직렬화 결과가 GenericRecord입니다. 생성된 클래스로 캐스팅하는 코드는 true가 필요합니다.
  • Registry가 응답하지 않으면 직렬화·역직렬화가 모두 실패합니다 — Kafka 브로커가 정상이어도 마찬가지입니다.

Connect의 key.converter/value.converter에 AvroConverter를 쓰면 같은 wire format과 같은 호환성 규칙이 적용됩니다. 컨버터도 value.converter.schema.registry.url처럼 접두어를 붙여 Registry URL을 받아야 한다는 점이 자주 나옵니다. 자세한 내용은 9장에서 다룹니다.

공식 문서 출처

Schema Registry는 Apache Kafka 본체가 아니므로, 이 장의 사실 확인은 Confluent Schema Registry와 Apache Avro의 공개 소스에서 했습니다. 각 항목이 어디서 확인되었는지 명시합니다.

  • Confluent — Schema Registry Concepts — subject · version · schema id 모델, Registry 아키텍처.
    확인 근거: confluentinc/schema-registry의 CompatibilityLevel(7종 열거), SchemaRegistryConfig의 schema.compatibility.level 기본값 backward
  • Confluent — Wire Format — magic byte + schema id + payload.
    확인 근거: io.confluent.kafka.serializers.schema.id.SchemaId의 MAGIC_BYTE_V0 = 0x0 · MAGIC_BYTE_V1 = 0x1 · ID_SIZE = 4, idToBytes()/guidToBytes()/fromBytes() 구현, Protobuf의 message index 추가분, PrefixSchemaIdSerializer
  • Confluent — Subject Name Strategy — 3종 전략.
    확인 근거: TopicNameStrategy(topic + "-key"/"-value"), RecordNameStrategy(레코드 FQN), TopicRecordNameStrategy(topic + "-" + recordName), 그리고 KEY/VALUE_SUBJECT_NAME_STRATEGY_DOC의 "By default, <topic>-key is used as subject" 서술
  • Confluent — Schema Evolution and Compatibility — 7개 모드와 배포 순서.
    확인 근거: CompatibilityChecker의 소스 주석과 구성 — BACKWARD=canReadStrategy()+validateLatest() ("새 스키마가 이전 스키마로 생산된 데이터를 읽을 수 있는지"), FORWARD=canBeReadStrategy()+validateLatest(), FULL=mutualReadStrategy(), *_TRANSITIVE=validateAll(), NONE=no-op. 그리고 SchemaValidatorBuilder가 각 전략에서 isBackwardCompatible의 인자 순서를 뒤집어 방향을 만드는 구현
  • Apache Avro — Schema Resolution — 매트릭스의 모든 판정 근거.
    확인 근거: Avro SchemaCompatibility의 checkReaderWriterCompatibility · checkReaderWriterRecordFields(reader 전용 필드의 default 요구) · lookupWriterField(reader 측 alias만 사용) · schemaNameEquals(reader aliases) · 타입 승격 분기(LONG←INT, FLOAT←INT/LONG, DOUBLE←INT/LONG/FLOAT, BYTES↔STRING) · checkReaderEnumContainsAllWriterEnumSymbols(enum default 예외) · union 분기 검사 · SchemaIncompatibilityType 6종(NAME_MISMATCH, FIXED_SIZE_MISMATCH, MISSING_ENUM_SYMBOLS, READER_FIELD_MISSING_DEFAULT_VALUE, TYPE_MISMATCH, MISSING_UNION_BRANCH). Confluent의 AvroSchema.isBackwardCompatible()이 이 함수를 (reader = this, writer = previousSchema)로 직접 호출하는 것도 확인했습니다
  • Confluent — Schema Registry API Reference — REST 엔드포인트.
    확인 근거: SubjectsResource(/subjects), SubjectVersionsResource(/subjects/{subject}/versions), CompatibilityResource(/compatibility/subjects/{subject}/versions/{version}), ConfigResource(/config, /config/{subject}), SchemasResource(/schemas/ids/{id}, /schemas/types), ModeResource(/mode)의 @Path·@GET/@POST/@PUT/@DELETE 애너테이션
  • Confluent — Serializer/Deserializer Configs — 직렬화기 설정 기본값.
    확인 근거: AbstractKafkaSchemaSerDeConfig의 AUTO_REGISTER_SCHEMAS_DEFAULT = true, USE_LATEST_VERSION_DEFAULT = false, LATEST_COMPATIBILITY_STRICT_DEFAULT = true, USE_SCHEMA_ID_DEFAULT = -1, NORMALIZE_SCHEMAS_DEFAULT = false, MAX_SCHEMAS_PER_SUBJECT_DEFAULT = 1000
  • Apache Kafka — Producer Configs — key.serializer/value.serializer 규약
