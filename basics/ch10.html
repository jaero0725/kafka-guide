Kafka Streams와 ksqlDB

Kafka Streams는 별도 클러스터를 세우지 않고 애플리케이션 안에서 돌아가는 라이브러리로 스트림 처리를 합니다. 이 장에서는 토폴로지와 태스크의 관계, KStream/KTable/GlobalKTable의 의미론 차이, 그리고 시험과 실무 양쪽에서 가장 자주 물리는 두 가지 — map은 리파티션을 유발하고 mapValues는 유발하지 않는다는 사실과 조인의 co-partitioning 요구사항 — 을 정확히 정리합니다. Kafka Streams는 CCDAK에서 12%, 함께 다루는 테스팅은 8% 비중입니다.

학습 목표

  • Streams가 왜 클러스터가 아니라 라이브러리인지, 그것이 배포와 확장에 무엇을 뜻하는지 설명할 수 있습니다.
  • 같은 입력에 대해 KStream · KTable · GlobalKTable이 서로 다른 결과를 내는 이유를 설명할 수 있습니다.
  • 어떤 DSL 연산이 상태를 만들고 어떤 연산이 리파티션을 유발하는지 구분할 수 있습니다.
  • 조인 4종의 윈도우 필요 여부와 co-partitioning 요구사항을 판단할 수 있습니다.
  • tumbling · hopping · sliding · session 윈도우를 구분하고 grace period의 역할을 설명할 수 있습니다.
  • TopologyTestDriver로 브로커 없이 토폴로지를 테스트할 수 있습니다.

클러스터가 아니라 라이브러리입니다

스트림 처리 프레임워크는 보통 자체 클러스터와 리소스 매니저를 요구합니다. Kafka Streams는 그 방향을 택하지 않았습니다. 공식 문서의 표현대로 "어떤 Java 애플리케이션에도 쉽게 임베드할 수 있는 단순하고 가벼운 클라이언트 라이브러리"이고, 내부 메시징 계층으로 Apache Kafka 자체 외에 어떤 외부 시스템에도 의존하지 않습니다. 문서는 "Kafka Streams는 리소스 매니저가 아니며, 스트림 처리 애플리케이션이 도는 곳이면 어디서든 돈다"고 명시합니다.

옮기기만 한다면 Kafka Connect, 옮기면서 계산해야 한다면 Kafka Streams입니다. Connect의 SMT는 stateless·레코드 단위이므로 집계와 조인을 할 수 없습니다. "SMT로 이걸 할 수 있나?"라는 질문이 나오면 대부분 답은 Streams입니다.

토폴로지 — source · processor · sink

Streams 애플리케이션은 프로세서 토폴로지(processor topology)로 계산 로직을 정의합니다. 토폴로지는 스트림 프로세서(노드)를 스트림(엣지)으로 연결한 그래프이며, 두 개의 특별한 프로세서가 있습니다.

  • source processor — 상위 프로세서가 없는 노드. 하나 이상의 Kafka 토픽에서 레코드를 읽어 하위로 전달합니다.
  • sink processor — 하위 프로세서가 없는 노드. 받은 레코드를 지정한 Kafka 토픽으로 보냅니다.

토폴로지를 정의하는 방법은 두 가지입니다 — Kafka Streams DSL(map, filter, join, 집계 등을 바로 제공)과 더 저수준인 Processor API(커스텀 프로세서를 직접 정의하고 상태 저장소에 접근). 토폴로지는 논리적 추상일 뿐이고, 런타임에는 병렬 처리를 위해 인스턴스화되고 복제됩니다.

공식 문서에 따르면 application.id는 ① 기본 client.id 접두어, ② 그룹 관리에 쓰이는 group.id, ③ changelog 토픽 이름 접두어로 함께 쓰입니다. 그래서 이 값을 바꾸면 새로운 애플리케이션이 됩니다 — 오프셋도 상태도 처음부터 다시 시작합니다. 반대로 서로 다른 애플리케이션이 같은 값을 쓰면 서로의 파티션을 빼앗습니다. 클러스터 안에서 유일해야 합니다.

KStream · KTable · GlobalKTable

같은 토픽을 읽어도 무엇으로 해석하느냐에 따라 결과가 달라집니다. 공식 문서가 드는 예시가 가장 명확합니다 — ("alice", 1) 다음에 ("alice", 3)이 들어올 때 사용자별 값을 합산하면,

  • KStream이면 4입니다. 두 번째 레코드는 앞 레코드를 대체하지 않는 별개의 사실이기 때문입니다.
  • KTable이면 3입니다. 두 번째 레코드가 앞 값의 갱신으로 해석되기 때문입니다.
세 추상의 의미론 비교 (Apache Kafka 4.3 Streams DSL 문서 기준)

어떤 데이터에 쓰나 클릭, 결제 트랜잭션, 센서 측정, 로그 사용자 프로필, 재고 수량, 계정 잔액 국가 코드, 환율처럼 작고 자주 변하지 않는 참조 데이터

"어떤 데이터를 KStream으로, 어떤 데이터를 KTable로 모델링해야 하는가"가 반복 출제됩니다. 판단 기준은 하나입니다 — 같은 키가 다시 오면 그것이 새 사건인가 갱신인가. 결제 트랜잭션은 같은 계정에 두 번 결제하면 두 건이므로 KStream, 계정 잔액은 같은 계정의 새 값이 이전 값을 대체하므로 KTable입니다.

함께 나오는 함정: KTable을 담는 토픽에는 로그 컴팩션이 안전하지만, KStream을 담는 토픽에는 잘못입니다. 컴팩션이 같은 키의 옛 레코드를 지우기 시작하면 ("alice", 1)이 사라져 합계가 4가 아니라 3이 되어 의미론이 깨집니다. 컴팩션 동작은 7장에 있습니다.

GlobalKTable은 co-partitioning이 필요 없고 키가 아닌 값으로도 조인할 수 있어 편리하지만, 공식 문서가 명시한 대가가 있습니다 — 파티션 KTable보다 로컬 저장 공간을 더 쓰고, 토픽 전체를 읽으므로 네트워크와 브로커 부하가 커집니다. 인스턴스를 늘려도 이 비용은 줄지 않고 인스턴스 수에 비례해 늘어납니다. "작고 자주 변하지 않는 참조 데이터"라는 조건이 붙는 이유입니다.

stateless와 stateful, 그리고 리파티션

DSL 연산을 분류하는 축은 두 개이고 서로 독립입니다 — 상태 저장소를 만드는가와 리파티션을 유발하는가입니다. map은 stateless이지만 리파티션을 유발하고, count는 stateful이지만 그 자체가 리파티션을 유발하지는 않습니다. 이 두 축을 섞으면 문제를 틀립니다.

map vs mapValues는 이 도메인의 단골 문항입니다. 정확한 서술은 이렇습니다 — map 뒤에 그룹화나 조인이 오면 리파티션이 일어납니다. map 자체가 즉시 토픽을 만드는 것이 아니라, 스트림을 "리파티션 필요"로 표시(mark)해 두고 실제 재분배는 다음 그룹화·조인 시점에 일어납니다. 공식 문서의 표현도 "Applying a grouping or a join after map will result in re-partitioning"입니다.

왜 필요한가: 키가 바뀌면 같은 새 키를 가진 레코드가 서로 다른 파티션에 흩어져 있을 수 있습니다. 집계와 조인은 같은 키가 같은 태스크로 모여야 성립하므로, 내부 리파티션 토픽을 거쳐 다시 분배합니다. 키를 바꿀 필요가 없다면 mapValues를 쓰는 것이 곧 성능 개선입니다 — 네트워크 왕복과 추가 토픽이 사라집니다.

같은 논리로 groupByKey는 필요할 때만, groupBy는 항상 리파티션합니다. 키를 바꾸지 않아도 되면 groupByKey가 정답입니다.

상태 저장소와 changelog

stateful 연산을 쓰면 DSL이 상태 저장소(state store)를 자동으로 만들고 관리합니다. 기본 구현은 디스크 기반 키-값 저장소(RocksDB)이고, 인메모리 해시맵도 선택할 수 있습니다. 내고장성은 changelog 토픽이 담당합니다.

  • 각 상태 저장소마다 복제되는 changelog Kafka 토픽이 유지되며 모든 상태 갱신이 기록됩니다.
  • changelog도 파티션되어 있어 각 저장소 인스턴스(=태스크)마다 전용 changelog 파티션을 가집니다.
  • changelog 토픽에는 로그 컴팩션이 켜져 있어 옛 데이터가 안전하게 정리됩니다 — 무한히 커지지 않습니다.
  • 태스크가 다른 머신에서 재시작되면 changelog를 재생(replay)해 장애 이전 상태로 복원한 뒤 처리를 이어갑니다.

문제는 복원 시간입니다. 태스크 재초기화 비용은 대부분 changelog 재생 시간이 차지합니다. 이를 줄이는 장치가 standby replica입니다. num.standby.replicas를 올리면 상태의 완전 복제본을 다른 인스턴스에 미리 유지하고, 태스크가 이동할 때 이미 최신 상태를 가진 인스턴스로 배정합니다. 2.6부터는 완전히 따라잡은 로컬 복사본을 가진 인스턴스가 존재한다면 반드시 그 인스턴스에 배정됩니다.

기본값이 0이므로, 아무 설정도 하지 않으면 standby가 없습니다. 상태가 큰 애플리케이션에서 인스턴스 하나가 죽으면 changelog를 처음부터 재생하는 동안 그 태스크는 멈춥니다. 상태 크기가 수 GB에 이르면 이 시간이 수십 분이 될 수 있습니다. 가용성이 중요하면 num.standby.replicas=1 이상을 검토하세요 — 대가는 저장 공간과 changelog 읽기 부하입니다.

랙 인식 배치도 가능합니다. rack.aware.assignment.tags를 설정하면 standby 태스크를 active와 다른 랙에 배치하려고 시도합니다. client.rack과 브로커의 broker.rack이 함께 설정되어 있으면 rack.aware.assignment.strategy로 랙 간 트래픽을 줄이는 배정도 가능합니다. 두 설정이 모두 있으면 standby 분산에는 rack.aware.assignment.tags가 우선합니다.

시간 — event time · processing time · ingestion time

세 가지 시간 개념 (Apache Kafka 4.3 Streams 핵심 개념 문서 기준)
개념언제의 시각인가누가 부여하는가
event time 이벤트가 소스에서 실제로 발생한 시점 이벤트를 만든 쪽 (예: GPS 센서가 위치 변화를 감지한 순간)
processing time 스트림 처리 애플리케이션이 그 레코드를 처리한 시점 처리 애플리케이션. event time보다 밀리초~수 시간 늦을 수 있습니다
ingestion time 브로커가 토픽 파티션에 저장한 시점 브로커. 레코드가 끝까지 처리되지 않아도 ingestion time은 존재합니다

event time과 ingestion time 중 무엇이 되는지는 Kafka Streams가 아니라 Kafka 쪽 설정이 결정합니다. 0.10.x부터 타임스탬프가 메시지에 자동으로 embed되며, 그 값이 event time인지 ingestion time인지는 브로커 또는 토픽 레벨 설정 (message.timestamp.type = CreateTime / LogAppendTime)에 달려 있습니다. Streams의 기본 TimestampExtractor는 그 embed된 값을 그대로 가져다 씁니다. 따라서 "Streams 설정으로 event time을 고른다"는 선택지는 오답입니다.

Streams는 TimestampExtractor 인터페이스로 모든 레코드에 타임스탬프를 부여합니다. 이 값이 진행 상황을 나타내는 stream time이고, 실제 실행 시각인 wall-clock time과 구분됩니다. stream time은 새 레코드가 프로세서에 도착할 때만 전진합니다 — 데이터가 멈추면 시간도 멈춥니다. 윈도우가 닫히지 않는 현상의 원인이 대부분 이것입니다.

윈도우 4종

윈도우는 stateful 연산을 위해 같은 키를 가진 레코드를 시간 구간으로 다시 묶는 장치입니다. 공식 문서가 강조하는 전제: 윈도우는 레코드 키별로 따로 추적됩니다.

윈도우 4종 비교 (Apache Kafka 4.3 DSL 문서 기준)
종류 정의 요소 겹침 정렬 기준 API
tumbling 크기(size)만 겹치지 않음. 레코드는 정확히 하나의 윈도우에 속합니다 epoch 정렬 — 5000ms면 [0,5000) [5000,10000). 하한 포함·상한 제외 TimeWindows.ofSizeAndGrace(size, grace)

다른 스트림 처리 도구에서 "sliding window"라고 부르는 것이 Kafka Streams의 hopping window입니다. 공식 문서가 이 점을 직접 지적합니다 — Kafka Streams는 학계 용어를 따르며, sliding window의 의미가 hopping window와 다릅니다. 다른 문서를 참고하다 개념이 어긋나는 대표적인 지점입니다.

그리고 tumbling window는 hopping window의 특수한 경우입니다 — 윈도우 크기와 advance 간격이 같으면 tumbling이 됩니다.

grace period — 늦게 온 데이터를 언제까지 받아 줄 것인가

grace period는 특정 윈도우에 대해 순서가 어긋난(out-of-order) 레코드를 얼마나 기다릴지를 정합니다. 공식 문서의 판정 규칙은 정확히 이렇습니다 — 레코드의 타임스탬프가 어떤 윈도우에 속하지만 현재 stream time이 그 윈도우의 끝 + grace period보다 크면, 그 레코드는 폐기되고 윈도우에 반영되지 않습니다.

윈도우 상태 저장소의 보관 기간(retention)은 grace period와 별개입니다. Streams는 윈도우를 최소 이 기간 동안 유지하며, 기본값은 1일이고 Materialized#withRetention()으로 바꿉니다.

순서 어긋남(out-of-order)은 event time에서만 의미가 있습니다. processing time 의미론에서는 "레코드가 처리되는 시점"이 정의상 시간이므로, 어긋날 수가 없습니다. 공식 문서가 이 점을 명시합니다.

그리고 조인별로 순서 어긋남 처리 수준이 다릅니다 — stream-stream 조인은 inner/left/outer 세 종류 모두 올바르게 처리하지만, stream-table과 table-table 조인은 versioned state store를 쓰지 않으면 처리하지 않고 오프셋 순서대로만 처리합니다. stream-table은 예측할 수 없는 결과가 나올 수 있고, table-table은 결과가 changelog라서 최종적으로는 일관해집니다.

윈도우 계산은 새 데이터가 올 때마다 결과를 갱신해 내려보냅니다. 최종 결과만 필요하면(알림 발송, 갱신을 지원하지 않는 시스템으로 전달 등) suppress로 윈도우가 닫힐 때까지 억제해야 합니다.

co-partitioning 3요건

공식 문서는 "조인 시 입력 데이터가 co-partition되어 있어야 하며, 그것을 보장하는 것은 사용자의 책임이다"라고 명시합니다. 요건은 다음과 같습니다.

co-partitioning 요구사항
요건내용Streams가 검증하는가
① 같은 키 equi-join은 레코드의 키를 기준으로 수행됩니다(leftRecord.key == rightRecord.key). 양쪽 입력이 키로 파티션되어 있어야 합니다 조인 조건 자체이므로 키가 맞지 않으면 결과가 비어 있습니다
② 같은 파티션 수 조인의 좌·우 입력 토픽은 파티션 수가 같아야 합니다 검증합니다. 파티션 배정 단계(런타임)에 다르면 TopologyBuilderException이 발생합니다
③ 같은 파티셔닝 전략 입력 토픽에 쓰는 모든 애플리케이션이 같은 파티셔너를 써야 합니다. Java Producer면 같은 partitioner.class, Streams면 KStream#to()에 같은 StreamPartitioner 검증할 수 없습니다. 공식 문서가 "사용자가 보장해야 한다"고 명시합니다

co-partitioning이 필요하지 않은 두 가지 예외를 정확히 기억하세요 — KStream-GlobalKTable 조인(GlobalKTable의 모든 파티션이 각 인스턴스에 전부 있으므로)과 KTable-KTable foreign-key 조인(Streams가 내부적으로 co-partitioning을 보장하므로)입니다.

그리고 KStream-KStream 조인은 언제나 윈도우 조인입니다. 공식 문서의 이유 설명이 명확합니다 — 그렇지 않으면 조인에 쓰이는 내부 상태 저장소가 무한히 커지기 때문입니다. "윈도우 없는 stream-stream 조인"을 고르면 오답입니다.

모든 파티셔너 관련 설정을 기본값으로 두고 있다면 ③은 걱정할 일이 없다는 점도 문서가 짚어 줍니다. 문제가 되는 것은 커스텀 파티셔너를 쓰는 프로듀서가 한쪽 토픽에만 있는 경우입니다.

파티션 수가 다를 때

공식 문서가 권하는 절차는 이렇습니다.

  1. 양쪽 중 파티션 수가 적은 쪽을 찾습니다(SMALLER). bin/kafka-topics --describe로 확인합니다.
  2. 애플리케이션 안에서 SMALLER를 repartition으로 재분배합니다. LARGER와 같은 파티셔너를 써야 합니다.
    • KStream이면 KStream#repartition(Repartitioned.numberOfPartitions(...))
    • KTable이면 KTable#toStream#repartition(Repartitioned.numberOfPartitions(...).toTable())
  3. LARGER와 새 스트림/테이블을 조인합니다.

방향에 대한 문서의 권고도 함께 기억할 만합니다 — 병목을 피하려면 적은 쪽을 많은 쪽에 맞추는 것이 권장됩니다. stream-table 조인에서는 KStream을 재분배하는 쪽이 좋습니다. KTable을 재분배하면 상태 저장소가 하나 더 생길 수 있기 때문입니다. table-table 조인이면 더 작은 KTable을 재분배하는 편이 낫습니다.

병렬성 — 태스크와 스레드

Streams의 병렬성 모델은 Kafka 파티션에 그대로 얹혀 있습니다.

  • 각 스트림 파티션은 완전히 순서가 정해진 레코드 시퀀스이며 Kafka 토픽 파티션에 대응합니다.
  • Streams는 입력 스트림 파티션에 기반해 고정된 수의 태스크를 만들고, 각 태스크에 파티션 목록을 배정합니다.
  • 파티션-태스크 배정은 절대 변하지 않습니다. 태스크가 곧 고정된 병렬 단위입니다.
  • 따라서 최대 병렬성은 입력 토픽의 최대 파티션 수입니다. 입력 토픽이 5파티션이면 인스턴스를 최대 5개까지 의미 있게 돌릴 수 있습니다.
  • 파티션 수보다 많은 인스턴스는 기동은 되지만 유휴 상태로 남습니다. 대신 바쁜 인스턴스가 죽으면 그중 하나가 일을 이어받습니다 — 무의미한 것은 아니고 hot standby가 됩니다.

exactly-once 구현의 세대 변화

0.11.0.0프로듀서 트랜잭션·멱등성을 기반으로 Streams가 종단 exactly-once를 처음 제공(KIP-129).
2.6.0개선 구현 "exactly-once v2" 도입(KIP-447). 클라이언트·브로커 자원 사용이 줄고 처리량·확장성이 좋아졌습니다. 브로커 2.5.0 이상 필요.
3.0.01세대 exactly_once가 deprecated. 이후 exactly_once_v2만 씁니다.
4.3 (현행)processing.guarantee의 유효 값은 at_least_once(기본)와 exactly_once_v2 둘뿐입니다.

processing.guarantee의 기본값은 at_least_once입니다. "Streams는 기본적으로 exactly-once"라는 선택지는 오답입니다. 그리고 값 이름이 exactly_once_v2라는 점 — exactly_once는 3.0에서 deprecated, exactly_once_beta도 deprecated된 옛 이름입니다.

범위도 정확히 기억하세요. Kafka 토픽과 Streams 상태 저장소 안에서만 성립합니다. 처리 도중 외부 DB나 결제 API를 호출하면 그 보장은 거기서 끝납니다. 자세한 경계 설명은 6장 전달 보장과 트랜잭션에 있습니다.

인터랙티브 쿼리

Streams는 상태 저장소를 읽기 전용으로 직접 조회하는 것을 허용합니다. 저장소를 만든 애플리케이션 외부의 메서드·스레드·프로세스·애플리케이션에서도 접근할 수 있으며, 모든 저장소는 이름을 가지고 인터랙티브 쿼리는 읽기 연산만 노출합니다.

이 기능의 가치는 출력 토픽을 거치지 않고 최신 집계 결과를 바로 서빙할 수 있다는 점입니다. 집계 결과를 다시 외부 DB에 넣고 그것을 조회하는 단계가 사라집니다. 다만 상태는 인스턴스에 분산되어 있으므로, 찾는 키가 다른 인스턴스에 있으면 그 인스턴스로 요청을 라우팅해야 합니다. 그 메타데이터를 Streams가 제공합니다.

GlobalKTable을 쓰면 모든 인스턴스가 전체 데이터를 가지므로 라우팅이 필요 없습니다. 그 편의의 대가가 앞에서 본 저장 공간·네트워크 비용입니다. 데이터 크기에 따라 선택이 갈립니다.

Streams Rebalance Protocol (KIP-1071)

KIP-848이 일반 컨슈머의 리밸런스 조정을 클라이언트에서 브로커로 옮겼듯이, KIP-1071은 같은 모델을 Kafka Streams 워크로드로 확장합니다. 리밸런스 이벤트마다 클라이언트가 배정을 계산하는 대신, 브로커에서 배정이 지속적으로 계산됩니다. 애플리케이션은 컨슈머 그룹이 아니라 streams group으로 등록됩니다.

Streams Rebalance Protocol의 성숙도

Kafka 4.1Early Access. 기본 비활성이고 프로덕션 용도가 아니라고 릴리스 노트가 명시했습니다.
Kafka 4.2핵심 기능 집합이 production-ready. 신규 4.2 클러스터에서는 브로커 쪽이 기본 활성입니다. 다만 4.2.0에는 오프라인 마이그레이션 코드의 심각한 버그(KAFKA-20254)가 있어 4.2.0에서 classic → streams 마이그레이션은 권장되지 않습니다. 4.2.1에서 수정되었습니다.
Kafka 4.3 (현행)클라이언트 쪽 group.protocol 기본값은 여전히 classic입니다. 쓰려면 streams로 명시해야 합니다.

streams group에는 컨슈머 그룹에 없는 NOT_READY 상태가 있습니다. 그룹 코디네이터가 토폴로지에 필요한 소스·내부 토픽이 없거나 설정이 맞지 않는 것을 감지하면 이 상태로 들어가고, 모든 멤버는 빈 배정을 받습니다. 코디네이터가 하는 검사에는 co-partition 그룹이 실제로 co-partition되어 있는지 확인하는 단계가 포함됩니다 — 앞에서 본 요건이 브로커 쪽에서도 검증되기 시작한 것입니다.

테스팅 — 브로커 없이 토폴로지를 검증합니다

CCDAK에는 Application Testing 도메인이 별도로 있고(8%), 그 안에서 가장 자주 다뤄지는 것이 TopologyTestDriver입니다. kafka-streams-test-utils 아티팩트를 테스트 의존성으로 추가하면 씁니다.

TopologyTestDriver는 라이브러리 런타임을 시뮬레이션합니다 — 입력 토픽에서 레코드를 계속 가져와 토폴로지를 순회하며 처리하는 동작을 대신하고, 결과 레코드를 캡처하며 내장 상태 저장소를 조회할 수 있게 해 줍니다. 브로커가 필요하지 않습니다.

punctuation을 지원합니다. event-time punctuation은 처리한 레코드의 타임스탬프에 따라 자동으로 발동하고, wall-clock-time punctuation은 advanceWallClockTime()으로 직접 전진시켜 발동합니다 (드라이버가 wall-clock time을 내부적으로 모킹합니다).

상태 저장소는 테스트 전후 모두 접근할 수 있어서, 미리 값을 채워 두고 시작할 수도 있습니다. 다만 사전 채우기를 하려면 withLoggingDisabled()로 changelog를 끄고 저장소를 만들어야 합니다.

Processor API로 프로세서를 직접 작성했다면 MockProcessorContext로 단위 테스트합니다. 프로세서는 결과를 반환하지 않고 컨텍스트로 forward하므로, forward된 데이터를 캡처하는 목 컨텍스트가 필요합니다. context.forwarded()로 검증하고, context.committed()로 커밋 호출 여부를 확인합니다. 다만 목 컨텍스트는 punctuator를 자동 실행하지 않습니다 — 캡처만 하므로 직접 호출해야 하고, 자동 발동까지 테스트하려면 TopologyTestDriver를 쓰라고 문서가 권합니다. 또한 목 컨텍스트는 changelog를 관리하지 않으므로 상태 저장소는 인메모리 + logging disabled로 등록합니다.

ksqlDB — Streams 위의 SQL 계층

ksqlDB는 Confluent가 개발·배포하는 별도 컴포넌트이며 Apache Kafka 배포판에 포함되지 않습니다. 내부적으로 Kafka Streams 위에서 동작하므로, 이 장에서 다룬 개념 (KStream/KTable 이원성, 윈도우, co-partitioning, 상태 저장소)이 그대로 적용됩니다. 아래 구문은 개념 이해를 위한 예시이며, 정확한 문법과 기능 범위는 Confluent의 ksqlDB 문서를 확인하세요.

ksqlDB의 가치는 Java 애플리케이션을 배포하지 않고 SQL 문장으로 스트림 처리를 정의한다는 데 있습니다. Streams의 KStream이 STREAM, KTable이 TABLE에 대응합니다.

흔한 오해

"Streams를 쓰려면 별도 처리 클러스터가 필요하다" — 아닙니다. Streams는 라이브러리이고, 배포 단위는 그냥 여러분의 애플리케이션입니다. 다만 내부 토픽이 생긴다는 사실은 놓치기 쉽습니다 — 리파티션 토픽과 changelog 토픽이 application.id 접두어로 만들어지고 브로커의 디스크와 파티션 예산을 씁니다. changelog 토픽의 복제 계수는 replication.factor 기본값이 -1이라 브로커 기본값(1장 참고: default.replication.factor 기본 1)을 따라갑니다. 프로덕션에서 명시하지 않으면 상태가 복제되지 않을 수 있습니다.

"인스턴스를 늘리면 계속 빨라진다" — 파티션 수까지만입니다. 태스크 수는 입력 토픽의 파티션 수로 고정되고, 파티션-태스크 배정은 절대 변하지 않습니다. 입력 토픽이 6파티션이면 7번째 인스턴스는 유휴 상태로 남습니다(hot standby 역할은 합니다). 처리량을 더 올려야 하면 파티션 수를 늘려야 하고, 그 대가는 7장과 케이스 5에서 다룹니다.

"윈도우가 닫히면 결과가 나온다" — 기본 동작은 그렇지 않습니다. 윈도우 계산은 새 데이터가 올 때마다 결과를 갱신해 계속 내려보냅니다. "닫힐 때 한 번"을 원하면 suppress를 써야 합니다. 그리고 윈도우가 닫히는 기준인 stream time은 레코드가 도착할 때만 전진하므로, 트래픽이 끊기면 마지막 윈도우가 영원히 닫히지 않을 수 있습니다.

시험 포인트 정리

  • map·flatMap·selectKey는 리파티션을 유발(표시)하고, mapValues·flatMapValues·filter는 유발하지 않습니다.
  • groupBy는 항상, groupByKey는 표시됐을 때만 리파티션합니다.
  • co-partitioning 3요건: 같은 키 · 같은 파티션 수 · 같은 파티셔너. Streams는 파티션 수만 검증하고 파티셔너는 검증하지 못합니다.
  • KStream-GlobalKTable 조인과 KTable-KTable foreign-key 조인은 co-partitioning이 불필요합니다.
  • KStream-KStream 조인은 반드시 윈도우가 필요합니다 (상태 저장소가 무한히 커지므로).
  • KStream은 INSERT, KTable은 UPSERT이고 KTable의 null은 DELETE(tombstone)입니다.
  • 같은 입력에 대한 합산: KStream이면 4, KTable이면 3.
  • processing.guarantee 기본값은 at_least_once. EOS 값 이름은 exactly_once_v2이고 브로커 2.5+가 필요합니다.
  • EOS를 켜면 commit.interval.ms 기본값이 100ms로, 컨슈머는 read_committed로 바뀝니다.
  • num.stream.threads 기본 1, num.standby.replicas 기본 0, replication.factor 기본 -1.
  • 태스크 수 = 입력 토픽 파티션 수. 파티션보다 많은 인스턴스는 유휴 상태입니다.
  • tumbling은 hopping의 특수 사례(size == advance)이고, 다른 도구의 "sliding"은 Kafka Streams의 hopping입니다.
  • tumbling·hopping은 epoch 정렬, sliding은 레코드 타임스탬프 정렬이며 sliding만 양쪽 경계가 포함입니다.
  • 브로커 없이 토폴로지 테스트 → TopologyTestDriver (kafka-streams-test-utils).
  • TestInputTopic.pipeInput() → TestOutputTopic.readKeyValue() → testDriver.close().
  • wall-clock punctuation은 advanceWallClockTime()로 직접 전진시켜야 발동합니다.
  • 상태 저장소 사전 채우기에는 withLoggingDisabled()가 필요합니다.
  • Processor 단위 테스트는 MockProcessorContext. punctuator를 자동 실행하지 않습니다.
  • 클라이언트 단위 테스트는 MockProducer / MockConsumer. 예외 주입은 setPollException().
  • 성능 측정은 kafka-producer-perf-test.sh / kafka-consumer-perf-test.sh, 종단 지연은 kafka-e2e-latency.sh.
