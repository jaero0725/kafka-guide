기본개념 · 9장

Kafka Connect

Kafka Connect는 외부 시스템과 Kafka 사이의 데이터 이동을 코드 없이 설정으로 처리하는 프레임워크입니다. 이 장에서는 worker · connector · task · converter · transform이라는 다섯 개의 어휘를 정확히 구분하고, 운영에서 가장 자주 물리는 두 지점 — source와 sink가 오프셋을 서로 다른 곳에 저장한다는 사실과 REST API가 409를 돌려주는 이유 — 를 원리부터 정리합니다. CCDAK에서 Kafka Connect는 15% 비중을 차지합니다.

학습 목표

  • worker · connector · task · converter · transform의 역할과 경계를 구분할 수 있습니다.
  • standalone과 distributed 모드의 차이, 그리고 distributed 모드에서만 가능한 것을 설명할 수 있습니다.
  • source 커넥터는 offset.storage.topic에, sink 커넥터는 __consumer_offsets에 진행 위치를 저장한다는 비대칭을 설명할 수 있습니다.
  • SMT가 stateless · 메시지 단위라는 제약과, 그래서 무엇을 할 수 없는지 판단할 수 있습니다.
  • errors.tolerance와 DLQ 설정 조합을 읽고 어떤 레코드가 어디로 가는지 예측할 수 있습니다.
  • REST API가 409 Conflict를 반환하는 세 가지 상황과 대응을 설명할 수 있습니다.

Connect가 해결하는 문제

데이터베이스 변경을 Kafka로 보내고, Kafka의 이벤트를 검색 엔진과 데이터 웨어하우스로 내려보내는 코드는 어느 조직에나 있습니다. 그리고 그 코드는 거의 항상 같은 문제를 다시 풉니다 — 어디까지 읽었는지 기록하고, 실패하면 재시도하고, 프로세스가 죽으면 다른 노드에서 이어받고, 스키마를 변환합니다. 공식 문서는 Connect의 목적을 "Kafka와 다른 시스템 사이에서 데이터를 확장성 있고 신뢰성 있게 흘려보내는 도구"로 정의하며, 그 특징으로 커넥터 공통 프레임워크, standalone/distributed 두 모드, REST 인터페이스, 자동 오프셋 관리, 기본 제공되는 분산·확장성, 스트리밍/배치 통합을 듭니다.

Connect를 쓰는 판단 기준은 간단합니다. 데이터를 옮기기만 한다면 Connect, 옮기면서 계산해야 한다면 Kafka Streams입니다. 이 경계는 뒤에서 다루는 SMT의 제약에서 다시 등장합니다.

standalone과 distributed 모드

Connect는 두 가지 실행 모드를 지원합니다. standalone은 모든 작업이 단일 프로세스에서 수행되며 설정이 간단하지만, 공식 문서는 내고장성(fault tolerance) 같은 Connect의 일부 기능을 누리지 못한다고 명시합니다. distributed는 작업 자동 분배, 동적 스케일 인/아웃, 그리고 활성 태스크와 설정·오프셋 커밋 데이터 양쪽에 대한 내고장성을 제공합니다.

"standalone 모드에서 source 커넥터의 exactly-once를 켜려면?"이라는 형태의 문항이 나오면 불가능이 정답입니다. 공식 문서는 source 커넥터의 exactly-once 지원이 distributed 모드에서만 제공된다고 못 박고 있습니다. 또한 standalone에서 source 오프셋이 가는 곳은 토픽이 아니라 offset.storage.file.filename이 가리키는 로컬 파일입니다.

모든 워커가 요구하는 설정

워커 설정에 그냥 적은 파라미터는 내부 토픽 접근용 클라이언트에 적용됩니다. source 태스크의 프로듀서와 sink 태스크의 컨슈머에는 producer. / consumer. 접두어를 붙여야 합니다. 접두어 없이 상속되는 유일한 값은 bootstrap.servers입니다. 보안이 켜진 클러스터라면 같은 인증 설정을 최대 세 번 (관리용 · source용 · sink용) 적어야 한다는 점을 공식 문서가 지적합니다. 커넥터별 개별 오버라이드는 producer.override. / consumer.override. 접두어를 씁니다.

내부 토픽 3종

distributed 모드의 Connect 클러스터는 상태를 워커 로컬에 두지 않고 Kafka 토픽 세 개에 둡니다. 그래서 워커가 죽어도 다른 워커가 이어받을 수 있습니다. 공식 문서는 이 세 토픽을 Connect 기동 전에 직접 만들 것을 권장합니다. 자동 생성에 맡기면 브로커의 기본 파티션 수·복제 계수가 적용되어 용도에 맞지 않을 수 있기 때문입니다.

이 장에서 하나만 기억해야 한다면 이것입니다. 같은 "오프셋"이라는 단어를 쓰지만 source와 sink는 완전히 다른 것을 다른 곳에 저장합니다.

데이터 방향 외부 시스템 → Kafka Kafka → 외부 시스템
"오프셋"이 가리키는 것 소스 시스템 안의 위치 (파일 바이트 위치, DB의 binlog 좌표, 테이블의 증가 컬럼 값 등). 커넥터가 스스로 정의한 임의 구조입니다. Kafka 토픽-파티션의 컨슈머 오프셋. 형식이 모든 sink 커넥터에 공통입니다.

가장 자주 출제되는 지점입니다. "sink 커넥터의 오프셋은 어디에 저장되는가?"라는 문항에서 offset.storage.topic을 고르면 오답입니다. sink 태스크는 내부적으로 그냥 컨슈머이며, __consumer_offsets에 커밋합니다. 반대로 "source 커넥터의 진행 위치"는 offset.storage.topic입니다.

이 비대칭이 실무에서 갖는 의미: sink 커넥터를 처음부터 다시 읽히려면 Connect의 내부 토픽을 건드릴 필요가 없습니다. kafka-consumer-groups.sh --reset-offsets --group connect-{커넥터명}으로 충분합니다 (커넥터를 먼저 정지해야 합니다). 반면 source 커넥터는 그 방법이 통하지 않습니다 — DELETE /connectors/{name}/offsets를 STOPPED 상태에서 호출합니다.

offset 필드가 null이면 해당 파티션의 오프셋을 초기화합니다. 공식 문서는 source 커넥터의 요청 본문 형식은 커넥터 구현에 따라 다르고, sink 커넥터는 공통 형식이라는 점을 명시합니다 — 이것도 위 비대칭의 결과입니다.

Connect의 기본 전달 보장은 at-least-once입니다. offset.flush.interval.ms가 1분이므로, 워커가 갑자기 죽으면 최대 1분치를 다시 처리할 수 있습니다. 목적지가 중복에 민감하다면 sink 쪽에 멱등 upsert를 두어야 합니다. Kafka 내부의 exactly-once가 외부 시스템까지 확장되지 않는다는 원칙은 6장 전달 보장과 트랜잭션과 같습니다.

Converter — Kafka에 무슨 바이트가 쓰이는가

커넥터는 데이터를 Connect의 내부 표현(Struct/Map + Schema)으로 다룹니다. 그것을 Kafka에 저장될 바이트열로 바꾸는 것이 converter입니다. converter는 커넥터와 독립이라서, 같은 JDBC source 커넥터를 Avro로도 JSON으로도 쓸 수 있습니다.

...converters.{Boolean,Double,Float,Integer,Long,Short}Converter 원시 타입 단일 값 변환 키가 숫자인 파이프라인에서 유용합니다
org.apache.kafka.connect.storage.SimpleHeaderConverter 헤더 값 변환. header.converter의 기본값 —

AvroConverter, ProtobufConverter, JsonSchemaConverter는 Apache Kafka 배포판에 포함되지 않습니다. Schema Registry와 함께 쓰는 Confluent 컴포넌트이며 plugin.path에 별도로 설치해야 합니다. wire format(magic byte + schema id + payload)과 호환성 모드는 8장 스키마와 직렬화에서 다룹니다.

JsonConverter의 schemas.enable 기본값은 true입니다. 이 상태로 쓰면 모든 메시지가 {"schema":{...},"payload":{...}} 형태로 감싸져 페이로드보다 스키마가 더 큰 결과가 나옵니다. 외부 시스템이 순수 JSON을 기대한다면 아래처럼 꺼야 합니다. key와 value를 각각 지정해야 한다는 점도 놓치기 쉽습니다.

스키마 봉투가 붙어 나갑니다. 목적지가 순수 JSON을 기대하면 파싱에 실패합니다.

스키마 없는 순수 JSON이 나갑니다. key/value를 각각 지정합니다.

SMT — Single Message Transform

공식 문서는 transform을 "가벼운 메시지 단위(message-at-a-time) 수정"이라고 정의하며, 데이터 정리와 이벤트 라우팅에 편리하다고 설명합니다. 이 정의에 SMT의 능력과 한계가 모두 들어 있습니다.

SMT의 성질 네 가지는 그대로 출제 지점입니다.

  • 레코드 하나씩 처리합니다. 여러 레코드를 함께 보지 못합니다.
  • stateless입니다. 상태 저장소가 없으므로 집계·조인·중복 제거·윈도우가 불가능합니다.
  • 체인으로 여러 개를 엮으며 transforms 목록의 순서가 결과를 바꿉니다.
  • 적용 지점이 방향에 따라 다릅니다 — source는 Kafka에 쓰기 전, sink는 목적지에 쓰기 직전입니다.

따라서 "여러 이벤트를 합산해 새 필드를 만들고 싶다"는 요구는 SMT로 풀 수 없습니다. Kafka Streams나 ksqlDB로 가야 합니다. 이 경계를 묻는 문항이 자주 나옵니다.

409 Conflict가 나는 이유

distributed 모드에서 REST API는 사용자 인터페이스이면서 워커 사이의 클러스터 내부 통신 채널이기도 합니다. 팔로워 워커가 받은 일부 요청은 리더 워커로 전달(forward)됩니다. 409 Conflict는 이 구조와 리밸런스가 만나는 지점에서 나옵니다.

409 Conflict의 원인과 대응
원인무슨 상황인가대응
리밸런스 진행 중 워커 합류·이탈, 커넥터 추가·설정 변경으로 클러스터가 재구성되는 동안 쓰기성 요청이 들어옴. 공식 문서는 리밸런스 중 태스크 재시작을 시도하면 409를 반환한다고 명시합니다 리밸런스 완료 후 재시도. 다만 리밸런스 자체가 커넥터·태스크를 사실상 재시작하므로 재시도가 불필요할 수도 있습니다
동명 커넥터가 이미 존재 POST /connectors에 이미 등록된 name을 다시 보냄. 공식 문서는 같은 이름으로 재등록하면 실패한다고 명시합니다 GET /connectors로 확인. 설정을 바꾸려는 것이면 PUT /connectors/{name}/config를 쓰세요
리더가 아닌 워커로 간 요청의 포워딩 실패 쓰기성 요청은 리더가 처리해야 하는데, 리더가 아직 정해지지 않았거나 포워딩 대상에 도달할 수 없음. rest.advertised.*가 잘못돼 워커끼리 서로 못 찾는 경우가 대표적입니다 rest.advertised.host.name·rest.advertised.port·rest.advertised.listener가 다른 워커에서 실제로 도달 가능한 주소인지 확인

409는 재시도 가능한(retriable) 상태 코드로 다뤄야 합니다. "커넥터 배포 스크립트가 409를 받았다. 무엇을 해야 하는가?"라는 문항에서 커넥터를 삭제하고 다시 만든다를 고르면 오답입니다. 정답 방향은 리밸런스 완료를 기다린 뒤 재시도 / 이름 충돌 확인입니다.

함께 나오는 오해: Connect는 실패한(FAILED) 태스크를 자동으로 재시작하지 않습니다. 그래서 커넥터 상태가 RUNNING인데도 태스크 하나가 FAILED로 남아 데이터가 부분적으로만 흐르는 상황이 생깁니다. 모니터링은 커넥터 상태가 아니라 태스크 상태까지 봐야 합니다.

Connect 워커는 각 노드의 로컬 파일에 로그를 남깁니다. 따라서 실패한 태스크의 상세 로그를 보려면 그 태스크가 배정되어 있던 워커의 로그를 직접 조회해야 합니다. GET /connectors/{name}/status의 worker_id가 그 노드를 알려 줍니다. 클러스터 전체를 한 곳에서 보려면 로그를 중앙 수집기로 보내도록 log4j2 appender를 추가하고, 커넥터별로 로그를 분리해 두는 것이 좋습니다. 런타임 레벨 조정은 위의 PUT /admin/loggers/{logger}로 합니다.

태스크 재분배와 확장 전략

공식 문서에 따르면 리밸런스는 다음 상황에 발생합니다 — 커넥터가 클러스터에 처음 제출될 때, 커넥터가 요구하는 태스크 수가 늘거나 줄 때, 커넥터 설정이 변경될 때, 그리고 워커가 그룹에 추가되거나 제거될 때 (의도적 업그레이드든 장애든).

증분 협력적 리밸런스

2.3.0 이전에는 리밸런스마다 클러스터의 모든 커넥터와 태스크를 전부 재배치했습니다. 2.3.0부터 기본값이 증분 협력적 리밸런스(incremental cooperative rebalancing)로 바뀌어, 새로 생기거나 없어지거나 이동해야 하는 태스크만 영향을 받습니다. 나머지 태스크는 멈추지도 재시작하지도 않습니다. connect.protocol의 4.3 기본값은 sessioned이며, eager로 두면 옛 전량 재배치 동작으로 돌아갑니다.

확장의 실제 상한

Connect의 병렬성은 세 단계로 제한됩니다.

  1. 커넥터가 만들 수 있는 태스크 수 — tasks.max는 상한일 뿐이고, 커넥터가 소스를 그만큼 쪼갤 수 없으면 태스크가 덜 생깁니다. sink 커넥터의 실질 상한은 구독 토픽의 총 파티션 수입니다.
  2. 워커 수 — 태스크는 워커에 배치되므로 워커가 적으면 한 프로세스에 태스크가 몰립니다.
  3. 목적지 시스템의 수용력 — 대부분의 실제 병목은 여기입니다.

"커넥터를 늘리면 무조건 빨라진다" — 아닙니다. 같은 토픽을 읽는 sink 커넥터를 두 개 만들면 서로 다른 컨슈머 그룹이 되어 같은 데이터를 두 번 목적지에 씁니다. 처리량이 두 배가 되는 것이 아니라 중복이 두 배가 됩니다. 처리량을 올리려면 커넥터 수가 아니라 tasks.max와 워커 수를 올려야 합니다.

"tasks.max를 파티션 수보다 크게 잡으면 더 빨라진다" — 아닙니다. sink 커넥터의 태스크는 컨슈머 그룹의 멤버처럼 파티션을 나눠 갖습니다. 파티션 수를 넘는 태스크는 아무 파티션도 배정받지 못하고 유휴 상태로 남습니다. 컨슈머 그룹의 파티션 소유권 모델과 같습니다(5장).

"커넥터 설정을 바꾸는 것은 커넥터 하나에만 영향을 준다" — 아닙니다. 커넥터 설정 변경은 Connect 클러스터의 리밸런스를 유발합니다. 증분 협력적 리밸런스라 영향 범위가 예전보다 좁아졌지만, 여전히 클러스터 이벤트입니다. 바쁜 시간대에 여러 커넥터의 설정을 연속으로 바꾸면 리밸런스가 계속 이어질 수 있습니다.

Connect에서의 exactly-once

공식 문서는 sink 커넥터의 exactly-once는 0.11.0부터, source 커넥터는 3.3.0부터 지원한다고 밝히면서, 동시에 "exactly-once 지원은 실행하는 커넥터 종류에 크게 의존한다"고 경고합니다. 워커 설정을 모두 올바르게 맞추더라도, 커넥터 자체가 프레임워크의 기능을 활용하도록 설계되지 않았다면 exactly-once가 성립하지 않습니다.

Connect exactly-once 설정

exactly.once.source.support 워커 · disabled source의 프레임워크 레벨 지원. disabled / preparing / enabled. distributed 모드 전용

보안에서 놓치기 쉬운 것

공식 문서는 이 점을 매우 직접적으로 경고합니다 — 기본적으로 REST API는 보호되지 않고, 접근할 수 있는 누구나 커넥터를 시작·중지할 수 있습니다. Connect는 커스텀 플러그인을 실행하므로 임의 코드 실행이 가능합니다. 신뢰할 수 있는 사용자에게만 노출하고, 신뢰하는 플러그인만 설치하세요.

그리고 connector.client.config.override.policy의 기본값이 All이라 커넥터 설정으로 sasl.jaas.config나 sasl.login.class까지 덮어쓸 수 있습니다. 이 값들은 설계상 워커에서 코드를 실행할 수 있게 합니다. Kafka 4.2부터 Allowlist가 권장되며 5.0에서 기본값이 됩니다.

Connect 워커의 principal은 최소한 다음 ACL이 필요합니다 — Connect 클러스터 group.id에 대한 Group Read, 내부 토픽 3종에 대한 Topic Read·Write (토픽이 아직 없으면 Create까지). 커넥터별로는 source가 대상 토픽에 Write, sink가 connect-{커넥터명} 그룹에 Read와 구독 토픽에 Read, 그리고 DLQ 토픽에 Write가 필요합니다. DLQ 권한을 빼먹어 DLQ 쓰기가 실패하는 것이 흔한 초기 설정 실수입니다.

시험 포인트 정리

  • source 오프셋 → offset.storage.topic, sink 오프셋 → __consumer_offsets. 이 비대칭이 이 도메인 최다 출제 지점입니다.
  • 내부 토픽 3종은 config·offset·status이고 전부 cleanup.policy=compact입니다. config 토픽은 단일 파티션입니다.
  • standalone에서는 source 오프셋이 로컬 파일(offset.storage.file.filename)이고, source exactly-once가 불가능합니다.
  • SMT는 stateless · 레코드 단위입니다. 집계·조인·중복 제거는 못 합니다. source는 쓰기 전, sink는 쓰기 직전 적용.
  • errors.tolerance의 값은 none(기본)과 all 둘뿐입니다.
  • DLQ는 sink 전용이고 errors.deadletterqueue.topic.name이 비어 있으면 꺼진 것입니다. context.headers.enable=true로 원인 헤더를 남기세요.
  • 409는 리밸런스 중 / 동명 커넥터 / 리더 포워딩 실패. 재시도 가능한 상태입니다.
  • 실패한 태스크는 자동 재시작되지 않습니다. POST .../restart?onlyFailed=true를 직접 호출합니다.
  • tasks.max는 상한일 뿐이며, sink의 실질 상한은 구독 토픽 파티션 수입니다.
  • PAUSED는 자원 유지, STOPPED는 자원 해제. 오프셋 수정은 STOPPED에서만.
  • 워커 로그는 노드 로컬입니다. status의 worker_id로 어느 노드를 볼지 정합니다.
  • PUT /admin/loggers/{logger}로 재시작 없이 로그 레벨을 바꿉니다.
  • scheduled.rebalance.max.delay.ms 기본 5분 — 워커 이탈 후 이 시간 동안 태스크가 미배정으로 남습니다. 롤링 재시작 시간과 함께 고려하세요.
  • 내부 토픽 3종은 Connect 기동 전에 직접 생성하는 것이 권장됩니다.
  • REST API는 기본 무인증이며 임의 코드 실행 경로입니다. 네트워크 수준에서 격리하세요.
