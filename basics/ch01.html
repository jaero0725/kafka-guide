기본개념 · 1장

Kafka 개요와 이벤트 스트리밍

Apache Kafka는 이벤트를 발행·구독하고, 원하는 기간만큼 durable하게 저장하고, 실시간 또는 사후에 처리하는 세 가지 일을 한 시스템에서 처리합니다. 이 장에서는 그 세 가지가 왜 한 묶음이어야 했는지, 전통적 메시지 큐와 무엇이 다른지, 그리고 이후 10개 장에서 계속 쓰게 될 토픽·파티션·오프셋 어휘를 정리합니다.

학습 목표

  • 이벤트 스트리밍이 해결하는 문제를 설명하고, 전통적 메시지 큐와 분산 커밋 로그의 차이를 구분할 수 있습니다.
  • 토픽 · 파티션 · 오프셋 · 레플리카의 관계를 그림 없이도 설명할 수 있습니다.
  • Producer · Consumer · Connect · Streams · Schema Registry가 각각 어떤 역할을 맡는지 구분할 수 있습니다.
  • kafka_2.13-4.3.0 같은 배포 파일명을 읽고, 2.13이 Kafka 버전이 아님을 설명할 수 있습니다.

왜 Kafka인가 — 메시지 큐가 아니라 로그입니다

시스템이 늘어나면 데이터 이동 경로가 곱셈으로 늘어납니다. 주문 서비스가 재고·정산·알림·분석에 각각 직접 연결하면 연결선은 서비스 수의 곱에 비례해 늘고, 새 소비자를 추가할 때마다 생산자 쪽을 고쳐야 합니다. Kafka는 그 사이에 durable한 로그를 하나 두어 생산자와 소비자를 완전히 분리합니다. 공식 문서는 이를 세 가지 능력의 조합으로 정의합니다.

  1. 이벤트 스트림을 발행(publish)하고 구독(subscribe)한다.
  2. 이벤트 스트림을 원하는 기간만큼 durable하고 신뢰성 있게 저장한다.
  3. 이벤트 스트림을 발생 시점에 또는 사후에 처리한다.

두 번째 항목이 전통적 메시지 큐와 결정적으로 다른 지점입니다. Kafka에서 이벤트는 소비되어도 삭제되지 않습니다. 보관 기간은 토픽별 설정으로 정하고, 그 기간이 지난 이벤트만 버려집니다. 읽기 위치는 브로커가 아니라 소비자 쪽 오프셋이 결정하므로, 같은 데이터를 여러 소비자가 각자의 속도로, 필요하면 처음부터 다시 읽을 수 있습니다.

전통적 메시지 큐(브로커 중심 소비 모델)와 Kafka의 로그 모델 비교

공식 문서는 하나의 데이터 단위를 event라고 부르며, record 또는 message도 같은 것을 가리킨다고 명시합니다. 이 가이드에서는 저장 구조를 이야기할 때 레코드(record), 비즈니스 의미를 이야기할 때 이벤트(event)를 씁니다. 하나의 이벤트는 키(key) · 값(value) · 타임스탬프(timestamp) · 선택적 헤더(headers)로 구성됩니다.

핵심 추상 — 이벤트, 토픽, 파티션, 오프셋

토픽과 파티션

이벤트는 토픽(topic)에 저장됩니다. 토픽은 파일시스템의 폴더에 가깝고, 이벤트가 그 안의 파일에 해당합니다. 토픽은 항상 다중 생산자·다중 구독자이며, 생산자 0개 이상, 소비자 0개 이상이 붙을 수 있습니다.

토픽은 여러 파티션(partition)으로 쪼개져 서로 다른 브로커에 배치됩니다. 이 분산 배치가 확장성의 근거입니다. 클라이언트가 여러 브로커에 동시에 읽고 쓸 수 있기 때문입니다. 새 이벤트를 토픽에 발행하면 실제로는 그중 한 파티션의 끝에 append됩니다.

같은 키를 가진 이벤트는 같은 파티션에 기록됩니다. 그리고 Kafka는 특정 토픽-파티션의 소비자가 그 파티션의 이벤트를 기록된 순서 그대로 읽는 것을 보장합니다. 순서 보장이 파티션 단위인 이유가 여기 있습니다. 주문 ID를 키로 쓰면 그 주문의 상태 변화가 뒤바뀌지 않습니다. 키를 지정하지 않으면 순서 보장의 근거 자체가 사라집니다 — 이 실수의 결과는 케이스 4에서 다룹니다.

오프셋 — 파티션 안의 좌표

오프셋(offset)은 파티션 안에서 레코드의 위치를 나타내는 단조 증가 정수입니다. 파티션에 append될 때 부여되고, 이후 변하지 않습니다. 오프셋은 파티션 안에서만 의미가 있습니다. 토픽 전체를 가로지르는 전역 오프셋은 존재하지 않습니다.

실무와 시험에서 가장 많이 혼동되는 것은 오프셋이 한 종류가 아니라는 점입니다. 하나의 파티션 로그 위에 최소 네 개의 서로 다른 지점이 동시에 존재합니다. 아래 다이어그램의 슬라이더를 움직여 이 네 지점이 어떻게 벌어지는지 확인해 보세요. 복제·ISR과 함께 보는 상세한 설명은 2장 아키텍처와 핵심 개념에 있습니다.

복제 — 파티션 단위로 복사됩니다

내구성과 가용성은 복제(replication)로 확보합니다. 복제 단위는 토픽이 아니라 토픽-파티션입니다. 공식 문서는 프로덕션에서 흔히 쓰이는 설정으로 복제 계수(replication factor) 3을 예로 듭니다. 즉 같은 파티션의 사본이 항상 3개 존재합니다. 파티션마다 리더 하나와 팔로워 0개 이상이 있고, 쓰기는 리더로 갑니다.

브로커의 default.replication.factor 기본값은 1이고 num.partitions 기본값도 1입니다. 자동 생성된 토픽은 복제되지 않은 단일 파티션이 됩니다. 프로덕션 토픽은 항상 명시적으로 생성하고 파티션 수와 복제 계수를 직접 지정하세요. 자세한 무손실 설정 조합은 4장 Producer 심화와 설정 치트시트를 보세요.

Kafka 생태계와 5개 API

Kafka는 서버(브로커)와 클라이언트가 TCP 기반 자체 프로토콜로 통신하는 분산 시스템입니다. 서버 일부는 저장 계층인 브로커를 이루고, 다른 일부는 Kafka Connect를 실행해 외부 시스템과 데이터를 주고받습니다. 공식 문서는 Java·Scala용 핵심 API를 다섯 개로 정리합니다.

클라이언트는 어떻게 클러스터를 찾는가

클라이언트는 bootstrap.servers에 적힌 host:port 목록으로 최초 연결을 맺고, 그 연결로 메타데이터를 받아 클러스터 전체를 알아냅니다. 공식 문서는 이 목록에 전체 브로커를 적을 필요가 없다고 명시하면서도, 일부 서버가 죽어 있을 때를 대비해 여러 개를 적으라고 권고합니다.

부트스트랩 지점이 하나뿐입니다. 이 브로커가 재시작 중이면 클러스터가 정상인데도 클라이언트가 붙지 못합니다.

초기 연결 지점을 이중화했습니다. 하나만 붙으면 나머지 브로커는 메타데이터로 알아내므로, 전체 목록을 적을 필요는 없습니다.

CCDAK · Application Development — "bootstrap.servers에 브로커를 여럿 적는 이유는?"이라는 문항에서 부하 분산을 고른 답은 오답입니다. 목적은 부트스트랩 시점의 단일 장애점 제거입니다. 실제 요청 부하는 파티션 리더 위치에 따라 분산되며, 그 정보는 메타데이터로 받습니다.

Kafka 버전 표기 읽는 법 — 2.13은 Kafka 버전이 아닙니다

Kafka 배포 파일명은 두 개의 버전 번호를 한 줄에 담고 있어서 매우 흔하게 오해를 일으킵니다. Apache 아카이브의 4.3.1 디렉터리에는 kafka_2.13-4.3.1.tgz 하나만 올라와 있습니다.

_2.13은 이 배포판이 컴파일된 Scala 버전입니다. Kafka 버전은 뒤쪽의 4.3.1입니다. Kafka 2.13이라는 버전은 존재하지 않습니다 — Kafka는 2.8 다음이 3.0입니다.

Scala를 직접 쓰지 않는다면 고민할 것 없이 _2.13을 고르면 됩니다. 현행 Kafka 배포판은 Scala 2.13용만 제공하며, 브로커는 JVM 바이너리로 동작하므로 Java만 있으면 됩니다. Scala 버전은 Java 클라이언트 API와 무관합니다.

내려받은 뒤 클러스터를 처음 띄우는 절차는 공식 quickstart와 같습니다. KRaft에서는 클러스터 UUID를 만들고 로그 디렉터리를 포맷한 뒤 브로커를 기동합니다. 동작하는 3노드 구성은 예제 1에서 다룹니다.

Apache Kafka 4.3 문서는 Java 17 · 21 · 25를 완전 지원하고, Java 11은 clients · streams 등 일부 모듈에만 해당한다고 명시합니다. Java 8은 4.0에서 제거되어 더 이상 지원되지 않습니다. 즉 서버(브로커)를 돌리려면 최소 Java 17이 필요합니다.

Kafka 4.x가 이전과 다른 점

이 가이드는 Apache Kafka 4.3.x를 기준으로 서술합니다. 시중 한국어 자료 대부분이 2.x/3.x(ZooKeeper 시대) 기준이므로, 특히 아래 세 가지는 예전 자료를 그대로 따라 하면 동작하지 않습니다.

메타데이터 저장소 — KRaft가 유일한 모드입니다

Kafka 2.xZooKeeper 앙상블이 필수였습니다. 토픽 메타데이터·ACL·동적 설정·컨트롤러 선출이 모두 거기 있었습니다.
Kafka 3.x3.3부터 KRaft가 production-ready가 되어 두 방식이 공존했습니다. 3.9가 마지막 ZooKeeper 지원 버전입니다.
Kafka 4.xZooKeeper 모드가 제거되었습니다. 4.3 업그레이드 문서는 브로커 업그레이드에 KRaft가 필수이며 소프트웨어·메타데이터 버전이 최소 3.3.x여야 한다고 명시합니다. ZooKeeper 클러스터는 4.3으로 올리기 전에 반드시 KRaft로 마이그레이션해야 합니다.

그래서 CLI의 --zookeeper 옵션도 4.0에서 제거되었습니다. 모든 명령은 --bootstrap-server를 씁니다. 자세한 배경과 마이그레이션 경로는 부록 · 버전 표기와 레거시에 있습니다.

새 컨슈머 리밸런스 프로토콜 (KIP-848)

4.0에서 GA가 되어 프로덕션 워크로드에 쓸 수 있습니다. 전면 증분 설계라서 전역 동기화 장벽(stop-the-world)이 없고 리밸런스 시간이 짧습니다. 서버 쪽은 4.0부터 자동 활성화되지만, 컨슈머 쪽은 기본값이 아닙니다. group.protocol의 기본값은 여전히 classic이며, 새 프로토콜을 쓰려면 consumer로 명시해야 합니다.

새 프로토콜을 켜면 heartbeat.interval.ms, session.timeout.ms, partition.assignment.strategy는 더 이상 클라이언트에서 쓰이지 않습니다(브로커가 관리합니다). 상세는 5장 Consumer 심화에서 다룹니다.

Queues for Kafka — Share Groups (KIP-932)

컨슈머 그룹과 나란히 존재하는 새로운 그룹 종류입니다. 4.1에서 preview, 4.2에서 production-ready가 되었습니다. 컨슈머 그룹과 달리 한 파티션을 여러 컨슈머가 함께 소비할 수 있고, 컨슈머 수가 파티션 수를 넘어설 수 있으며, 레코드 단위로 ack합니다. 배달 시도 횟수도 집계됩니다. 순서 있는 스트림보다 "레코드를 하나씩 처리하는" 작업 큐 성격의 워크로드에 씁니다. 자세한 내용은 11장 운영 기초에 있습니다.

흔한 오해

"Kafka는 메시지 큐라서 읽으면 사라진다" — 아닙니다. 소비는 읽기일 뿐이고, 데이터는 보관 정책에 따라 남습니다. retention.ms의 기본값은 604800000ms(7일)입니다. 같은 데이터를 다른 소비자 그룹이 다시 읽을 수 있고, 오프셋을 되돌려 재처리할 수도 있습니다. 반대로 말하면 보관 기간이 지나면 아무도 못 읽습니다. 장애 복구에 며칠이 필요한 파이프라인이라면 이 값을 먼저 확인하세요.

"파티션을 많이 만들면 항상 빨라진다" — 아닙니다. 파티션은 소비 병렬성의 상한을 올리지만, 브로커가 관리할 메타데이터, 열어 둘 파일 핸들, 리밸런스 비용, 리더 선출 대상이 함께 늘어납니다. 파티션을 1000개로 늘려 오히려 느려진 사례는 케이스 5에서 다룹니다. 그리고 파티션 수는 늘릴 수만 있고 줄일 수 없으며, 늘리면 기존 키의 해시 분배가 바뀌어 순서 보장이 깨집니다.

"Kafka가 exactly-once를 지원하니 중복은 걱정 없다" — 범위를 잘못 이해한 것입니다. Kafka의 EOS는 Kafka 토픽을 읽고 처리해 Kafka 토픽에 쓰는 경계 안에서만 성립합니다. 외부 데이터베이스나 결제 API를 호출하는 순간 그 보장은 끝나므로, 소비자 쪽 멱등성을 직접 구현해야 합니다. 기본 동작은 at-least-once이며, 이 경계 문제는 6장 전달 보장과 트랜잭션과 케이스 7에서 다룹니다.

시험 포인트

이 장 범위에서 반복 출제되는 지점입니다.

  • 순서 보장의 단위는 파티션입니다. 토픽 전체가 아닙니다. 키가 없으면 순서 근거가 없습니다.
  • 오프셋은 파티션 안에서만 의미가 있습니다. 전역 오프셋은 없습니다.
  • bootstrap.servers를 여럿 적는 목적은 초기 연결 이중화이며 부하 분산이 아닙니다.
  • message.max.bytes 기본값은 1048588이고 압축 후 배치 기준입니다.
  • 2.13은 Scala 버전입니다. Kafka 2.13은 존재하지 않습니다.
  • ZooKeeper는 4.0에서 제거되었고 --zookeeper 옵션도 없습니다.
  • KIP-848은 4.0 GA이지만 컨슈머 기본값은 group.protocol=classic입니다.

운영 관점에서는 auto.create.topics.enable=true와 default.replication.factor=1의 조합이 위험 신호입니다. 오타로 만들어진 단일 레플리카 토픽이 조용히 생겨나기 때문입니다. 클러스터 구성 도메인에서 자주 다뤄집니다.

확인 문제

네 가지 문항 유형(단일 선택 · 복수 선택 · 연결형 · 순서 배열)이 섞여 있습니다. 실제 CCDAK/CCAAK 시험에도 matching과 list order 유형이 출제되므로 함께 연습하세요. 키보드만으로 완주할 수 있습니다 — 숫자키로 선택, Enter로 제출입니다.
