전달 보장과 트랜잭션

"Kafka는 exactly-once를 지원한다"는 문장은 맞지만, 그 문장만으로는 아무것도 설계할 수 없습니다. 중요한 것은 어디까지가 그 보장의 경계인가입니다. 이 장은 세 가지 전달 보장의 정확한 정의에서 출발해, 멱등 프로듀서와 트랜잭션이 각각 무엇을 해결하는지 구분하고, Kafka 내부에서는 EOS가 성립하지만 외부 DB·API 호출에는 성립하지 않는다는 경계를 확정합니다. 이 경계를 아는 것이 이 장의 실질적 가치입니다.

학습 목표

  • at-most-once · at-least-once · exactly-once를 정의하고, 각각을 만드는 설정 조합을 쓸 수 있습니다.
  • 중복이 어디서 생기고 유실이 어디서 생기는지 — 재시도와 커밋 순서로 나누어 설명할 수 있습니다.
  • 멱등 프로듀서(파티션 단위 중복 제거)와 트랜잭션(원자적 다중 파티션 쓰기)의 차이를 구분할 수 있습니다.
  • isolation.level=read_committed와 LSO의 관계, 그리고 그것이 만드는 지연을 설명할 수 있습니다.
  • EOS가 어디서 끝나는지 판단하고, 외부 시스템에 대한 멱등성을 직접 설계할 수 있습니다.

세 가지 전달 보장

공식 설계 문서는 세 가지를 다음과 같이 정의합니다.

전달 보장의 정의 (공식 설계 문서 · Message Delivery Semantics)
보장정의감당해야 하는 것
at-most-once 메시지가 유실될 수 있지만 재전달되지는 않습니다 데이터 누락
at-least-once 메시지가 유실되지 않지만 재전달될 수 있습니다 중복 처리
exactly-once 각 메시지가 정확히 한 번 처리됩니다 복잡도와 지연 — 그리고 경계 제약

공식 문서는 곧바로 중요한 단서를 붙입니다. "이것은 두 개의 문제로 갈라진다" — 메시지를 발행할 때의 내구성 보장과, 메시지를 소비할 때의 보장입니다. 그리고 exactly-once를 주장하는 많은 시스템에 대해 "작은 글씨를 읽어야 한다"고 경고합니다. 컨슈머나 프로듀서가 실패하는 경우, 컨슈머 프로세스가 여러 개인 경우, 디스크에 쓴 데이터가 유실될 수 있는 경우로 번역되지 않는 주장이 흔하다는 것입니다.

중복은 재시도에서, 유실은 커밋 순서에서

두 문제는 발생 지점이 다릅니다. 섞어서 생각하면 처방이 엉킵니다.

중복 — 프로듀서 쪽 재시도. 프로듀서가 메시지를 보낸 뒤 네트워크 오류를 만나면, 그 오류가 커밋 전에 발생한 것인지 커밋 후에 발생한 것인지 알 수 없습니다. 공식 문서는 이를 "자동 생성 키가 있는 데이터베이스 테이블에 insert하는 것과 비슷한 상황"으로 설명합니다. 재전송하면 중복이 생기고, 재전송하지 않으면 유실이 생깁니다. 0.11.0.0부터는 멱등 프로듀서가 이 딜레마를 해소합니다 — 브로커가 프로듀서마다 ID를 부여하고 시퀀스 번호로 중복을 제거합니다.

유실과 중복 — 컨슈머 쪽 커밋 순서. 공식 문서가 드는 두 가지 선택입니다.

  1. 읽고 → 위치를 저장하고 → 처리한다. 위치 저장 후 처리 결과 저장 전에 크래시하면, 인수한 프로세스가 저장된 위치부터 시작하므로 그 앞의 몇 건은 처리되지 않은 채 건너뛰어집니다. → at-most-once
  2. 읽고 → 처리하고 → 위치를 저장한다. 처리 후 위치 저장 전에 크래시하면, 인수한 프로세스가 이미 처리한 몇 건을 다시 받습니다. → at-least-once

공식 문서는 2번에 대해 "많은 경우 메시지에 기본 키가 있어 갱신이 멱등적이다" (같은 메시지를 두 번 받아도 같은 레코드를 덮어쓰는 것뿐)라고 덧붙입니다. 이것이 실무에서 at-least-once + 컨슈머 멱등성이 가장 널리 쓰이는 조합인 이유입니다.

공식 문서의 결론 문장입니다. "Kafka는 기본적으로 at-least-once 전달을 보장하며, 프로듀서의 재시도를 끄고 컨슈머가 배치 처리 전에 오프셋을 커밋하도록 하면 사용자가 at-most-once 전달을 구현할 수 있다." 즉 at-least-once가 기본이고, at-most-once는 의도적으로 만들어야 하는 상태입니다.

멱등 프로듀서와 트랜잭션은 다른 것입니다

둘 다 "중복을 막는다"고 설명되지만 해결하는 문제가 다릅니다. 멱등성은 재시도로 인한 중복을 없애고, 트랜잭션은 여러 쓰기를 원자적으로 묶습니다.

멱등성이 요구하는 것

공식 문서는 enable.idempotence=true가 세 가지를 요구한다고 명시합니다.

  • max.in.flight.requests.per.connection이 5 이하 — 이유가 명확합니다. 브로커가 프로듀서마다 최대 5개의 배치만 보관하기 때문입니다. 5를 넘으면 이전 배치가 브로커 쪽에서 제거되어 중복 판별을 할 수 없습니다.
  • retries가 0보다 커야 합니다.
  • acks가 all이어야 합니다.

충돌하는 설정이 있고 멱등성을 명시적으로 켜지 않았다면 멱등성이 비활성화됩니다. 명시적으로 켰는데 충돌 설정이 있으면 설정 오류가 됩니다 — 조용히 꺼지지 않습니다.

단골 문항입니다. max.in.flight.requests.per.connection의 상한이 5인 이유는 "성능 때문"이 아니라 브로커가 프로듀서당 최대 5개 배치만 보관하기 때문입니다. 그리고 이 값이 1이 아니라 5까지도 순서가 보장됩니다 — 멱등성이 켜져 있으면 시퀀스 번호로 브로커가 순서를 복원하기 때문입니다. "순서를 보장하려면 in-flight를 1로 낮춰야 한다"는 선택지는 3.0 이전 기준의 함정입니다. 자세한 프로듀서 쪽 서술은 4장에 있습니다.

공식 문서가 직접 경고하는 두 가지입니다.

  • 애플리케이션 레벨의 재전송은 중복 제거되지 않습니다. 멱등성은 클라이언트 내부의 재시도만 커버합니다. 애플리케이션이 send()를 두 번 호출하면 두 건이 기록됩니다.
  • 단일 세션 안에서만 멱등성이 보장됩니다. 프로세스가 재시작하면 새 PID를 받으므로, 재시작 전에 보낸 것과의 중복은 판별할 수 없습니다. 이 경계를 넘으려면 transactional.id가 필요합니다.

또한 공식 문서는 멱등성을 쓸 때 retries를 설정하지 말고 기본값 Integer.MAX_VALUE로 두라고 권고합니다. 무한 재시도에도 실패했다면 (예: 버퍼에서 만료) 프로듀서를 종료하고 마지막 메시지의 중복 여부를 확인하라고 합니다.

트랜잭션 — API와 코디네이터

공식 문서는 Kafka 트랜잭션이 다른 메시징 시스템의 트랜잭션과 다르다는 점을 먼저 짚습니다. Kafka에서는 컨슈머와 프로듀서가 분리되어 있고, 트랜잭션은 프로듀서만 갖습니다. 다만 프로듀서가 컨슈머의 위치(committed offset)를 트랜잭션 안에서 갱신할 수 있고, 바로 이것이 전체적인 exactly-once 동작을 만들어 냅니다.

transactional.id 의 역할

공식 문서의 정의입니다. transactional.id의 목적은 "단일 프로듀서 인스턴스의 여러 세션에 걸친 트랜잭션 복구를 가능하게 하는 것"입니다. 같은 transactional.id를 쓰는 트랜잭션이 새 트랜잭션 시작 전에 완료되었음을 보장하기 때문입니다. 재시작한 애플리케이션이 이전 인스턴스의 진행 중 트랜잭션을 중단(abort)시키는 효과도 여기서 나옵니다.

따라서 이 값은 파티션된 상태 저장 애플리케이션의 샤드 식별자에서 유도하는 것이 전형적이고, 애플리케이션 안에서 실행되는 프로듀서 인스턴스마다 유일해야 합니다.

여러 인스턴스가 같은 transactional.id를 쓰면 나중에 initTransactions()를 호출한 쪽이 앞의 것을 펜싱(fencing)합니다. 앞의 인스턴스는 다음 트랜잭션 작업에서 ProducerFencedException을 받고 복구할 수 없습니다 — 프로듀서를 닫고 종료하는 것이 유일한 선택입니다. 공식 문서 예시 코드가 ProducerFencedException을 복구 불가로 처리하는 이유입니다.

반대로 인스턴스마다 매번 랜덤한 ID를 주면 세션을 가로지르는 복구가 성립하지 않습니다. 재시작 후에도 같은 샤드에는 같은 ID가 오도록 결정적으로 만들어야 합니다.

트랜잭션 API (Apache Kafka 4.3 Producer 인터페이스)

sendOffsetsToTransaction(offsets, groupMetadata) consume-transform-produce에서 입력 오프셋을 트랜잭션에 포함 4.x에는 ConsumerGroupMetadata를 받는 시그니처만 있습니다

sendOffsetsToTransaction(Map, String consumerGroupId)는 제거되었습니다

Kafka 4.3의 Producer 인터페이스에는 sendOffsetsToTransaction(Map<TopicPartition, OffsetAndMetadata>, ConsumerGroupMetadata) 하나만 존재합니다. 그룹 ID 문자열을 받던 예전 오버로드는 없습니다. consumer.groupMetadata()를 넘겨야 합니다 — 그래야 브로커가 제너레이션까지 검증해 좀비 컨슈머의 오프셋 커밋을 차단할 수 있습니다. 예전 자료를 그대로 복사하면 컴파일되지 않습니다.

공식 문서는 "모든 트랜잭션 API는 블로킹이며 실패 시 예외를 던진다"고 명시하고, send()에 콜백을 지정하거나 Future.get()을 호출할 필요가 없다고 합니다. 트랜잭션 중에 복구 불가한 오류가 발생하면 KafkaException이 던져지기 때문입니다.

4.x의 표준화된 예외 분류

Apache Kafka 4.x에서 트랜잭션 프로듀서의 오류 처리가 표준화되었습니다. 공식 문서가 정의하는 여섯 개 범주입니다. 어느 것이 애플리케이션까지 올라오는지가 핵심입니다.

트랜잭션 프로듀서 예외 범주 (공식 문서 · Using Transactions)
범주 애플리케이션까지 올라오는가 필요한 조치
RetriableException아니요클라이언트가 자동 재시도합니다
RefreshRetriableException아니요클라이언트가 메타데이터를 갱신한 뒤 재시도합니다
AbortableException예트랜잭션을 abort하고 컨슈머 위치를 되돌려 재처리합니다
ApplicationRecoverableException예애플리케이션이 복구 전략을 구현해야 하며, 프로듀서 재시작을 포함해야 합니다
InvalidConfigurationException예설정 문제. 프로듀서 재시작은 필요하지 않습니다
KafkaException예위에 속하지 않는 일반 예외

공식 문서가 강조하는 지점입니다. 트랜잭션이 중단되면 애플리케이션의 상태, 특히 컨슈머의 현재 위치를 명시적으로 되돌려야 중단된 트랜잭션이 처리하던 레코드를 다시 처리할 수 있습니다. abortTransaction()만 호출하고 컨슈머를 그대로 두면 그 구간의 레코드가 유실됩니다 — 오프셋 커밋도 함께 롤백되었지만 컨슈머의 메모리상 위치는 앞으로 나가 있기 때문입니다. 공식 문서 표현으로는 "컨슈머가 자동으로 되감기지 않으므로 커밋된 오프셋을 다시 fetch해야 한다"입니다.

Transactions Server Side Defense (KIP-890) — Kafka 4.0

Apache Kafka 4.0부터 강화된 트랜잭션 프로토콜이 도입되었습니다. 활성화되고 4.0 이상 프로듀서를 쓰면 매 트랜잭션마다 프로듀서 에포크가 올라가 각 트랜잭션이 의도한 메시지만 포함하고 중복이 다음 트랜잭션에 섞여 들어가지 않도록 보장합니다.

서버 쪽은 4.0부터 자동 활성이며 transaction.version 피처 플래그로 제어합니다 (새 클러스터는 storage 도구로, 기존 클러스터는 features 도구로 transaction.version=2 설정). 프로듀서 클라이언트는 재시작할 필요가 없습니다 — 브로커에 재연결하는 시점에 동적으로 업그레이드되며, 트랜잭션 중간에는 전환하지 않고 다음 트랜잭션 시작 시점에 반영됩니다. 다운그레이드도 같은 방식으로 안전합니다.

consume-transform-produce 패턴

Kafka 토픽을 읽어 처리하고 다른 Kafka 토픽에 쓰는 파이프라인이 EOS가 성립하는 정확한 범위입니다. 공식 문서는 그 원리를 이렇게 설명합니다 — 컨슈머의 위치가 내부 토픽의 메시지로 저장되므로, 출력 토픽에 쓰는 것과 같은 트랜잭션 안에서 오프셋을 Kafka에 쓸 수 있습니다. 트랜잭션이 중단되면 컨슈머의 저장된 위치는 이전 값으로 되돌아가고, 출력 토픽에 쓰인 데이터는 read_committed 컨슈머에게 보이지 않습니다.

공식 문서가 드는 세 가지 요건

프로듀서와 컨슈머를 직접 써서 exactly-once 처리를 만들 때 필요한 것입니다.

  1. 컨슈머는 파티션 할당을 통해 자신이 그 파티션을 처리하는 그룹 내 유일한 컨슈머임을 보장받습니다.
  2. 프로듀서는 트랜잭션을 사용해 자신이 생산하는 모든 레코드와 컨슈머를 대신해 갱신하는 오프셋을 원자적으로 처리합니다.
  3. 리밸런싱과의 조합을 올바르게 다루기 위해, 컨슈머 인스턴스마다 프로듀서 인스턴스를 하나씩 쓰는 것이 권장됩니다. 더 복잡하고 효율적인 방식도 가능하지만 복잡도가 올라갑니다.

Kafka Streams — processing.guarantee

공식 문서는 "Kafka에서 exactly-once 의미론을 얻는 가장 간단한 방법은 Kafka Streams를 쓰는 것"이라고 명시합니다. 위의 루프를 직접 쓰는 대신 설정 하나로 같은 결과를 얻습니다.

processing.guarantee (Kafka Streams)
값상태요구사항

exactly_once_v2현행 EOS브로커 2.5 이상
exactly_oncedeprecated (EOS alpha)브로커 0.11.0 이상
exactly_once_betadeprecated (v2와 동일)브로커 2.5 이상

exactly_once_v2를 켜면 공식 문서 기준으로 다음이 자동으로 바뀝니다.

  • commit.interval.ms 기본값이 100ms로 변경됩니다.
  • 컨슈머에 isolation.level=read_committed가 설정됩니다.
  • 프로듀서에 enable.idempotence=true가 설정됩니다.

그리고 기본적으로 최소 3대의 브로커가 필요합니다. 개발용으로는 transaction.state.log.replication.factor와 transaction.state.log.min.isr를 브로커 수에 맞춰 낮춰야 합니다. Streams 상세는 10장에서 다룹니다.

processing.guarantee의 기본값은 at_least_once이고, 현행 EOS 값은 exactly_once_v2입니다. exactly_once와 exactly_once_beta는 deprecated입니다. 그리고 EOS를 켜면 commit.interval.ms가 100ms로 바뀐다는 점이 "EOS를 켰는데 처리량이 떨어졌다"는 시나리오 문항의 근거입니다.

isolation.level 과 LSO

isolation.level은 컨슈머 설정입니다. 프로듀서 설정이 아닙니다. 그리고 기본값은 read_uncommitted입니다. 즉 아무 설정도 하지 않은 컨슈머는 중단된(aborted) 트랜잭션의 메시지까지 봅니다. 프로듀서 쪽에서 트랜잭션을 완벽하게 구현해도, 컨슈머가 read_committed가 아니면 EOS는 성립하지 않습니다.

isolation.level의 두 값 (공식 문서 Consumer Configs)
값poll()이 반환하는 것읽기 상한
read_uncommitted 기본값 모든 메시지. 중단된 트랜잭션의 메시지도 포함됩니다 high watermark
read_committed 커밋된 트랜잭션 메시지와 비트랜잭션 메시지만 LSO (Last Stable Offset)

비트랜잭션 메시지는 두 모드 모두에서 무조건 반환됩니다. 그리고 메시지는 항상 오프셋 순서로 반환됩니다 — 이 두 사실이 다음 절의 근거입니다.

LSO — Last Stable Offset

공식 문서의 정의입니다. LSO는 "가장 처음 열려 있는 트랜잭션의 오프셋보다 1 작은 값"입니다. read_committed 모드의 poll()은 LSO까지만 반환합니다.

여기서 실무적으로 가장 중요한 결론이 나옵니다. 진행 중인 트랜잭션에 속한 메시지 뒤에 오는 메시지는, 그 자체가 이미 커밋되었더라도 해당 트랜잭션이 완료될 때까지 보류됩니다. 메시지가 오프셋 순서로만 반환되므로 중간을 뛰어넘을 수 없기 때문입니다. 그 결과 공식 문서 표현대로 "진행 중인 트랜잭션이 있으면 read_committed 컨슈머는 high watermark까지 읽을 수 없습니다."

트랜잭션이 오래 열려 있으면 LSO가 앞으로 나가지 못하고 그 파티션을 읽는 모든 read_committed 컨슈머의 lag이 늘어납니다. 단 하나의 느린 트랜잭션 프로듀서가 파티션 전체의 가시성을 붙잡습니다. 처방은 두 방향입니다.

  • 트랜잭션을 짧게 유지합니다. 한 트랜잭션에 담는 레코드 수를 제한하세요.
  • transaction.timeout.ms(기본 60000)를 요구 지연에 맞춰 조정합니다. 브로커의 transaction.max.timeout.ms(기본 900000)가 상한입니다. 공식 문서는 이 브로커 설정의 목적이 "클라이언트가 지나치게 큰 타임아웃을 잡아 트랜잭션에 포함된 토픽을 읽는 컨슈머를 정지시키는 것을 막는 것"이라고 밝힙니다.

컨트롤 레코드와 seekToEnd

트랜잭션이 커밋 또는 중단되면 트랜잭션 마커 레코드가 각 파티션에 기록됩니다. read_committed 컨슈머는 이 마커를 보고 중단된 트랜잭션의 레코드를 걸러 냅니다. 이 마커는 애플리케이션에 반환되지 않습니다 — 하지만 오프셋 공간은 차지합니다.

트랜잭션 토픽에서 컨슈머가 받는 레코드의 오프셋이 연속하지 않을 수 있습니다. 컨트롤 레코드가 오프셋을 소비하고, 중단된 트랜잭션의 레코드도 오프셋을 이미 차지했기 때문입니다. "오프셋이 5, 6, 9로 건너뛰었으니 메시지가 유실됐다"는 판단은 틀립니다. lag 계산 시 LOG-END-OFFSET − CURRENT-OFFSET이 실제 미처리 건수보다 크게 나오는 원인도 이것입니다.

공식 문서가 명시하는 또 하나의 차이입니다. read_committed 모드에서 seekToEnd()는 high watermark가 아니라 LSO를 반환합니다. "끝으로 이동"의 의미가 모드에 따라 달라집니다.

isolation.level 관련 출제 포인트를 정리하면 다음과 같습니다.

  • 컨슈머 설정입니다. 기본값은 read_uncommitted입니다.
  • read_committed는 LSO까지만 읽습니다. LSO = 가장 처음 열린 트랜잭션의 오프셋 − 1.
  • 진행 중 트랜잭션이 있으면 그 뒤의 커밋된 메시지도 보이지 않습니다 → 지연 증가.
  • 비트랜잭션 메시지는 두 모드 모두에서 무조건 반환됩니다.
  • 컨트롤 레코드는 애플리케이션에 노출되지 않지만 오프셋을 차지합니다.
  • read_committed에서 seekToEnd()는 LSO를 반환합니다.

EOS의 경계 — 이 장에서 가장 중요한 절

여기까지의 모든 장치는 Kafka 토픽을 읽어 Kafka 토픽에 쓰는 경계 안에서만 성립합니다. 공식 문서의 결론 문장을 그대로 인용하면 이렇습니다.

"Kafka는 Kafka Streams에서 exactly-once 전달을 지원하며, 트랜잭션 프로듀서와 read-committed 격리 수준을 쓰는 컨슈머는 Kafka 토픽에서 데이터를 읽고 처리하고 쓸 때 exactly-once 전달을 제공하는 데 일반적으로 사용할 수 있습니다. 다른 목적지 시스템에 대한 exactly-once 전달은 일반적으로 그 시스템과의 협력이 필요합니다."

왜 외부 시스템에는 성립하지 않는가

공식 문서가 설명하는 이유는 명확합니다. 외부 시스템에 쓸 때의 제약은 "컨슈머의 위치와 실제로 저장된 출력을 조율해야 하는 필요"에 있습니다. 고전적 해법은 컨슈머 위치 저장과 출력 저장 사이의 2단계 커밋(two-phase commit)인데, 공식 문서는 "컨슈머가 쓰려는 많은 출력 시스템이 2단계 커밋을 지원하지 않는다"고 지적합니다.

결국 Kafka 트랜잭션은 Kafka 안의 파티션들과 __consumer_offsets에 대해서만 원자성을 만듭니다. HTTP 요청 하나, SQL INSERT 하나는 그 원자성 안에 들어갈 방법이 없습니다. 트랜잭션이 abort되어 Kafka 쪽이 전부 되돌아가도 이미 나간 HTTP 요청은 되돌아오지 않습니다.

EOS가 성립하는 범위와 성립하지 않는 범위
시나리오EOS필요한 조치
Kafka 토픽 → 처리 → Kafka 토픽 성립 트랜잭션 프로듀서 + sendOffsetsToTransaction + read_committed. 또는 Kafka Streams exactly_once_v2
Kafka 토픽 → 처리 → 외부 RDBMS 성립하지 않음 DB 쪽 멱등 upsert(유니크 키) 또는 오프셋을 DB에 함께 저장해 트랜잭션으로 묶기
Kafka 토픽 → 처리 → 외부 HTTP/결제 API 성립하지 않음 API의 idempotency key 지원에 의존. 없으면 처리 이력 테이블로 직접 중복 차단

그래서 컨슈머 멱등성을 직접 만듭니다

공식 문서가 제시하는 일반적 해법은 "컨슈머가 자신의 오프셋을 출력과 같은 곳에 저장하게 하는 것"입니다. 2단계 커밋보다 단순하고 범용적이기 때문입니다. 실무에서는 다음 세 가지 형태로 나타납니다.

외부 시스템에 대한 멱등성 구현 패턴
패턴방법쓰는 곳
① 멱등 upsert 메시지의 비즈니스 키를 유니크 제약으로 걸고 UPSERT/MERGE로 씁니다. 같은 메시지를 두 번 받아도 결과가 같습니다 상태 갱신형(재고, 프로필, 잔액). 공식 문서가 언급하는 "기본 키가 있어 갱신이 멱등적인" 경우
② 오프셋 동거 처리 결과와 오프셋을 같은 DB 트랜잭션에 저장합니다. 컨슈머는 assign() + seek()로 DB의 오프셋에서 시작합니다 진짜 EOS가 필요하고 DB 트랜잭션을 쓸 수 있는 경우. Kafka에 오프셋을 커밋하지 않습니다
③ 처리 이력 테이블 (topic, partition, offset) 또는 메시지 ID를 유니크 키로 기록하고, 이미 있으면 건너뜁니다. 이력 기록과 부수효과를 한 트랜잭션에 묶습니다 부수효과가 멱등적이지 않은 경우(발송, 외부 API 호출)

가장 자주 나오는 시나리오 문항입니다. "트랜잭션 프로듀서와 read_committed 컨슈머로 EOS를 구성했는데, 컨슈머가 처리 중 호출하는 외부 결제 API에서 중복 결제가 발생했다. 원인은?"

답은 설정 문제가 아니라 EOS의 범위 문제입니다. Kafka 트랜잭션은 Kafka 토픽과 __consumer_offsets에 대해서만 원자적입니다. 외부 API 호출은 트랜잭션에 포함되지 않으므로, 트랜잭션이 abort되고 재처리되면 API는 두 번 호출됩니다. 해결은 애플리케이션 레벨의 멱등성(idempotency key, 처리 이력 테이블)입니다. "isolation.level을 바꾼다", "transactional.id를 바꾼다" 같은 선택지는 모두 오답입니다.

흔한 오해

"EOS를 켜면 DB 중복도 막힌다" — 이 장에서 가장 중요한 오해입니다. Kafka의 exactly-once는 Kafka 토픽을 읽고 Kafka 토픽에 쓰는 경계 안에서만 성립합니다. 외부 데이터베이스나 결제 API를 호출하는 순간 그 보장은 끝납니다. 공식 문서 표현대로 "다른 목적지 시스템에 대한 exactly-once는 그 시스템과의 협력이 필요"합니다. 컨슈머 쪽 멱등성은 EOS를 켜도 여전히 필요합니다. 이 착각이 만드는 장애는 케이스 7에서 다룹니다.

"프로듀서에 isolation.level=read_committed를 넣어야 한다" — isolation.level은 컨슈머 설정입니다. 프로듀서에 넣으면 아무 효과도 없이 무시됩니다. 그리고 기본값이 read_uncommitted라는 점이 함정입니다 — 프로듀서 쪽에서 트랜잭션을 완벽하게 구현해도 컨슈머가 기본 설정이면 중단된 트랜잭션의 메시지까지 읽습니다. EOS는 프로듀서와 컨슈머 양쪽 설정이 맞아야 성립합니다.

"멱등 프로듀서를 켜면 애플리케이션이 같은 메시지를 두 번 보내도 한 번만 기록된다" — 아닙니다. 멱등성은 클라이언트 내부 재시도로 인한 중복만 제거합니다. 공식 문서가 직접 경고합니다 — "애플리케이션 레벨의 재전송은 중복 제거될 수 없으므로 반드시 피해야 한다." 그리고 멱등성은 단일 프로듀서 세션 안에서만 유효합니다. 프로세스가 재시작하면 새 PID를 받으므로 재시작 전에 보낸 것과의 중복은 판별할 수 없습니다 — 이 경계를 넘으려면 transactional.id가 필요합니다.

"read_committed로 바꿨는데 lag이 늘었다. 버그다" — 정상 동작입니다. read_committed 컨슈머는 LSO까지만 읽습니다. 진행 중인 트랜잭션이 하나라도 있으면 그 뒤의 커밋된 메시지까지 보류되므로 high watermark 기준으로 계산한 lag이 커집니다. 그리고 컨트롤 레코드가 오프셋을 차지하기 때문에 lag 숫자가 실제 미처리 건수보다 큽니다. 처방은 트랜잭션을 짧게 유지하는 것입니다.

시험 포인트 요약

6장 범위의 출제 지점을 한 곳에 모았습니다.

  • Kafka의 기본 동작은 at-least-once입니다. at-most-once는 재시도를 끄고 처리 전에 커밋해서 의도적으로 만듭니다.
  • 중복은 프로듀서 재시도에서, 유실/중복은 컨슈머 커밋 순서에서 나옵니다.
  • 멱등 프로듀서 = 파티션 단위 · 단일 세션 내 중복 제거. 트랜잭션 = 다중 파티션 원자적 쓰기 + 오프셋 포함 + 세션 경계 넘기.
  • enable.idempotence=true는 max.in.flight.requests.per.connection ≤ 5, retries > 0, acks=all을 요구합니다. 5인 이유는 브로커가 프로듀서당 5개 배치만 보관하기 때문입니다.
  • transactional.id는 프로듀서 설정입니다. 설정하면 멱등성이 자동 활성됩니다. 인스턴스마다 유일해야 하고, 중복 시 ProducerFencedException(복구 불가).
  • EOS 컨슈머 요구 설정: isolation.level=read_committed + enable.auto.commit=false.
  • isolation.level은 컨슈머 설정, 기본값은 read_uncommitted. read_committed는 LSO까지만 읽습니다.
  • API 순서: initTransactions(한 번) → beginTransaction → send/sendOffsetsToTransaction → commitTransaction/abortTransaction.
  • 4.x의 sendOffsetsToTransaction은 ConsumerGroupMetadata를 받는 시그니처만 존재합니다.
  • abort 후에는 컨슈머 위치를 직접 되돌려야 재처리됩니다. 자동으로 되감기지 않습니다.
  • EOS는 Kafka 내부에서만 성립합니다. 외부 시스템에는 컨슈머 멱등성이 필요합니다.

내부 토픽과 브로커 요구사항이 Fundamentals 쪽에서 나옵니다.

  • 트랜잭션 상태는 __transaction_state에, 오프셋은 __consumer_offsets에 저장됩니다.
  • transaction.state.log.replication.factor 기본 3, transaction.state.log.min.isr 기본 2. 브로커가 3대 미만이면 내부 토픽 생성이 실패합니다 — 단일 노드 개발 환경에서 트랜잭션이 안 되는 이유입니다.
  • transaction.timeout.ms(프로듀서) 기본 60000, transaction.max.timeout.ms(브로커) 기본 900000. 초과 요청은 InvalidTxnTimeoutException.
  • 컨트롤 레코드는 애플리케이션에 노출되지 않지만 오프셋을 차지합니다.

processing.guarantee의 기본값은 at_least_once, 현행 EOS 값은 exactly_once_v2(브로커 2.5+), exactly_once·exactly_once_beta는 deprecated입니다. EOS를 켜면 commit.interval.ms가 100ms로 바뀌고, 컨슈머에 read_committed, 프로듀서에 enable.idempotence=true가 자동 설정됩니다.
