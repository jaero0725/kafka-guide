버전 표기와 레거시

이 가이드의 본문은 Apache Kafka 4.3.x를 기준으로 씌어 있습니다. 하지만 현실의 많은 조직이 아직 2.x나 3.x를 운영하고 있고, 그 시절 자료를 읽다가 kafka_2.13을 Kafka 버전으로 착각하는 일이 매우 흔합니다. 이 페이지는 그 두 가지 — 버전 표기 읽는 법과 레거시 환경에서 4.x로 오는 길 — 을 다룹니다.

이 페이지는 ZooKeeper 기반 운영을 서술하는 유일한 페이지입니다. 다른 장에서 ZooKeeper가 등장하면 "3.x 이전에는 …였다"는 역사적 맥락뿐입니다.

학습 목표

  • kafka_2.13-4.3.1.tgz를 읽고 2.13이 Scala 버전임을 설명할 수 있습니다.
  • 2.0부터 4.3까지 어느 버전에서 무엇이 바뀌었는지 타임라인으로 짚을 수 있습니다.
  • ZooKeeper 시대에 무엇이 어디에 저장됐고 어떤 장애가 잦았는지 설명할 수 있습니다.
  • 2.x → 3.9 → 4.x 경로가 왜 필요한지, 각 단계에서 무엇을 확인해야 하는지 말할 수 있습니다.
  • 옛 명령·설정을 보고 현행 대응물을 찾을 수 있습니다.

버전 표기 읽는 법

Apache 아카이브의 4.3.1 디렉터리에는 배포 파일이 하나만 올라와 있습니다. kafka_2.13-4.3.1.tgz입니다. 이 한 줄에 버전 번호가 두 개 들어 있어서 오해가 끊이지 않습니다.

_2.13은 이 배포판이 컴파일된 Scala 버전입니다. Kafka 버전은 뒤쪽의 4.3.1입니다. Kafka 2.13이라는 버전은 존재하지 않습니다 — Kafka는 2.8 다음이 3.0입니다.

Scala를 직접 쓰지 않는다면 고민할 것 없이 _2.13을 고르면 됩니다. 현행 Kafka는 Scala 2.13용 배포판만 제공하며, 브로커는 JVM 바이너리로 동작하므로 Java만 있으면 됩니다. Scala 버전은 Java 클라이언트 API와 무관합니다.

Kafka 브로커의 상당 부분이 Scala로 작성되어 있고, Scala는 메이저·마이너 버전 간 바이너리 호환이 보장되지 않습니다. 그래서 같은 Kafka 버전이라도 Scala 버전별로 별도 빌드를 배포해 왔습니다.

이것이 문제가 되는 경우는 하나뿐입니다 — Scala로 작성한 애플리케이션이 Kafka의 Scala 라이브러리를 직접 참조하는 경우입니다. Java 클라이언트(kafka-clients)를 쓰는 대부분의 애플리케이션은 Scala 접두어가 없는 아티팩트를 쓰므로 영향이 없습니다.

참고로 kafka-streams-scala 라이브러리는 Kafka 4.3에서 deprecated되었고 5.0에서 제거될 예정입니다. Scala DSL을 쓰고 있다면 마이그레이션 계획이 필요합니다.

이 내용은 문제은행과 실제 시험 양쪽에서 직접 출제되는 지점입니다. 출제 형태는 대략 셋입니다.

  • "kafka_2.13-4.3.1.tgz에서 2.13은 무엇인가?" → Scala 버전입니다. Kafka 마이너 버전·프로토콜 버전·Java 버전은 모두 오답 선택지입니다.
  • "Kafka 2.8 다음 릴리스는?" → 3.0입니다. 2.9 · 2.13 같은 버전은 존재하지 않습니다.
  • "Java 애플리케이션에서 Kafka를 쓰려면 어떤 아티팩트가 필요한가?" → kafka-clients이며 Scala 접두어가 붙지 않습니다. Scala 접두어가 필요한 것은 kafka-streams-scala_2.13처럼 Scala API를 쓰는 경우뿐입니다.

Kafka 2.x / 3.x를 아직 쓰는 조직을 위한 안내

아래는 Kafka 3.9 이하에서만 유효한 서술입니다. 4.0부터 ZooKeeper 모드가 제거되었으므로, 4.x에서는 아래 내용 중 어느 것도 적용되지 않습니다. 현행 아키텍처는 3장 KRaft와 클러스터 메타데이터를 보세요.

ZooKeeper 앙상블 구성

ZooKeeper는 과반수 기반 합의를 쓰므로 앙상블 크기를 홀수로 두는 것이 관례였습니다. 3대면 1대 장애, 5대면 2대 장애를 견딥니다. 운영 관점의 핵심은 Kafka 브로커와 ZooKeeper 노드를 같은 머신에 두지 않는 것과 ZooKeeper의 트랜잭션 로그를 별도 디스크에 두는 것이었습니다 — ZooKeeper는 쓰기마다 fsync를 하므로 디스크 지연에 매우 민감했습니다.

이 "두 개의 분산 시스템을 함께 운영해야 한다"는 부담이 KIP-500(ZooKeeper 제거)의 출발점이었습니다. Kafka를 운영하려면 Kafka와 ZooKeeper 양쪽의 튜닝·모니터링·보안·업그레이드를 모두 알아야 했습니다.

--zookeeper CLI의 시대

2.x 자료를 보면 아래와 같은 명령이 흔히 나옵니다. 이 명령들은 현행 Kafka에서 동작하지 않습니다. 관리 도구의 --zookeeper 플래그는 KIP-555로 deprecated되고 Kafka 3.0에서 제거되었습니다(KIP-604).

Kafka 2.x 시절 — ZooKeeper에 직접 접속해 메타데이터를 고쳤습니다. 클라이언트가 브로커를 거치지 않으므로 ACL·인증을 우회하는 문제도 있었습니다.

Kafka 4.x — 모든 관리 요청이 브로커(또는 컨트롤러)를 거칩니다. 인증·인가가 일관되게 적용되고, 클라이언트가 알아야 할 엔드포인트가 하나로 줄었습니다.

4.0에서는 남아 있던 ZooKeeper 흔적까지 정리되었습니다 — kafka-acls의 --authorizer·--authorizer-properties·--zk-tls-config-file 옵션이 제거되고 --bootstrap-server 또는 --bootstrap-controller를 쓰게 되었으며, kafka.admin.ZkSecurityMigrator 도구도 제거되었습니다. 또한 KRaft 모드용 설정 파일이 별도의 config/kraft 디렉터리에 있던 관행도 끝나 모든 설정 파일이 config 디렉터리로 통합되었습니다.

어떤 장애가 잦았는지는 Kafka가 그 시절 어떤 메트릭을 노출했는지를 보면 드러납니다. 아래 메트릭들은 모두 4.x에서 제거되었지만, 그 이름이 곧 당시의 걱정거리 목록입니다.

ZooKeeper 시대의 장애 유형과 그것을 감시했던 메트릭 (모두 4.x에서 제거됨)
장애무슨 일이 일어나는가당시의 메트릭
ZooKeeper 세션 만료 GC 정지, 네트워크 순단, ZooKeeper 과부하로 브로커의 ZooKeeper 세션이 만료됩니다. 브로커는 살아 있는데 클러스터에서 이탈한 것으로 처리되어 리더 선출과 ISR 축소가 연쇄로 일어납니다. zookeeper.session.timeout.ms가 너무 짧으면 이 현상이 잦아졌습니다 SessionExpireListener.ZooKeeperExpiresPerSec, SessionExpireListener.SessionState
ZooKeeper 연결 끊김 세션 만료까지 가지 않아도 재연결이 반복되면 메타데이터 갱신이 지연되고 컨트롤러 동작이 불안정해졌습니다 SessionExpireListener.ZooKeeperDisconnectsPerSec, SessionExpireListener.ZooKeeperSyncConnectsPerSec
ZooKeeper 디스크 압박 ZooKeeper는 쓰기마다 트랜잭션 로그를 디스크에 sync합니다. 스냅샷·로그 정리(autopurge)가 안 되어 디스크가 차거나 디스크가 느리면 ZooKeeper 응답 지연 → 브로커 세션 위험으로 이어졌습니다 ZooKeeperClientMetrics.ZooKeeperRequestLatencyMs
인증 실패 ZooKeeper에 SASL 인증을 켠 환경에서 자격증명 문제로 브로커가 ZooKeeper에 붙지 못했습니다 SessionExpireListener.ZooKeeperAuthFailuresPerSec
컨트롤러 이슈 · split-brain 우려 컨트롤러 페일오버 시 메타데이터 전체를 ZooKeeper에서 다시 읽어야 했으므로 파티션이 많은 클러스터에서 페일오버가 오래 걸렸고, 그 사이 파티션이 오프라인으로 남았습니다. 옛 컨트롤러가 자신이 여전히 컨트롤러라고 믿는 상황(zombie controller)을 컨트롤러 epoch로 걸러 내야 했습니다 ControllerStats.ControllerChangeRateAndTimeMs, ControllerStats.ControllerShutdownRateAndTimeMs, KafkaController.ControllerState
마이그레이션 상태 추적 ZooKeeper → KRaft 마이그레이션 중에는 브로커가 어느 단계에 있는지 확인해야 했습니다 KafkaController.ZkMigrationState, KafkaController.MigratingZkBrokerCount

시험은 4.x 기준으로 출제되므로, 위 내용은 "KRaft가 무엇을 개선했는가"를 설명하는 근거로 쓰입니다. 출제 형태로 정리하면:

  • KRaft 도입 이유 3가지 — 이중 운영 부담 / 메타데이터 확장 한계 / 컨트롤러 페일오버 지연
  • 브로커 생존 판정: ZooKeeper 시대는 ZooKeeper 세션, KRaft는 컨트롤러 하트비트
  • ACL 저장 위치: ZooKeeper znode → 클러스터 메타데이터 로그
  • inter.broker.protocol.version → metadata.version (kafka-features.sh로 관리)
  • --zookeeper 옵션은 존재하지 않습니다. 모든 명령은 --bootstrap-server(또는 컨트롤러 대상이면 --bootstrap-controller)입니다

업그레이드 경로 — 2.x → 3.9 → 4.x

왜 3.9를 경유해야 하는가

4.3 업그레이드 문서의 서술을 정리하면 이유가 세 겹입니다.

  1. 4.x는 KRaft만 지원합니다. 문서는 "ZooKeeper 모드 클러스터는 4.3.x로 업그레이드하기 전에 반드시 KRaft로 마이그레이션되어야 한다"고 명시합니다. 그리고 ZooKeeper → KRaft 마이그레이션 기능이 있는 마지막 버전이 3.9입니다. 4.0 이후에는 마이그레이션 경로 자체가 없습니다.
  2. 4.x 브로커 업그레이드는 소프트웨어·메타데이터 버전이 최소 3.3.x여야 합니다. 문서는 이를 "KRaft 모드가 production ready로 판정된 첫 버전"이라는 이유로 설명합니다. 3.3.x보다 오래된 KRaft 클러스터에는 3.9.x로 먼저 올리는 것을 권장합니다.
  3. 클라이언트는 4.0 이전에 2.1 이상이어야 합니다. 4.0에서 오래된 프로토콜 API 버전이 제거되었기 때문입니다(KIP-896). Connect와 Kafka Streams도 내부적으로 클라이언트를 쓰므로 함께 해당됩니다.

ZooKeeper 모드에서 곧바로 4.x 바이너리로 브로커를 교체하면 기동되지 않습니다. 그리고 4.3은 클러스터 메타데이터 다운그레이드를 지원하지 않습니다 — IPB_4_3_IV0에 메타데이터 변경이 포함되어 있기 때문입니다. 업그레이드 확정(kafka-features.sh upgrade --release-version 4.3)은 되돌릴 수 없는 단계이므로, 그 전에 클러스터 동작과 성능을 충분히 검증해야 합니다.

참고로 4.2는 메타데이터 변경이 없어(IBP_4_2_IV1) 다운그레이드가 가능했습니다. 버전마다 다르므로 반드시 해당 버전의 업그레이드 문서를 확인하세요.

단계별 절차

레거시 클러스터를 4.3으로 올리는 큰 흐름
단계무엇을 하는가확인 사항
① 클라이언트 정비 모든 프로듀서·컨슈머·Connect·Streams 클라이언트를 최소 2.1 이상으로 올립니다. 가능하면 더 최신으로 4.0에서 제거된 API를 쓰고 있지 않은지. Apache Kafka 외부의 서드파티 클라이언트도 KIP-896을 확인해야 합니다
② 3.9로 롤링 업그레이드 (ZooKeeper 모드 유지) 브로커를 하나씩 3.9로 교체합니다. 아직 ZooKeeper 모드입니다 ZooKeeper 모드에서는 inter.broker.protocol.version을 단계적으로 상향합니다 — 먼저 모든 브로커의 바이너리를 교체하고, 전부 정상 동작을 확인한 뒤 이 값을 올려 다시 롤링합니다
③ ZooKeeper → KRaft 마이그레이션 (3.9에서) KRaft 컨트롤러 쿼럼을 구성하고 브로커를 마이그레이션 모드로 전환한 뒤, 메타데이터를 KRaft로 옮기고 ZooKeeper 의존을 끊습니다 3.9의 공식 마이그레이션 문서를 그대로 따르세요. 컨트롤러 수는 3 또는 5(3장). KafkaController.ZkMigrationState 메트릭으로 진행을 확인합니다
④ 4.x로 롤링 업그레이드 브로커를 하나씩 정지 → 코드 교체 → 재시작합니다. 이 시점에는 이미 KRaft 모드입니다 UnderReplicatedPartitions가 0으로 돌아온 뒤 다음 브로커로 넘어가세요(11장)
⑤ 업그레이드 확정 bin/kafka-features.sh --bootstrap-server localhost:9092 upgrade --release-version 4.3 되돌릴 수 없습니다. 클러스터 동작·성능을 먼저 충분히 검증하세요
⑥ 설정·기본값 정리 제거된 ZooKeeper 관련 설정을 지우고, 바뀐 기본값이 의도와 맞는지 확인합니다 linger.ms 5, acks all, enable.idempotence true, num.recovery.threads.per.data.dir 2, message.timestamp.after.max.ms 1시간, segment.bytes 최소 1MB
⑦ 신기능 선택 적용 KIP-848 컨슈머 프로토콜, Share Groups, Streams Rebalance Protocol을 필요에 따라 켭니다 모두 클라이언트 쪽 기본값이 아닙니다. group.protocol=consumer(5장), share.version=1·group.protocol=streams(11장·10장)
  • 한 번에 한 대씩. 다음 브로커로 넘어가기 전에 UnderReplicatedPartitions가 0으로 돌아오고 ISR이 복구됐는지 확인하세요.
  • min.insync.replicas와 브로커 수의 관계를 먼저 계산하세요. RF=3, min.insync.replicas=2에서 브로커 한 대를 내리면 여유가 0입니다 — 그 사이 다른 브로커에 문제가 생기면 acks=all 쓰기가 거부됩니다.
  • Connect 워커의 scheduled.rebalance.max.delay.ms(기본 5분)를 고려하세요. 워커를 내리고 5분 안에 복귀하지 않으면 태스크가 재배치되고, 그 사이 태스크는 미배정 상태입니다(9장).
  • 컨슈머 그룹 리밸런스를 줄이려면 static membership(group.instance.id)이나 KIP-848 프로토콜을 검토하세요(5장).
  • Kafka Streams는 별도로 확인하세요. 4.0에서 3.6 이전에 deprecated된 public API가 대량 제거되었습니다. Streams 업그레이드 가이드를 따로 읽어야 합니다.
  • 4.1.0의 Streams 메모리 누수(KAFKA-19748)가 range scan과 일부 DSL 연산자 (session window, sliding window, stream-stream join, foreign-key join)에 영향을 주었습니다. 공식 문서는 4.1.1로 직행할 것을 권고합니다.

업그레이드 경로에서 출제되는 숫자는 네 개입니다. 이것만 정확히 외우면 됩니다.

자주 나오는 함정: "ZooKeeper 클러스터를 4.x로 바로 업그레이드한 뒤 KRaft로 마이그레이션한다"는 선택지입니다. 순서가 반대입니다 — KRaft 마이그레이션을 3.9에서 먼저 끝낸 뒤 4.x로 올립니다. 그리고 클라이언트는 4.0 이전에 2.1 이상이어야 합니다(KIP-896).

문제문에 버전이 명시되어 있는지 먼저 확인하세요. "acks의 기본값은?"처럼 버전이 없으면 최신(4.x) 기준으로 답합니다.

  • linger.ms는 5입니다. 시중 자료가 대부분 0으로 적혀 있어 가장 많이 틀립니다.
  • group.protocol은 classic입니다. KIP-848이 4.0 GA인 것과 기본값인 것은 다릅니다.
  • processing.guarantee는 at_least_once이고 EOS 값 이름은 exactly_once_v2입니다.
  • isolation.level은 read_uncommitted입니다.
  • Share Groups는 4.2 GA(4.1은 preview)입니다.
  • KRaft production-ready는 3.3, ZooKeeper 마지막 지원은 3.9, 제거는 4.0입니다.
  • 2.13은 Scala 버전입니다. Kafka 2.13은 존재하지 않습니다.
