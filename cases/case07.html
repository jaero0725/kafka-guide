실수 케이스 · 7

재처리했더니 결제가 두 번 됐다

누락된 4시간분을 복구하려고 오프셋을 되돌렸습니다. 결과는 이중 청구 3,180건이었습니다. 팀은 "우리는 exactly-once를 켰는데요"라고 했습니다. 맞습니다 — 켰습니다. 다만 EOS의 경계는 Kafka 토픽까지이고, 외부 결제 API는 그 밖에 있었습니다.

이 케이스에서 얻어 갈 것

  • Kafka EOS가 성립하는 정확한 경계를 한 문장으로 말할 수 있습니다.
  • Kafka의 기본 전달 보장이 at-least-once이며, 그것이 무엇을 요구하는지 압니다.
  • 멱등 프로듀서 · 트랜잭션 · 컨슈머 멱등성의 역할이 서로 다르다는 것을 구분할 수 있습니다.
  • 외부 시스템에 대한 멱등성을 실제로 구현하는 세 가지 패턴을 압니다.

상황

결제 확정 파이프라인입니다. payment-approved 토픽은 파티션 12개, 복제 계수 3, 브로커 3대에서 일 40만 건을 받습니다. 컨슈머는 이벤트를 받아 PG사 결제 확정 API를 호출하고, 응답을 payment-settled 토픽에 발행합니다.

아키텍처는 Kafka Streams 기반이고 processing.guarantee=exactly_once_v2가 설정되어 있었습니다. 팀은 이 설정 덕분에 "중복 걱정은 없다"고 이해하고 있었습니다.

금요일 04:00~08:00 사이 업스트림 장애로 payment-approved 소비가 멈췄고, 복구 과정에서 오프셋이 잘못 전진해 68,000건이 처리되지 않은 채 건너뛰어졌습니다 (케이스 1과 같은 유형).

11:00, 팀은 누락을 복구하기로 결정했습니다. --reset-offsets --to-datetime 2026-07-24T04:00:00.000 --execute로 4시간분을 되돌렸습니다. 그런데 그 4시간 안에는 이미 정상 처리된 3,180건도 포함되어 있었습니다. 재처리가 시작되자 PG사 결제 확정 API가 그 3,180건에 대해 두 번째로 호출됐습니다.

13:40에 PG사에서 "동일 주문 중복 승인 요청" 알림을 받았습니다. 환불 처리와 고객 안내에 4일이 걸렸습니다.

Kafka의 exactly-once는 "Kafka 토픽을 읽고 처리해 Kafka 토픽에 쓰는" 경계 안에서만 성립합니다. 공식 설계 문서의 표현을 그대로 옮기면, "다른 목적지 시스템에 대한 exactly-once 전달은 일반적으로 그 시스템과의 협력이 필요하다"이며 "그렇지 않으면 Kafka는 기본적으로 at-least-once 전달을 보장한다"입니다.

pgClient.confirmPayment()는 Kafka 트랜잭션의 원자성 범위 밖입니다. 트랜잭션이 abort 되더라도 이미 나간 HTTP 요청은 취소되지 않습니다.

관측된 증상

메트릭이 어떻게 보였는가

  • Kafka 지표 전부 정상. lag이 68,000에서 0으로 정상 감소, 에러율 0, 리밸런스 없음.
  • payment-settled 토픽 유입: 재처리 구간에서 정상보다 높음. 이것이 유일한 Kafka 쪽 단서였습니다.
  • PG API 호출 수: 11:00~11:40 사이 평소의 4.2배.
  • PG사 중복 승인 알림: 3,180건. 이것이 사고 인지 경로였습니다.

이 케이스에서 Kafka는 완벽하게 정상 동작했습니다. exactly_once_v2도 정상 동작했습니다 — payment-settled 토픽에는 중복이 없고, 오프셋 커밋도 원자적으로 처리됐습니다.

중복이 생긴 곳은 Kafka가 관여하지 않는 HTTP 호출이었습니다. 그래서 브로커 로그·클라이언트 로그·JMX 어디에도 단서가 없습니다. 이 사고는 외부 시스템 쪽 지표로만 감지됩니다.

출력 토픽에서 본 증거

payment-settled에는 트랜잭션 덕분에 중복 레코드가 없지만, PG 승인 번호가 다른 두 개의 레코드가 같은 주문에 대해 존재했습니다. 같은 주문을 두 번 승인받았다는 뜻입니다.

isolation.level의 기본값은 read_uncommitted입니다. 이 기본값에서는 abort 된 트랜잭션의 레코드까지 컨슈머에게 보입니다. 트랜잭션을 쓰는 파이프라인을 조사할 때는 CLI에도 --isolation-level read_committed를 반드시 붙이세요. 그러지 않으면 "중복이 있다"는 잘못된 결론에 도달합니다.

원인 분석

1단계 — 세 가지 전달 보장을 정확히 구분한다

전달 보장 세 가지와 그것을 만드는 설정 조합
보장 정의 만드는 방법
at-most-once 메시지가 유실될 수 있지만 재전달되지 않음 프로듀서 재시도를 끄고, 컨슈머는 처리 전에 오프셋을 커밋
at-least-once
Kafka 기본		 메시지가 유실되지 않지만 재전달될 수 있음 컨슈머가 처리 후에 오프셋을 커밋. 별도 설정이 필요 없는 기본 동작
exactly-once 각 메시지가 정확히 한 번 처리됨 Kafka 토픽 → Kafka 토픽 경계에서 트랜잭션 사용. 외부 시스템은 별도 협력 필요

공식 설계 문서는 "Kafka는 기본적으로 at-least-once 전달을 보장한다"고 명시합니다. 그리고 컨슈머의 두 가지 선택을 이렇게 설명합니다.

  1. 읽고 → 위치를 저장하고 → 처리한다 → at-most-once (처리 전에 죽으면 유실)
  2. 읽고 → 처리하고 → 위치를 저장한다 → at-least-once (커밋 전에 죽으면 재처리)

그리고 이어서 이렇게 씁니다 — "많은 경우 메시지에는 primary key가 있어 갱신이 멱등적이다 (같은 메시지를 두 번 받아도 같은 레코드를 덮어쓸 뿐)." 즉 at-least-once를 안전하게 만드는 것은 소비 측 멱등성이라는 것이 Kafka 설계의 전제입니다.

2단계 — EOS가 실제로 무엇을 원자적으로 묶는가

Kafka 트랜잭션의 특이한 점은 프로듀서만 트랜잭션 주체라는 것입니다. 컨슈머는 트랜잭션에 참여하지 않고, 대신 프로듀서가 컨슈머의 커밋 오프셋까지 트랜잭션 안에서 갱신합니다.

트랜잭션의 원자성 범위
대상원자성 보장비고
출력 Kafka 토픽 쓰기보장여러 토픽·파티션에 걸쳐도 원자적
입력 오프셋 커밋보장sendOffsetsToTransaction으로 같은 트랜잭션에 포함
외부 DB 쓰기보장 없음Kafka 트랜잭션과 분리된 트랜잭션
외부 HTTP·gRPC 호출보장 없음abort 해도 호출은 취소되지 않음
이메일·푸시 발송보장 없음되돌릴 수단이 아예 없음
파일·오브젝트 스토리지보장 없음Connect처럼 오프셋을 출력과 같은 곳에 저장하는 패턴이 필요

공식 문서는 외부 시스템에 쓸 때의 한계를 이렇게 설명합니다 — "컨슈머의 위치를 실제 저장된 출력과 조율해야 한다는 데 한계가 있다. 고전적 방법은 2단계 커밋이지만, 더 간단하고 일반적인 방법은 컨슈머가 자기 오프셋을 출력과 같은 장소에 저장하는 것이다."

예로 든 것이 Kafka Connect의 HDFS 커넥터입니다 — 데이터와 오프셋을 함께 기록해 "둘 다 갱신되거나 둘 다 갱신되지 않음"을 보장합니다. 이 아이디어가 아래 해결 섹션의 처리 이력 테이블 패턴의 근거입니다.

3단계 — 멱등 프로듀서 · 트랜잭션 · 컨슈머 멱등성은 다른 것이다

이름이 비슷해 가장 많이 혼동되는 세 가지
기능 해결하는 문제 범위 설정
멱등 프로듀서 프로듀서 재시도로 인한 중복 append 파티션 단위, 하나의 프로듀서 세션 enable.idempotence=true (4.x 기본값)
트랜잭션 여러 파티션 쓰기 + 오프셋 커밋의 원자성 Kafka 내부. 여러 토픽·파티션에 걸침 transactional.id (프로듀서 전용), 컨슈머는 isolation.level=read_committed + enable.auto.commit=false
컨슈머 멱등성 외부 시스템에 대한 중복 부작용 애플리케이션이 직접 구현 Kafka 설정이 아님. 코드로 만들어야 함

멱등 프로듀서는 파티션 단위 중복 제거이고, 트랜잭션과 다릅니다. 멱등 프로듀서는 "같은 배치를 재전송해도 로그에 두 번 들어가지 않는다"만 보장합니다. 프로세스가 재시작되면 새 프로듀서 세션이 되므로 그 보장도 끊깁니다.

그리고 둘 중 어느 것도 외부 시스템의 중복을 막지 못합니다. 그건 세 번째 항목이고, Kafka 설정으로는 켤 수 없습니다.

4단계 — abort 는 외부 호출을 되돌리지 않는다

4.x에서는 트랜잭션 프로듀서의 예외 처리가 카테고리로 표준화되었습니다. 공식 문서가 정의하는 6개 범주입니다.

트랜잭션 프로듀서 예외 범주 (Apache Kafka 4.x)
범주애플리케이션까지 올라오는가필요한 처리
RetriableException아니요클라이언트가 자동 재시도
RefreshRetriableException아니요메타데이터 갱신 후 클라이언트가 재시도
AbortableException예트랜잭션 abort + 컨슈머 위치 재설정 후 재처리
ApplicationRecoverableException예애플리케이션이 복구 전략 구현. 프로듀서 재시작 포함
InvalidConfigurationException예설정 수정. 프로듀서 재시작은 필수 아님
KafkaException예위 범주에 속하지 않는 일반 예외

중요한 것은 AbortableException을 만나 abort 했을 때 "그 트랜잭션 안에서 이미 실행한 외부 호출"은 그대로 남는다는 점입니다. 공식 문서도 abort 후에는 애플리케이션 상태와 컨슈머 위치를 명시적으로 재설정해 재처리해야 한다고 명시합니다. 재처리하면 외부 호출은 다시 일어납니다.

전달 보장과 트랜잭션의 전체 그림은 6장 전달 보장과 트랜잭션에서, 동작하는 파이프라인은 예제 5 · Exactly-Once 파이프라인에서 다룹니다.

재현 방법

단일 노드 KRaft 클러스터로 재현합니다. 아래 compose는 Apache Kafka의 공식 단일 노드 예제입니다 (3노드 구성은 예제 1). 트랜잭션을 쓰므로 내부 토픽 복제 계수를 1로 낮춰 둡니다.

isolation.level=read_committed도, 트랜잭션도, 멱등 프로듀서도 이 중복을 막지 못합니다. 중복이 생긴 곳은 external-ledger.txt이고 Kafka는 그 존재를 모릅니다.

해결 섹션의 처리 이력 테이블 패턴을 적용한 뒤 4~5단계를 다시 실행하면 wc -l이 5에서 그대로 멈춥니다. 그것이 이 케이스의 정답입니다.

해결

즉시 조치 — 되돌리기 전에 범위를 좁힌다

멱등성 구현은 배포가 필요합니다. 그 전에 재처리를 해야 한다면 "이미 처리한 것을 다시 처리하지 않도록" 범위를 좁히는 것이 유일한 방어입니다.

--reset-offsets는 그룹이 비활성일 때만 동작합니다 (케이스 1). 그리고 되돌리기 전에 반드시 이 질문에 답하세요 — "이 구간을 다시 처리하면 외부 시스템에 어떤 부작용이 몇 건 생기는가?" 답을 모르면 되돌리지 마세요.

근본 해결 1 — 외부 API의 멱등 키를 쓴다

가장 깨끗한 방법입니다. 대부분의 결제·정산 API는 멱등 키(idempotency key)를 지원합니다. Kafka 레코드에서 안정적으로 파생되는 값을 키로 써야 합니다.

같은 주문에 대해 호출할 때마다 PG사는 새 승인 요청으로 처리합니다. 재처리는 곧 이중 청구입니다.

멱등 키를 전달하면 PG사가 두 번째 요청에 첫 번째 결과를 그대로 반환합니다. 몇 번 재처리해도 승인은 한 번입니다.

  • UUID.randomUUID() — 재처리마다 값이 바뀌어 멱등성이 없습니다.
  • System.currentTimeMillis() — 같은 이유로 안 됩니다.
  • topic-partition-offset — 매력적이지만 위험합니다. 케이스 3처럼 로그가 잘리거나 케이스 5처럼 토픽을 재적재하면 오프셋이 달라집니다. 비즈니스 식별자를 우선하세요.
  • 키가 너무 넓으면(주문 ID만) 정당한 재승인도 막힙니다. 버전·시퀀스를 포함하세요.

근본 해결 2 — 처리 이력 테이블 (외부 API가 멱등 키를 지원하지 않을 때)

공식 문서가 제시하는 방향, 즉 "오프셋(또는 처리 이력)을 출력과 같은 장소에 저장"하는 패턴입니다. DB 트랜잭션 하나로 "부작용 기록"과 "처리 표시"를 묶습니다.

①과 ② 사이에서 프로세스가 죽으면 "선점은 했지만 외부 호출은 안 된" 상태가 남습니다. 재처리 때 ①이 0을 반환해 건너뛰므로 유실이 됩니다.

이 빈틈을 막으려면 상태 컬럼을 두고 CLAIMED → CALLED → DONE으로 전이시키면서, CLAIMED 상태로 일정 시간 이상 남은 행을 복구 배치가 재시도하게 만듭니다. 그 재시도가 안전하려면 외부 API의 조회 API로 "이미 승인됐는지" 확인할 수 있어야 합니다.

완벽한 exactly-once는 외부 시스템의 협력 없이 만들 수 없습니다. 이것이 공식 문서가 말하는 내용의 실무적 의미입니다.

근본 해결 3 — 부작용을 경계 밖으로 밀어낸다

구조적으로 가장 견고한 방법은 외부 호출을 파이프라인에서 분리하는 것입니다. Kafka 안에서는 EOS를 온전히 쓰고, 외부 호출은 전용 컨슈머 하나가 담당하며 그 컨슈머에만 멱등성을 구현합니다.

예방 체크리스트

시험 포인트

  • Kafka의 기본 전달 보장은 at-least-once입니다. "exactly-once가 기본"을 고르면 오답입니다.
  • at-most-once를 만드는 방법 → 프로듀서 재시도를 끄고 처리 전에 오프셋 커밋. at-least-once → 처리 후에 커밋. 순서를 바꿔 놓은 선택지가 오답으로 나옵니다.
  • EOS 경계: Kafka 토픽 → 처리 → Kafka 토픽. "EOS를 켜면 DB 중복도 막힌다"는 대표적 오답입니다.
  • 트랜잭션에서 transactional.id는 프로듀서에만 있습니다. 컨슈머 쪽 필수 설정은 isolation.level=read_committed와 enable.auto.commit=false입니다.
  • isolation.level 기본값은 read_uncommitted입니다. 이 값에서는 abort 된 트랜잭션의 레코드도 보입니다.
  • API 순서: initTransactions() → beginTransaction() → send()… → sendOffsetsToTransaction() → commitTransaction() / abortTransaction(). 순서 배열 유형으로 자주 출제됩니다.

멱등 프로듀서 = 파티션 단위 중복 제거(재시도로 인한 중복 append 방지).
트랜잭션 = 여러 파티션 쓰기 + 오프셋 커밋의 원자성(Kafka 내부).
컨슈머 멱등성 = 외부 부작용 중복 방지(애플리케이션 코드).

"멱등 프로듀서를 켜면 exactly-once가 된다"는 오답입니다. 멱등 프로듀서는 하나의 프로듀서 세션 안에서 파티션 단위로만 동작합니다. enable.idempotence 기본값은 true이고, 이때 max.in.flight.requests.per.connection은 5 이하여야 합니다.

Streams의 EOS 설정 값은 processing.guarantee=exactly_once_v2입니다. 이 값은 Streams 애플리케이션 내부의 상태 저장소·리파티션 토픽·출력 토픽까지 원자적으로 묶어 줍니다. 그러나 Processor 안에서 호출한 외부 시스템은 여전히 그 밖입니다.

트랜잭션 프로듀서의 예외는 4.x에서 6개 범주로 표준화되었습니다. 그중 애플리케이션이 abort + 컨슈머 위치 재설정으로 대응해야 하는 것은 AbortableException이고, 프로듀서 재시작이 필요한 것은 ApplicationRecoverableException입니다.
