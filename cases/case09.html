실수 케이스 · 9

스키마 배포 후 전체 컨슈머가 죽었다

스키마 등록이 409 Conflict로 막혔습니다. 릴리스 일정이 급해 호환성 모드를 NONE으로 바꿔 통과시켰고, 프로듀서를 먼저 배포했습니다. 11분 뒤 이 토픽을 구독하는 컨슈머 7개가 전부 크래시 루프에 들어갔습니다. 409는 버그가 아니라 이 사고를 막고 있던 안전장치였습니다.

이 케이스에서 얻어 갈 것

  • 호환성 모드 7종의 정의를 "누가 누구의 데이터를 읽는가"로 설명할 수 있습니다.
  • BACKWARD면 컨슈머 먼저, FORWARD면 프로듀서 먼저 배포해야 하는 이유를 압니다.
  • 역직렬화 실패가 남기는 실제 예외와, 그것이 왜 크래시 루프가 되는지 압니다.
  • 이미 잘못된 스키마가 등록되고 나쁜 레코드가 토픽에 들어간 뒤의 복구 절차를 압니다.

상황

주문 이벤트 파이프라인입니다. orders 토픽은 파티션 24개, 복제 계수 3, 브로커 3대에서 일 500만 건을 받습니다. Avro + Schema Registry를 쓰고, subject는 기본 전략(TopicNameStrategy)에 따라 orders-value입니다.

이 토픽을 구독하는 컨슈머는 7개입니다 — 정산, 배송, 알림, 리스크, 검색 인덱서, 데이터 웨어하우스 싱크, 실시간 대시보드. 전부 생성된 Avro 클래스(SpecificRecord)를 씁니다.

CI 파이프라인의 스키마 등록 단계가 409로 실패했습니다. 릴리스 창구가 닫히기 30분 전이었고, 담당자는 스택오버플로에서 본 대로 subject의 호환성 모드를 NONE으로 바꿨습니다.

그리고 프로듀서를 먼저 배포했습니다. "데이터의 원천이니까 프로듀서가 먼저"라는 것이 이유였습니다. 14:02에 배포가 끝나고, 14:13에 7개 컨슈머 전부가 재시작 루프에 들어갔습니다.

  1. 409를 우회했다. 409는 "이 변경은 기존 스키마와 호환되지 않는다"는 정확한 진단이었습니다. 모드를 NONE으로 바꾼 것은 진단을 고친 것이 아니라 진단기를 끈 것입니다.
  2. 양방향 비호환 변경을 했다. 타입 변경(long → string)과 default 없는 필드 추가·제거는 어느 방향으로도 호환되지 않습니다. 배포 순서를 어떻게 바꿔도 깨집니다.
  3. 프로듀서를 먼저 배포했다. 기존 컨슈머(v1 리더)가 새 데이터(v2 라이터)를 읽어야 하는 상황이 되었습니다. 이 방향을 보장하는 것은 FORWARD이고, 이 변경은 그것도 만족하지 않았습니다.

관측된 증상

메트릭이 어떻게 보였는가

  • consumer lag: 7개 그룹 전부가 동시에 수직 상승. 여러 그룹이 함께 죽는 것은 공통 원인(브로커 또는 데이터 형식)을 가리킵니다.
  • 파드 재시작 횟수: 컨슈머 파드가 3~5분마다 재시작. CrashLoopBackOff.
  • records-consumed-rate: 0. 첫 번째 v2 레코드에 부딪히는 순간 예외로 죽고, 재시작해도 같은 오프셋에서 다시 죽습니다.
  • Schema Registry 요청: 스키마 조회(GET /schemas/ids/1418)가 급증. 컨슈머가 재시작마다 다시 조회합니다.
  • 브로커·프로듀서 지표: 전부 정상. 프로듀서는 아무 문제 없이 쓰고 있었습니다.

컨슈머 로그 — 크래시 루프의 지문

Kafka 클라이언트가 역직렬화 실패를 감싸는 예외는 RecordDeserializationException이고, 메시지에 파티션과 오프셋이 정확히 찍힙니다. 이 오프셋이 재시작마다 같다는 것이 크래시 루프의 증거입니다.

"Error deserializing VALUE for partition {} at offset {}. If needed, please seek past the record to continue consumption."는 Kafka 4.3의 CompletedFetch에서 확인한 문자열입니다. VALUE 자리에는 KEY 또는 VALUE가 들어갑니다 (RecordDeserializationException.DeserializationExceptionOrigin 열거형).

"Error deserializing Avro message for id {}"는 Confluent AbstractKafkaAvroDeserializer에서 확인한 SerializationException 메시지입니다. id가 스키마 ID라는 점이 중요합니다 — 이 번호로 어떤 스키마가 문제인지 바로 조회할 수 있습니다.

가장 아래의 AvroTypeException: Found string, expecting long은 Avro 라이브러리가 던지는 형태만 재현한 것으로, 문구가 정확히 일치하지 않을 수 있습니다. 실제 원인 판별은 위의 두 줄과 스키마 ID로 충분합니다.

레코드가 여러 건 섞여 있으면 다음 형태로 감싸져 나오기도 합니다. 같은 CompletedFetch가 출력합니다.

그리고 원래 나왔어야 했던 오류

14:02 이전, CI가 받았던 409가 정확한 진단이었습니다. Schema Registry가 반환하는 본문은 다음 형태입니다.

프로듀서 애플리케이션에서는 이 응답이 아래 형태의 예외로 나타납니다. RestClientException이 메시지 끝에 ; error code: 40901을 붙입니다.

auto.register.schemas가 true면 프로듀서가 런타임에 새 스키마를 등록합니다. 이 케이스에서는 CI에서 409로 막혔지만, 자동 등록에 의존하는 파이프라인에서는 배포 시점에 아무 검증 없이 등록이 시도되고, 실패는 런타임 예외로 나타납니다. 프로덕션 프로듀서에는 auto.register.schemas=false를 두고 스키마 등록을 CI의 명시적 단계로 분리하는 것이 안전합니다.

원인 분석

1단계 — 호환성 모드를 확인한다

전역 모드가 BACKWARD여도 subject 레벨 오버라이드가 있으면 그것이 이깁니다. "우리는 BACKWARD로 운영한다"고 믿고 있어도 subject마다 다를 수 있습니다. 모든 subject의 모드를 정기적으로 점검하세요.

DELETE /config/{subject}로 오버라이드를 제거하면 전역 설정으로 되돌아갑니다.

2단계 — 호환성 모드 7종을 정확히 안다

Schema Registry 설정의 compatibility 유효 값과 그 정의입니다. 공식 설정 설명을 그대로 옮긴 것이므로 이 문장을 기준으로 판단하세요.

3단계 — 배포 순서는 정의에서 그대로 따라 나온다

배포 순서를 외우지 말고 정의에서 유도하세요.

BACKWARD = "새 스키마가 옛 데이터를 읽는다". 그러면 새 스키마를 가진 쪽(리더 = 컨슈머)이 먼저 준비되어야 합니다. 컨슈머를 먼저 올리면, 그 컨슈머는 아직 남아 있는 옛 데이터도 읽고 곧 들어올 새 데이터도 읽습니다. → 컨슈머 먼저

FORWARD = "옛 스키마가 새 데이터를 읽는다". 그러면 새 데이터를 만드는 쪽(라이터 = 프로듀서)을 먼저 올려도 안전합니다. 기존 컨슈머가 새 데이터를 읽을 수 있기 때문입니다. → 프로듀서 먼저

FULL은 양방향이 보장되므로 순서가 자유롭습니다. NONE은 아무것도 보장하지 않으므로 어떤 순서도 안전하지 않습니다.

4단계 — 이 변경이 어느 방향으로도 호환되지 않는 이유

v1 → v2 변경은 세 가지였습니다. 각각을 방향별로 따져 봅니다. 리더(reader) = 읽는 쪽의 스키마, 라이터(writer) = 데이터를 쓴 쪽의 스키마입니다.

변경 BACKWARD

표를 보면 각 변경의 안전한 방향이 서로 다릅니다. 하나는 FORWARD만, 하나는 BACKWARD만 만족하고, 타입 변경은 둘 다 불가입니다. 세 개를 한 릴리스에 묶으면 어떤 모드로도 통과할 수 없습니다.

스키마 변경은 한 릴리스에 한 종류씩 나누는 것이 원칙입니다. 아래 해결 섹션의 다단계 전환이 그 방법입니다.

필드 제거 — default 있던 필드 가능 가능 제거 전에 default를 붙여 두는 것이 요령

직렬화 형식·Schema Registry 아키텍처·wire format의 상세는 8장 스키마와 직렬화에서 다룹니다.

재현 방법

브로커와 Schema Registry가 함께 필요합니다. 브로커는 Apache Kafka의 공식 단일 노드 예제를 쓰고, Schema Registry 컨테이너를 추가합니다 (3노드 구성은 예제 1, Avro 진화 실습은 예제 7).

Schema Registry는 Confluent가 제공하는 별도 컴포넌트이며 Apache Kafka 배포판에 포함되지 않습니다. 위 compose의 :latest 태그는 재현 편의를 위한 것이며, 실제 사용 중인 Confluent Platform 버전으로 고정하세요. Apache Kafka 4.3 문서에는 Schema Registry 관련 설정이 없으므로 이 컴포넌트의 사실은 Confluent 공식 문서와 confluentinc/schema-registry 소스를 근거로 씁니다. CCDAK 출제 범위에는 포함되므로 이 가이드도 다룹니다.

해결

즉시 조치 — 컨슈머를 살리고 프로듀서를 되돌린다

크래시 루프는 같은 오프셋에서 반복해서 죽는 것이므로, 컨슈머를 살리는 방법은 두 가지뿐입니다 — 나쁜 레코드를 건너뛰거나, 나쁜 레코드가 더 생기지 않게 막는 것입니다.

--shift-by 1로 나쁜 레코드를 건너뛰면 그 레코드는 처리되지 않습니다. 나쁜 레코드가 수천 건이면 그만큼 유실됩니다.

더 나은 방법은 컨슈머 쪽에 역직렬화 실패 핸들러를 두는 것입니다. Spring Kafka의 ErrorHandlingDeserializer처럼 역직렬화 실패를 예외로 전파하지 않고 DLQ로 보내는 구조라면 컨슈머가 죽지 않고 나쁜 레코드만 격리됩니다. DLQ 패턴은 예제 6에 있습니다.

hard delete(?permanent=true)는 그 스키마 ID로 쓰인 레코드를 영구히 읽을 수 없게 만듭니다. 토픽에 그 ID의 레코드가 남아 있는 동안에는 하지 마세요.

근본 해결 — 변경을 쪼개고, 게이트를 CI에 둔다

비호환 변경 세 개를 한 릴리스에 묶고, 막히자 검사를 껐습니다. 프로듀서가 런타임에 스키마를 등록하므로 배포 전에 검증할 기회도 없었습니다.

모드는 전역 FULL_TRANSITIVE로 강화하고, 프로듀서의 자동 등록을 끄고, 등록·검증을 CI의 명시적 단계로 옮깁니다.

필요한 변경을 여러 릴리스로 쪼개는 방법

이 케이스의 세 가지 변경을 FULL 호환을 유지하면서 달성하는 절차입니다.

비호환 변경을 호환 변경의 연속으로 분해하기
릴리스 스키마 변경 애플리케이션 변경 호환성
R1 amountMinor(string, default "")와 currency(string, default "KRW") 추가. legacyCouponId에 default 부여 프로듀서가 amount와 amountMinor를 둘 다 채움 FULL
R2 없음 컨슈머 7개를 순차적으로 amountMinor 읽기로 전환 변경 없음
R3 없음 모든 컨슈머 전환 완료 확인. 대시보드로 검증 변경 없음
R4 amount와 legacyCouponId 제거(둘 다 default가 있는 상태) 프로듀서가 amountMinor만 채움 FULL

타입을 바꾸지 말고 새 필드를 추가하세요. amount(long)를 string으로 바꾸는 대신 amountMinor(string)를 추가하고, 전환이 끝난 뒤 옛 필드를 제거합니다.

제거하기 전에 default를 붙이세요. default가 있는 필드의 제거는 양방향 호환입니다. R1에서 legacyCouponId에 default를 준 것이 R4를 가능하게 만듭니다.

이렇게 하면 모드를 FULL_TRANSITIVE로 두어도 전부 통과하고, 배포 순서를 고민할 필요가 없어집니다.

예방 체크리스트

시험 포인트

  • 배포 순서는 CCDAK 단골 문항입니다. BACKWARD → 컨슈머 먼저, FORWARD → 프로듀서 먼저, FULL → 순서 무관.
  • Schema Registry의 기본 호환성 모드는 BACKWARD입니다.
  • 모드 정의: BACKWARD = "새 스키마가 최신 등록 스키마로 생산된 데이터를 읽을 수 있다", FORWARD = "최신 등록 스키마가 새 스키마로 생산된 데이터를 읽을 수 있다". 두 문장을 바꿔 놓은 선택지가 오답으로 나옵니다.
  • *_TRANSITIVE는 최신 버전 하나가 아니라 이전 모든 버전과 비교합니다.
  • default 있는 필드 추가는 양방향(FULL) 호환입니다. default 없는 필드 추가는 FORWARD만 만족합니다.
  • 호환성 위반 시 HTTP 409, 에러 코드 40901. 프로듀서에서는 SerializationException이 RestClientException을 감싸고, 메시지 끝에 ; error code: 40901이 붙습니다.
  • 기본 subject naming strategy는 TopicNameStrategy이며 subject 이름은 {topic}-key / {topic}-value입니다. 다른 전략은 RecordNameStrategy, TopicRecordNameStrategy입니다.
  • wire format은 magic byte(1) + schema id(4, big-endian) + payload입니다. 컨슈머는 이 id로 Schema Registry에서 라이터 스키마를 조회합니다. 역직렬화 실패 로그의 for id N이 그 id입니다.
  • auto.register.schemas=true의 위험 — 프로듀서가 런타임에 스키마를 등록하므로 검증 없이 새 버전이 생길 수 있습니다. 프로덕션에서는 false가 권장됩니다.

"여러 컨슈머 그룹이 동시에 lag이 치솟고 재시작을 반복한다" → 공통 원인을 의심합니다. 브로커 장애가 아니라면 데이터 형식 변경입니다. 확인 순서는 ① 최근 스키마 등록 이력 → ② subject 호환성 모드 → ③ 컨슈머 로그의 RecordDeserializationException과 스키마 ID입니다.

역직렬화 실패 예외 메시지는 파티션과 오프셋을 정확히 알려 줍니다 — "Error deserializing VALUE for partition {tp} at offset {n}. If needed, please seek past the record to continue consumption." 이 안내대로 seek하거나 오프셋을 밀면 진행할 수 있지만, 그 레코드는 유실됩니다.
