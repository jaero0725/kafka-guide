Exactly-Once 파이프라인 (consume-transform-produce)

Kafka의 exactly-once는 "중복이 절대 없다"는 마법이 아닙니다. 출력 레코드와 입력 오프셋 커밋을 하나의 원자적 트랜잭션으로 묶는 것이 전부입니다. 그래서 Kafka 토픽 → 처리 → Kafka 토픽 경계 안에서만 성립합니다. 이 예제는 그 경계 안에서 완전히 동작하는 파이프라인을 만들고, 경계를 넘는 순간 무엇이 깨지는지까지 확인합니다.

학습 목표

  • initTransactions → beginTransaction → send → sendOffsetsToTransaction → commitTransaction 순서를 근거와 함께 쓸 수 있습니다.
  • transactional.id가 왜 재시작 후에도 같아야 하는지, 좀비 프로듀서 차단(fencing)이 어떻게 동작하는지 설명할 수 있습니다.
  • isolation.level=read_committed와 LSO(Last Stable Offset)가 컨슈머에게 어떻게 보이는지 직접 관찰할 수 있습니다.
  • EOS가 외부 DB·API 호출에는 적용되지 않는다는 점을 코드 수준에서 구분할 수 있습니다.

시나리오

주문 수집 서비스가 orders.raw 토픽에 원본 주문을 넣습니다. 중간 파이프라인이 이 원본을 읽어 통화 정규화와 세금 계산을 하고 orders.enriched 토픽에 씁니다. 하류의 정산 시스템은 orders.enriched만 봅니다.

문제는 이 파이프라인이 배포·크래시·리밸런스로 재시작될 때입니다. at-least-once로 짜면 같은 주문의 보강 결과가 두 번 발행되어 정산 금액이 두 배가 됩니다. at-most-once로 짜면 누락됩니다. 정산 시스템에 멱등 처리를 넣는 것이 정석이지만, 레거시라 손댈 수 없다는 제약이 있습니다.

입력과 출력이 모두 Kafka 토픽이므로 이 구간은 EOS의 적용 대상입니다. Kafka 트랜잭션으로 처리합니다.

at-least-once 파이프라인이 중복을 만드는 이유는 두 개의 쓰기가 원자적이지 않기 때문입니다.

  1. 출력 토픽에 보강 결과를 쓴다.
  2. 입력 토픽의 오프셋을 커밋한다.

1과 2 사이에서 프로세스가 죽으면 재시작 후 같은 입력을 다시 읽어 같은 출력을 또 씁니다. 순서를 뒤집어 2를 먼저 하면 이번엔 유실이 됩니다. 어느 순서로도 해결되지 않으므로 둘을 하나의 트랜잭션으로 묶는 것이 유일한 답입니다.

핵심 메커니즘 세 가지

EOS를 구성하는 세 부품
부품 담당하는 문제 없으면 무슨 일이 생기는가

멱등 프로듀서와 트랜잭션은 다른 것입니다.

  • 멱등성(enable.idempotence=true) — 한 세션 안에서, 파티션 단위로 재시도 중복을 제거합니다. 프로세스를 재시작하면 PID가 새로 발급되어 이전 세션과의 중복은 판별할 수 없습니다.
  • 트랜잭션(transactional.id) — 여러 파티션·토픽에 걸친 원자성과 세션을 넘는 fencing을 제공합니다. 오프셋 커밋도 트랜잭션에 포함시킬 수 있습니다.

transactional.id를 설정하면 멱등성이 자동으로 켜집니다. 반대로 enable.idempotence=false인 상태에서 transactional.id를 주면 ConfigException이 발생합니다.

사전 요구사항

  • 예제 1의 3노드 KRaft 클러스터. 트랜잭션 상태 토픽의 복제 계수가 3, 최소 ISR이 2여야 합니다 — 예제 1의 compose가 그렇게 설정합니다.
  • 토픽 orders.raw(6파티션·RF3·min.insync.replicas=2), orders.enriched(동일). 예제 1의 create-topics.sh가 만듭니다.
  • Apache Kafka 4.3.1 클라이언트, Java 17 이상

transaction.state.log.replication.factor의 기본값은 3, transaction.state.log.min.isr의 기본값은 2입니다. 브로커가 1대인 환경에서 트랜잭션을 쓰려면 두 값을 1로 내려야 하고, 그러면 트랜잭션 로그가 단일 사본이 되어 EOS 보장 자체가 무의미해집니다. 트랜잭션 실습은 반드시 3노드에서 하세요.

트랜잭션 루프 — 이 예제의 본체

진입점 — transactional.id를 어떻게 정하는가

재시작해도 같아야 하고, 인스턴스끼리는 달라야 합니다.

  • UUID.randomUUID()로 만들면 재시작마다 달라져 fencing이 동작하지 않습니다. 옛 인스턴스가 계속 쓸 수 있습니다.
  • 모든 인스턴스가 같은 값을 쓰면 서로를 계속 fencing해서 아무도 일하지 못합니다.
  • 정답은 안정적인 인스턴스 식별자입니다. K8s StatefulSet의 파드 서수(pipeline-0), 또는 배포 시 주입하는 INSTANCE_ID를 씁니다.

KIP-447 이후에는 인스턴스마다 프로듀서 하나로 충분합니다. 파티션마다 프로듀서를 만드는 옛 패턴은 필요하지 않습니다 — groupMetadata()를 넘기면 브로커가 그룹 세대로 fencing해 줍니다.

실행 방법

검증 방법

1. 출력이 정확히 한 번씩 있는가

2. read_committed와 read_uncommitted의 차이를 눈으로 본다

이것이 이 예제의 가장 교육적인 검증입니다. 트랜잭션 마커(commit/abort 표시)는 로그에 실제 레코드로 기록되므로, 두 격리 수준의 건수와 오프셋이 다르게 보입니다.

정상 종료된 파이프라인에서는 두 격리 수준의 레코드 수가 같습니다 (abort된 트랜잭션이 없으므로). 하지만 kafka-get-offsets.sh의 합계는 레코드 수보다 큽니다. 차이가 바로 트랜잭션 커밋 마커가 차지한 오프셋입니다. "오프셋 합계와 메시지 수가 안 맞는다"는 신고의 흔한 원인이 이것입니다.

3. abort된 트랜잭션이 하류에 보이지 않는가

파이프라인을 처리 도중에 강제 종료해 미완료 트랜잭션을 만들고, read_committed에는 나타나지 않는지 확인합니다.

epoch가 0에서 1로 올라간 것이 fencing이 동작한 증거입니다. 이제 옛 프로세스(있었다면)가 같은 transactional.id로 쓰려 하면 ProducerFencedException을 받고 죽습니다. 그리고 위 검증 1을 다시 실행하면 여전히 모든 키의 카운트가 1입니다 — 크래시했는데도 중복이 없습니다.

4. 오프셋과 출력이 같이 전진했는가

LAG이 0이면 입력을 모두 처리했다는 뜻입니다. 여기서 CURRENT-OFFSET은 트랜잭션과 함께 커밋된 값입니다. 즉 이 오프셋이 전진했다는 것은 그 구간의 출력이 반드시 커밋되었다는 것과 동의어입니다.

EOS의 경계 — 가장 흔한 오해

Kafka 트랜잭션이 롤백할 수 있는 것은 Kafka에 쓴 것뿐입니다. 트랜잭션 안에서 DB에 INSERT하거나 결제 API를 호출하면 그 부수효과는 abort되어도 남습니다.

트랜잭션 안에서 외부 시스템을 호출합니다. abortTransaction()이 실행되면 Kafka 출력은 사라지지만 DB 행과 이메일은 남습니다. 재처리 시 두 번째 이메일이 발송됩니다.

트랜잭션 안에서는 Kafka 쓰기만 합니다. 외부 시스템 반영은 별도 컨슈머가 자체 멱등 키로 처리합니다. 같은 이벤트를 두 번 받아도 결과가 같습니다.

"EOS를 켜면 데이터베이스 중복도 방지된다"는 선택지는 항상 오답입니다. Kafka의 exactly-once는 Kafka 토픽을 읽고 Kafka 토픽에 쓰는 경계에서만 성립합니다. 외부 시스템에는 컨슈머 측 멱등성(고유 키 + upsert, 또는 처리 기록 테이블)을 직접 구현해야 합니다.

Kafka Streams에서 같은 보장을 얻는 설정은 processing.guarantee=exactly_once_v2입니다 (기본값은 at_least_once이고, 유효값은 이 두 개뿐입니다 — exactly_once와 exactly_once_beta는 4.0에서 제거되었습니다). 이 설정을 켜면 commit.interval.ms 기본값이 30000에서 100으로 바뀝니다.

자주 하는 실수

props.put(TRANSACTIONAL_ID_CONFIG, UUID.randomUUID().toString())은 트랜잭션은 동작하지만 fencing이 동작하지 않습니다. 재시작하면 브로커가 다른 논리적 프로듀서로 보기 때문에 네트워크 분리로 살아남은 옛 인스턴스를 차단할 수 없습니다. 게다가 쓰이지 않는 transactional.id가 코디네이터에 누적되어 transactional.id.expiration.ms(기본 7일) 동안 남습니다. 안정적인 인스턴스 식별자를 쓰세요.

enable.auto.commit의 기본값은 true입니다. 그대로 두면 컨슈머가 auto.commit.interval.ms(기본 5000)마다 트랜잭션과 무관하게 오프셋을 커밋합니다. 트랜잭션이 abort되어도 오프셋은 이미 전진해 있으므로 그 구간의 입력이 영구히 유실됩니다. 공식 문서는 sendOffsetsToTransaction을 쓸 때 자동 커밋을 끄고 수동 커밋도 하지 말라고 명시합니다.

프로듀서 쪽 트랜잭션만 완벽하게 짜고 하류 컨슈머를 기본값으로 두면, abort된 레코드가 그대로 읽혀 EOS가 무너집니다. isolation.level의 기본값은 read_uncommitted입니다. 토픽에 "이 토픽은 트랜잭션 토픽"이라는 표시를 붙일 방법이 없으므로 팀 간 문서로 관리해야 합니다.

new OffsetAndMetadata(record.offset() + 1)은 동작하지만 리더 에포크 정보가 빠집니다. Kafka 4.x는 ConsumerRecords#nextOffsets()로 다음 오프셋과 리더 에포크를 함께 제공합니다. 공식 javadoc도 리더 에포크를 커밋 메타데이터로 넣으라고 명시합니다. records.nextOffsets()를 쓰세요.

그리고 sendOffsetsToTransaction의 두 번째 인자에는 new ConsumerGroupMetadata(groupId)를 직접 만들지 말고 consumer.groupMetadata()를 넘기세요. 그래야 브로커가 그룹 세대까지 검증하는 더 강한 fencing을 제공합니다.

트랜잭션 블록 안의 DB INSERT·HTTP 호출·파일 쓰기는 abortTransaction()으로 되돌아가지 않습니다. 이 예제 EOS의 경계 절의 Before/After를 보세요. 외부 반영은 별도 컨슈머 + 멱등 키로 분리하는 것이 정석입니다.

max.poll.records=500(기본값)에 건당 200ms가 걸리면 배치 처리에 100초가 걸립니다. transaction.timeout.ms=60000(기본값)을 넘기므로 커밋 시점에 코디네이터가 이미 트랜잭션을 abort한 상태입니다. 결과는 무한 재처리 루프입니다. max.poll.records를 줄이거나 transaction.timeout.ms를 늘리세요 (단 브로커의 transaction.max.timeout.ms=900000이 상한입니다).
