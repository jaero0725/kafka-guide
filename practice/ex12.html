실무 예제 · 12

Python / Node.js 클라이언트

Kafka 프로토콜은 언어 중립이지만 클라이언트 구현은 그렇지 않습니다. 같은 개념의 설정이 이름이 다르고, 기본값도 다릅니다. 특히 librdkafka 계열은 Java와 다른 기본값을 가진 항목이 있어서 Java 기준 문서를 그대로 옮기면 동작이 달라집니다. 이 예제는 그 차이를 표로 정리하고, 양쪽 언어의 완전한 코드를 제공합니다.

학습 목표

  • librdkafka 설정 이름이 Java와 어떻게 대응되는지 알 수 있습니다.
  • confluent-kafka-python에서 poll()을 왜 호출해야 하는지, flush()가 무엇을 보장하는지 설명할 수 있습니다.
  • kafkajs의 eachMessage·eachBatch와 수동 커밋을 구분해 쓸 수 있습니다.
  • 언어별로 제공되지 않거나 다르게 동작하는 기능(트랜잭션, 리밸런스 콜백)을 판단할 수 있습니다.

시나리오

데이터 팀은 Python으로 ETL을 짜고, 프론트엔드 팀은 Node.js로 BFF를 운영합니다. 둘 다 orders 토픽을 읽어야 합니다.

문제가 된 것은 Java 기준으로 작성된 사내 가이드를 그대로 따랐을 때였습니다. Python 쪽에서 acks=all과 enable.idempotence=true는 잘 넘어갔지만, producer.produce() 뒤에 flush()를 부르지 않아 스크립트가 종료될 때 버퍼의 레코드가 사라졌습니다. Node 쪽에서는 eachMessage가 자동 커밋을 한다는 사실을 모른 채 예외를 삼켜 유실이 발생했습니다.

"프로토콜이 같으니 코드도 비슷할 것"이라는 가정이 사고의 원인이었습니다.

검증 방법

1. 건수가 맞는가

Python은 delivered=1000, Node는 delivered=1000이 나오고 위 합계가 그만큼 증가해야 합니다. 애플리케이션 카운터와 브로커 오프셋이 어긋나면 어딘가에서 실패를 삼킨 것입니다.

2. flush()를 빼면 실제로 유실되는가

linger.ms=20이므로 마지막 배치가 큐에 남은 채 프로세스가 끝납니다. 에러도 로그도 남지 않습니다 — on_delivery 콜백이 실행될 기회가 없기 때문입니다. 시나리오의 사고가 정확히 이것입니다.

3. 두 언어의 컨슈머 그룹이 독립적인가

서로 다른 group.id이므로 같은 데이터를 각자 전부 읽습니다. 같은 그룹 ID를 쓰면 파티션을 나눠 갖게 되어 각 팀이 데이터의 일부만 보게 됩니다 — 흔한 사고입니다.

4. 키 파티셔닝이 언어 간에 호환되는가

Java 기본 파티셔너는 키의 murmur2 해시를 씁니다. librdkafka와 kafkajs도 Java 호환 파티셔너를 제공하지만 기본값이 항상 그것인지는 라이브러리·버전마다 다릅니다.

같은 키가 여러 언어에서 같은 파티션으로 가야 하는 요구사항이 있다면 (예: 한 주문의 이벤트를 Java와 Python이 나눠 발행) — 반드시 실측으로 확인하고 파티셔너를 명시하세요. 어긋나면 순서 보장이 조용히 깨집니다. 이 문서를 작성한 환경에서는 각 라이브러리의 기본 파티셔너를 공식 소스로 확인할 수 없었으므로 단정하지 않습니다.

자주 하는 실수

confluent-kafka의 전달 콜백은 poll() 또는 flush()를 호출하는 스레드에서 실행됩니다. produce()만 반복하면 콜백이 전혀 실행되지 않고 큐가 계속 쌓여 결국 BufferError가 발생합니다. 루프 안에서 producer.poll(0)을 호출하세요.

Java의 close()는 내부적으로 flush를 시도하지만, Python 스크립트는 그냥 끝나면 큐가 사라집니다. flush()의 반환값이 "아직 전달되지 않은 건수"이므로 0이 아니면 유실이 발생한 것입니다 — 반드시 확인하세요.

eachMessage/eachBatch는 autoCommit이 기본 true입니다. 핸들러가 정상 반환하면 오프셋이 전진합니다. 그래서 핸들러 안에서 try-catch로 예외를 삼키면 실패했는데 커밋된 상태가 되어 유실이 됩니다.

커밋 시점을 통제하려면 autoCommit: false + resolveOffset + commitOffsetsIfNecessary를 쓰세요. resolveOffset만으로는 브로커에 커밋되지 않습니다.

eachBatch에서 긴 배치를 처리하는 동안 하트비트를 보내지 않으면 sessionTimeout을 넘겨 그룹에서 축출됩니다. 그러면 다른 인스턴스가 같은 구간을 다시 처리하고, 반복되며 리밸런스 스톰이 됩니다 (케이스 2). 루프 안에서 await heartbeat()를 호출하세요.

리밸런스가 일어난 뒤에도 eachBatch 루프가 계속 돌면 이미 소유권을 잃은 파티션을 처리하게 됩니다. 커밋은 실패하고 처리는 중복됩니다. isStale()과 isRunning()을 매 레코드마다 검사해 즉시 빠져나오세요.

kafkajs는 camelCase 옵션 객체를 씁니다 — bootstrap.servers가 아니라 brokers, acks="all"이 아니라 acks: -1입니다. 알 수 없는 키는 조용히 무시되므로 "설정했는데 안 먹는다"는 상태가 됩니다. librdkafka는 반대로 알 수 없는 키에 오류를 냅니다 — 그쪽이 더 안전합니다.

관련 케이스 스터디

  • 케이스 1 — auto.offset.reset/fromBeginning이 커밋된 오프셋이 없을 때만 적용된다는 점.
  • 케이스 2 — 처리 시간 초과로 리밸런스가 반복된 사고. kafkajs의 heartbeat() 누락이 같은 결과를 만듭니다.
  • 케이스 4 — 키 없는 발행으로 순서가 깨진 사고. 언어 간 파티셔너 불일치도 같은 증상을 만듭니다.
