Kafka Streams 실시간 집계

Kafka Streams는 별도 클러스터가 아니라 애플리케이션에 링크되는 라이브러리입니다. 컨슈머·프로듀서·로컬 상태 저장소를 하나로 묶어 주는 대신, 상태 저장소·changelog·윈도우 시간 개념을 이해하지 않으면 결과가 왜 그렇게 나오는지 설명할 수 없습니다. 이 예제는 1분 단위 클릭 집계를 만들면서 그 부분을 확인합니다.

학습 목표

  • tumbling 윈도우 집계를 DSL로 작성하고 grace period가 늦은 이벤트에 어떻게 작용하는지 설명할 수 있습니다.
  • 상태 저장소(RocksDB)와 changelog 토픽의 관계, 복구 절차를 알 수 있습니다.
  • suppress로 중간 결과를 억제해 윈도우당 한 번만 결과를 내보낼 수 있습니다.
  • processing.guarantee=exactly_once_v2가 바꾸는 설정과 트레이드오프를 알 수 있습니다.

시나리오

커머스 사이트의 클릭 스트림을 실시간으로 집계해 상품별 1분간 클릭 수를 대시보드에 표시합니다. 피크 시 초당 8천 건, 상품은 12만 종입니다.

기존에는 5분마다 도는 배치가 전체를 다시 집계했습니다. 문제는 두 가지였습니다 — 지연이 최대 5분이고, 모바일 앱의 오프라인 큐에서 늦게 도착하는 이벤트가 누락되었습니다. 어떤 이벤트는 30초, 어떤 이벤트는 3분 늦게 옵니다.

Streams로 옮기면서 늦게 온 이벤트를 어디까지 받아 줄지를 명시적인 설정(grace period)으로 정합니다.

아키텍처

집계는 상태를 필요로 합니다. Streams는 그 상태를 로컬 RocksDB에 두고, 같은 내용을 changelog 토픽({application.id}-{store}-changelog)에 compact 정책으로 복제합니다. 인스턴스가 죽으면 다른 인스턴스가 changelog를 재생해 상태를 복원합니다.

병렬성의 단위는 태스크이고, 태스크 수는 입력 파티션 수로 결정됩니다. num.stream.threads(기본값 1)는 한 인스턴스가 돌릴 스레드 수이고, 태스크는 인스턴스·스레드에 분배됩니다. 파티션 6개인 토픽을 처리하는 애플리케이션은 태스크가 6개이므로 인스턴스 × 스레드의 합이 6을 넘으면 나머지는 유휴 상태가 됩니다.

사전 요구사항

토폴로지

Suppressed.untilWindowCloses는 윈도우당 정확히 한 번의 결과를 보장하지만, 결과가 나오는 시점이 윈도우 종료 + grace period 이후로 밀립니다. 이 예제는 1분 윈도우 + 3분 grace이므로 최대 4분 뒤에 결과가 나옵니다.

대시보드가 "대략적인 현재 값"을 실시간으로 보여 줘야 한다면 suppress를 빼고 중간 결과를 그대로 흘려보내거나, Suppressed.untilTimeLimit(Duration, BufferConfig)로 일정 시간 안의 갱신만 묶는 절충안을 씁니다.

BufferConfig.unbounded()는 메모리를 무제한 씁니다. 키 카디널리티가 큰 경우(이 시나리오는 상품 12만 종) 힙 사용량을 실측하고 BufferConfig.maxBytes(...)·maxRecords(...)를 검토하세요. 단 이 두 개는 EagerBufferConfig이므로 untilWindowCloses에는 넣을 수 없습니다.

설정과 기동

실행 방법

suppress(untilWindowCloses) + grace 3분 때문에 결과는 최대 4분 뒤에 나옵니다. 정상입니다. 그리고 Streams는 스트림 시각(이벤트 시각의 진행)으로 윈도우 종료를 판단하므로, 새 이벤트가 들어와 시각이 전진해야 윈도우가 닫힙니다. 이벤트를 한 번만 넣고 기다리면 결과가 나오지 않습니다 — 이후 시각의 이벤트를 하나 더 넣어 시각을 전진시키세요.

검증 방법

1. 내부 토픽이 만들어졌는가

repartition 토픽은 selectKey로 키를 바꿨기 때문에 생겼습니다. mapValues처럼 값만 바꾸는 연산으로는 생기지 않습니다. changelog 토픽은 상태 저장소의 백업이며 compact 정책입니다.

윈도우 저장소의 changelog는 compact,delete 조합을 씁니다 — 키별 최신값을 유지하면서 보관 기간이 지난 윈도우는 삭제합니다. ReplicationFactor: 3이 나오는 것은 StreamsConfig.REPLICATION_FACTOR_CONFIG=3을 명시했기 때문입니다. 명시하지 않으면 브로커 default.replication.factor(기본 1)를 따릅니다.

2. 집계 결과가 맞는가

30건을 3개 상품에 나눠 넣었으므로 각 10이 나옵니다. windowStart가 분 경계(00초)에 정렬되어 있는지 확인하세요 — tumbling 윈도우는 epoch 기준으로 정렬되며, 이벤트가 들어온 시각이 아니라 고정된 경계를 씁니다.

3. grace period가 늦은 이벤트를 받아 주는가

dropped-records-total이 증가하면 grace period가 짧다는 신호입니다. 이 메트릭에 알림을 걸어 두지 않으면 "집계가 조금씩 부족한데 이유를 모르겠다"는 상태가 됩니다. 늦은 이벤트는 에러 없이 조용히 버려집니다.

4. 상태 복구가 동작하는가

REBALANCING에 머무는 시간이 복구에 걸리는 시간입니다. 상태가 크면 이 시간이 수십 분까지 늘어납니다 — num.standby.replicas를 1 이상으로 두면 다른 인스턴스가 미리 상태를 따라 만들어 두므로 이 시간이 크게 줄어듭니다.

5. exactly_once_v2가 커밋 주기를 바꾸는가

ProducerId set to ... 로그가 나오면 트랜잭션 프로듀서가 쓰이는 것입니다. transactional.id는 Streams가 application.id와 태스크에서 자동으로 만들므로 직접 정하지 않습니다. 하류에서 이 결과를 읽는 컨슈머는 isolation.level=read_committed여야 EOS가 완성됩니다(예제 5).

자주 하는 실수

StreamsConfig.REPLICATION_FACTOR_CONFIG의 기본값은 -1이며 "브로커 기본값을 따름"을 뜻합니다. 브로커의 default.replication.factor 기본값은 1이므로, changelog와 repartition 토픽이 단일 사본으로 만들어집니다. 그 브로커 한 대가 죽으면 상태를 복구할 수 없습니다. 내부 토픽은 자동 생성되기 때문에 이 문제가 조용히 지나갑니다.

기본값이 /tmp/kafka-streams입니다. 컨테이너를 재생성하면 로컬 상태가 사라지고 changelog 전체를 재생해야 합니다. 상태가 수백 GB면 복구에 수십 분이 걸리고, 그동안 처리가 멈춥니다. 영속 볼륨 + num.standby.replicas ≥ 1을 함께 쓰세요.

selectKey·map·flatMap·groupBy는 키를 바꿀 수 있으므로 리파티션을 유발합니다. Streams가 내부 토픽을 만들어 데이터를 한 번 더 브로커로 왕복시킵니다 — 네트워크와 디스크 비용이 두 배가 됩니다.

값만 바꾸면 되는 경우에는 mapValues·flatMapValues를 쓰세요. 키가 바뀌지 않으므로 리파티션이 없습니다. 어디에 리파티션 토픽이 생기는지는 topology.describe() 출력으로 확인할 수 있습니다.

윈도우 저장소의 보관 기간이 (윈도우 크기 + grace period)보다 짧으면, grace 안에 도착한 이벤트를 담을 저장소가 이미 없습니다. 결과적으로 grace 설정이 무의미해지고 이벤트가 조용히 버려집니다. 이 예제는 WINDOW_SIZE + GRACE + 1분으로 여유를 두었습니다.

Streams의 윈도우는 벽시계가 아니라 이벤트 시각으로 닫힙니다. 입력이 멈추면 스트림 시각도 멈추므로 윈도우가 영원히 닫히지 않습니다. 테스트할 때 "결과가 안 나온다"의 대부분이 이 원인입니다. 이후 시각의 이벤트를 하나 더 넣어 시각을 전진시키세요.

StreamThreadExceptionResponse.REPLACE_THREAD는 인프라 오류(일시적 네트워크 문제)에 적합합니다. 데이터 오류(파싱 실패 등)에 쓰면 교체된 스레드가 같은 레코드에서 다시 실패해 무한 루프가 됩니다. CPU만 태우고 lag은 줄지 않습니다. 역직렬화·처리 예외는 전용 핸들러 (default.deserialization.exception.handler, default.processing.exception.handler)로 분리하세요.
