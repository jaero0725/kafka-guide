Kafka Connect CDC 파이프라인

MySQL의 binlog를 Debezium이 읽어 Kafka 토픽으로 흘리고, sink 커넥터가 그것을 외부 저장소로 내립니다. 코드를 한 줄도 쓰지 않고 JSON 설정만으로 파이프라인이 만들어지는 대신, 내부 토픽 3개·오프셋 저장 위치의 비대칭·에러 처리를 모르면 장애 때 손을 쓸 수 없습니다. 그 부분을 중심으로 다룹니다.

학습 목표

  • Connect distributed 모드의 내부 토픽 3개가 무엇을 저장하고 왜 compact여야 하는지 설명할 수 있습니다.
  • source 커넥터와 sink 커넥터의 오프셋 저장 위치가 다르다는 것을 확인할 수 있습니다.
  • errors.* 설정으로 DLQ를 구성하고 실패 원인 헤더를 읽을 수 있습니다.
  • REST API로 커넥터를 배포·상태 확인·재시작·오프셋 조회할 수 있습니다.

시나리오

주문 서비스의 MySQL orders 테이블을 분석 시스템과 검색 인덱스가 함께 필요로 합니다. 기존에는 두 팀이 각각 야간 배치로 전체를 덤프해 가져갔습니다. 데이터가 최대 24시간 낡고, 배치가 돌 때마다 DB에 부하가 걸렸습니다.

CDC(Change Data Capture)로 바꿉니다. Debezium이 MySQL binlog를 읽어 INSERT/UPDATE/DELETE를 이벤트로 발행하면, 하류는 그 스트림만 소비합니다. DB에 추가 쿼리가 발생하지 않고 지연은 초 단위가 됩니다.

애플리케이션 코드를 고칠 수 없다는 제약이 있어 outbox 패턴 대신 테이블 직접 캡처를 선택했습니다.

아키텍처

distributed 모드의 내부 토픽 3개
설정 저장하는 것 권장 파티션 cleanup.policy
config.storage.topic 커넥터·태스크 설정 반드시 1 (순서가 의미를 갖습니다) compact
offset.storage.topic source 커넥터의 진행 위치 (binlog 파일·포지션 등) 기본 25 compact
status.storage.topic 커넥터·태스크 상태, 사용 중인 토픽 목록 기본 5 compact

이 세 토픽이 cleanup.policy=delete로 만들어지면 리텐션이 지난 뒤 커넥터 설정과 진행 위치가 사라집니다. 워커를 재시작하는 순간 커넥터가 사라지거나 source가 처음부터 다시 읽습니다. Connect가 자동 생성할 때는 compact로 만들지만, 운영자가 미리 만들어 둘 때 실수하기 쉬운 지점입니다. 변경은 소급 적용되지 않으므로 이미 delete로 만들었다면 토픽을 다시 만들어야 합니다(케이스 8).

오프셋 저장 위치가 비대칭입니다.

  • source 커넥터 — 외부 시스템에서 어디까지 읽었는지를 Connect가 관리합니다. offset.storage.topic에 저장됩니다. 컨슈머 그룹이 아닙니다.
  • sink 커넥터 — 내부적으로 컨슈머 그룹(connect-{connector-name})을 씁니다. 오프셋은 __consumer_offsets에 저장되고 kafka-consumer-groups.sh로 조회·리셋할 수 있습니다.

그래서 "sink 커넥터를 처음부터 다시 읽게 하려면?"의 답은 kafka-consumer-groups.sh --reset-offsets이고, "source 커넥터를 처음부터 다시 읽게 하려면?"의 답은 커넥터를 stop한 뒤 DELETE /connectors/{name}/offsets입니다.

실행 방법

검증 방법

1. CDC 토픽이 만들어지고 이벤트가 들어왔는가

__op 값이 핵심입니다. r은 초기 스냅샷(read), c는 INSERT, u는 UPDATE, d는 DELETE입니다. 키가 테이블의 프라이머리 키({"id":4})로 설정되므로 같은 행의 변경이 항상 같은 파티션으로 가 순서가 보장됩니다. 이것이 CDC에서 키 설계가 자동으로 해결되는 이유입니다.

2. source와 sink의 오프셋이 다른 곳에 있는지 확인

source는 REST로만 보이고 sink는 컨슈머 그룹으로 보입니다. 이 비대칭이 실무에서 가장 자주 헷갈리는 지점이고 시험에도 나옵니다.

3. sink 파일에 실제로 적재되었는가

4. 워커 이탈 시 태스크가 재분배되는가

5. DLQ가 동작하는가

__connect.errors.stage가 어느 단계에서 실패했는지를 알려 줍니다 — VALUE_CONVERTER(역직렬화), TRANSFORMATION(SMT), TASK_PUT(sink 쓰기) 등입니다. 이 헤더가 없으면 DLQ는 원인을 알 수 없는 레코드 더미가 됩니다.

자주 하는 실수

errors.tolerance의 기본값은 none입니다. errors.deadletterqueue.topic.name만 설정하고 errors.tolerance를 바꾸지 않으면 첫 실패에서 태스크가 FAILED로 죽습니다. 그리고 errors.deadletterqueue.context.headers.enable의 기본값도 false이므로, 켜지 않으면 원인을 알 수 없습니다. 세 개를 함께 설정해야 DLQ가 의미를 갖습니다.

tasks.max는 상한일 뿐이고, 실제 태스크 수는 커넥터가 결정합니다. MySQL binlog는 단일 순서 스트림이므로 Debezium MySQL 소스는 항상 태스크 1개입니다. 10으로 올려도 1개입니다. sink 커넥터는 구독 파티션 수가 상한입니다. "커넥터를 늘리면 무조건 빨라진다"는 오해가 여기서 나옵니다.

topic.prefix는 토픽 이름과 오프셋 저장 키에 모두 들어갑니다. 운영 중에 바꾸면 Connect가 완전히 새로운 커넥터로 인식해 초기 스냅샷을 다시 뜨고, 하류는 새 토픽을 구독해야 합니다. 처음에 정하고 바꾸지 마세요. 토픽 이름만 바꾸고 싶으면 RegexRouter SMT를 쓰세요 (이 예제가 그렇게 했습니다).

group.id는 달라도 config.storage.topic 등을 같게 두면 서로의 커넥터 설정을 덮어씁니다. Connect 클러스터를 나눌 때는 group.id와 내부 토픽 3개 이름을 모두 분리하세요.

plugin.path 하위에 여러 커넥터의 jar를 섞어 두면 의존성 버전이 충돌해 기동은 되지만 런타임에 NoSuchMethodError가 납니다. 커넥터마다 별도 하위 디렉터리로 격리하세요. 플러그인이 실제로 로드되었는지는 GET /connector-plugins로 확인합니다.

DELETE /connectors/{name}는 설정만 지웁니다. 같은 이름으로 다시 만들면 이전 오프셋을 이어받습니다. 이것은 대개 원하는 동작이지만, "처음부터 다시 읽으려고 지웠다 다시 만들었는데 아무 데이터도 안 온다"는 혼란의 원인이기도 합니다. 오프셋을 지우려면 stop → DELETE .../offsets 순서를 밟으세요.
