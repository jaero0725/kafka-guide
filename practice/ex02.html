Spring Boot Producer/Consumer 기본

Spring for Apache Kafka는 KafkaProducer·KafkaConsumer를 감싸 템플릿과 애노테이션으로 바꿔 줍니다. 편해지는 대신 어떤 설정이 어디로 흘러가는지가 가려지므로, 이 예제는 Spring 프로퍼티 ↔ Kafka 설정의 대응을 명시하면서 최소 애플리케이션을 만듭니다.

학습 목표

  • spring.kafka.* 프로퍼티가 어떤 Kafka 설정으로 매핑되는지, 전용 키가 없는 설정은 어디에 넣는지 알 수 있습니다.
  • KafkaTemplate.send()가 반환하는 CompletableFuture를 버리지 않고 다루는 방법을 씁니다.
  • ack-mode 7종의 차이를 알고, 수동 ack(MANUAL_IMMEDIATE)를 코드로 구현할 수 있습니다.
  • concurrency와 파티션 수의 관계를 설명할 수 있습니다.

시나리오

사내 알림 서비스가 여러 도메인 서비스로부터 알림 요청을 받습니다. 기존에는 HTTP 동기 호출이라 알림 서비스가 느려지면 호출한 서비스의 응답 시간까지 함께 늘어났습니다.

이를 Kafka로 분리합니다. 도메인 서비스는 notifications 토픽에 요청을 넣고 즉시 반환하고, 알림 서비스는 그 토픽을 소비해 실제 발송을 합니다. 첫 단계 목표는 가장 단순하지만 유실이 없는 구조를 만드는 것입니다.

아키텍처

하나의 Spring Boot 애플리케이션이 프로듀서와 컨슈머를 모두 갖습니다 (실제로는 서비스가 분리되지만, 학습을 위해 한 프로세스에 둡니다). REST 엔드포인트가 프로듀서를 호출하고, @KafkaListener가 소비합니다.

Spring for Apache Kafka의 주요 구성 요소와 대응하는 Kafka 클라이언트
Spring 컴포넌트 감싸는 Kafka 객체 역할
ProducerFactory KafkaProducer 생성 프로듀서 설정을 보관하고 인스턴스를 만듭니다. 기본적으로 하나를 공유합니다
KafkaTemplate KafkaProducer.send() CompletableFuture<SendResult>를 반환합니다. 3.0부터 ListenableFuture가 아닙니다
ConsumerFactory KafkaConsumer 생성 컨슈머 설정을 보관합니다
ConcurrentMessageListenerContainer KafkaConsumer.poll() 루프 concurrency 개의 컨슈머 스레드를 돌립니다. 각 스레드가 별개의 KafkaConsumer입니다
@KafkaListener — poll로 받은 레코드를 메서드 호출로 변환합니다
KafkaAdmin + NewTopic 빈 AdminClient.createTopics() 기동 시 토픽을 선언적으로 만듭니다 (spring.kafka.admin.auto-create, 기본 true)

concurrency는 이 인스턴스가 만드는 컨슈머 스레드 수입니다. 컨슈머 그룹의 병렬성 상한은 여전히 파티션 수입니다. 파티션 3개인 토픽에 concurrency=5를 주면 2개 스레드는 파티션을 할당받지 못해 유휴 상태가 됩니다. 인스턴스를 늘릴 때도 같습니다 — 파티션 수를 넘는 컨슈머는 일하지 않습니다.

전체 코드

application.yml — 프로퍼티가 어디로 가는지

Spring Boot 4.1.0의 spring.kafka.producer.*에는 acks·batch-size·buffer-memory·compression-type·retries·transaction-id-prefix 같은 전용 키만 있습니다. linger.ms·enable.idempotence·delivery.timeout.ms에는 전용 키가 없으므로 spring.kafka.producer.properties.*에 Kafka 원래 이름 그대로 씁니다. 컨슈머도 같습니다 — isolation.level은 properties로 넣어야 합니다.

이 두 모드를 쓰려면 리스너 메서드가 Acknowledgment 파라미터를 받아야 합니다. 받지 않으면 기동 시점에 설정 오류가 발생합니다. 그리고 acknowledge()를 호출하지 않으면 오프셋이 영구히 전진하지 않아 재시작마다 같은 레코드를 다시 읽습니다. 예외 경로에서 acknowledge()를 건너뛰도록 짜는 것이 중요합니다.

실행 방법

검증 방법

1. 토픽이 선언대로 만들어졌는가

2. 같은 키가 같은 파티션으로 가는가

같은 userId의 레코드가 모두 하나의 파티션 번호로 나옵니다. 기본 파티셔너는 키가 있으면 murmur2(key) % 파티션수로 결정적으로 배치합니다. 여기서 파티션이 여러 개로 흩어진다면 키가 null로 들어간 것입니다.

3. concurrency가 실제로 파티션을 나눠 갖는가

concurrency: 3이므로 컨슈머 3개가 파티션 하나씩 가져갑니다. concurrency를 5로 올려 다시 확인해 보세요 — CONSUMER-ID는 5개가 되지만 파티션을 할당받은 것은 여전히 3개이고 2개는 아무 파티션도 없이 유휴 상태입니다.

4. 수동 ack가 유실을 막는가

레코드가 사라지지 않고 다시 처리되는 것이 정답입니다. 만약 ack.acknowledge()를 처리 전으로 옮기면 같은 실험에서 그 레코드가 영구히 사라집니다(at-most-once). 커밋 시점이 유실·중복 경계를 결정한다는 것을 직접 확인할 수 있습니다 (예제 4에서 더 자세히 다룹니다).

자주 하는 실수

template.send(topic, key, value);로 끝내면 브로커가 거부해도 애플리케이션은 성공한 것으로 압니다. whenComplete로 실패를 관측하거나, 결과가 중요하면 join()으로 확인하세요. (join()은 배치를 무력화하므로 고빈도 경로에는 쓰지 않습니다.)

concurrency: 10을 파티션 3개 토픽에 주면 7개 스레드가 아무 일도 하지 않습니다. 처리량을 늘리려면 파티션 수를 먼저 늘려야 합니다. 단 파티션 수는 늘릴 수만 있고, 늘리면 기존 키의 해시 분배가 바뀌어 순서 보장이 깨집니다(케이스 5).

spring.json.trusted.packages: "*"는 레코드에 담긴 타입 정보로 임의 클래스를 역직렬화할 수 있게 만듭니다. 외부에서 토픽에 쓸 수 있는 환경이라면 역직렬화 취약점이 됩니다. 구체적인 패키지만 나열하세요.

auto-offset-reset은 커밋된 오프셋이 없을 때만 적용됩니다. 이미 커밋된 그룹에서 earliest로 바꿔도 아무 일도 일어나지 않습니다. 처음부터 다시 읽으려면 그룹을 새로 만들거나 kafka-consumer-groups.sh --reset-offsets를 써야 합니다 (케이스 1).

Spring Boot 4에서 Kafka 스타터 이름과 자동 설정 패키지가 바뀌었습니다. org.springframework.kafka:spring-kafka를 직접 넣는 3.x 방식도 동작하지만, Boot 4에서는 spring-boot-starter-kafka를 쓰는 것이 권장입니다. 그리고 ListenableFuture는 3.0에서 제거되었으므로 2.x 예제의 addCallback(...) 코드는 컴파일되지 않습니다.
