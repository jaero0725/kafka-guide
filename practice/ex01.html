로컬 KRaft 클러스터 구축

Docker Compose v2로 브로커·컨트롤러 겸용 노드 3대를 띄웁니다. ZooKeeper 컨테이너는 하나도 등장하지 않습니다 — ZooKeeper 모드는 Kafka 4.0에서 제거되었기 때문입니다. 이 페이지의 docker-compose.yml은 이후 예제 2~12과 케이스 스터디의 재현 코드가 모두 참조하는 공통 기반이므로, 여기서 한 번 제대로 만들어 두고 계속 재사용합니다.

학습 목표

  • KRaft 노드 롤(process.roles)과 컨트롤러 쿼럼 구성을 실제 설정 파일로 읽고 쓸 수 있습니다.
  • listeners · advertised.listeners · listener.security.protocol.map 세 개가 왜 함께 필요한지, 컨테이너 안/밖에서 접속 주소가 왜 달라야 하는지 설명할 수 있습니다.
  • 브로커 3대 기준의 내부 토픽 복제 계수(offsets.topic.replication.factor 등)를 왜 바꿔야 하는지 알고 설정할 수 있습니다.
  • kafka-metadata-quorum.sh로 컨트롤러 쿼럼이 정상인지 검증할 수 있습니다.

시나리오

커머스 플랫폼의 주문 도메인 팀이 이벤트 기반 아키텍처로 이동하기로 했습니다. 운영 클러스터는 SRE 팀이 관리하지만, 개발자 8명이 각자 노트북에서 프로듀서 재시도·리밸런스·리더 선출 같은 장애 동작을 직접 재현해 볼 로컬 환경이 필요합니다. 단일 브로커로는 복제 계수 3, min.insync.replicas=2, ISR 축소, 리더 이동을 재현할 수 없으므로 처음부터 3노드로 만듭니다.

조건은 세 가지입니다. (1) docker compose up 한 번으로 뜬다. (2) 호스트에서 IDE로 돌리는 Java 애플리케이션도, 컨테이너 안에서 돌리는 CLI도 같은 클러스터에 붙는다. (3) 컨테이너를 재시작해도 토픽과 데이터가 남는다.

이후 예제들은 클러스터 구축을 다시 설명하지 않고 "예제 1의 클러스터를 사용합니다"라고만 씁니다. 아래 파일을 kafka-lab/ 같은 디렉터리에 저장해 두고 계속 재사용하세요. 케이스 스터디의 재현 코드도 동일한 클러스터를 전제로 합니다.

아키텍처

노드 3대 모두 process.roles=broker,controller인 combined 모드입니다. 각 노드는 컨트롤러 쿼럼의 투표자이면서 동시에 파티션 데이터를 담는 브로커입니다. 메타데이터는 __cluster_metadata 라는 내부 토픽에 Raft로 복제되며, ZooKeeper 앙상블은 존재하지 않습니다.

리스너 설계 — 이 예제의 핵심

컨테이너 네트워크 안의 이름(kafka-1)과 호스트에서 보이는 이름(localhost)이 다르기 때문에, 리스너를 세 개로 나눕니다. 하나라도 잘못 두면 "브로커는 떠 있는데 클라이언트가 붙지 못하는" 증상이 나옵니다.

이 예제의 리스너 3종과 용도
리스너 이름 컨테이너 내부 포트 누가 쓰는가 광고 주소(advertised.listeners)

advertised.listeners는 브로커가 "나에게 접속하려면 이 주소를 쓰라"고 클라이언트에게 알려 주는 값입니다. 클라이언트는 bootstrap.servers로 최초 접속한 뒤, 메타데이터에 실린 광고 주소로 다시 접속합니다. 그래서 여기에 kafka-1:19092만 적어 두면 호스트의 IDE는 최초 연결에는 성공하고 그 다음에 kafka-1 이름 해석 실패로 멈춥니다. 리스너 조합의 원리는 11장 운영 기초에서 자세히 다룹니다.

정적 쿼럼과 동적 쿼럼 — 이 예제는 controller.quorum.voters로 투표자를 고정하는 정적 쿼럼을 씁니다. Kafka 4.1부터는 KIP-853 기반의 동적 쿼럼도 쓸 수 있는데, 그때는 controller.quorum.voters를 설정하지 않고 controller.quorum.bootstrap.servers만 두고 kafka-storage.sh format --standalone 또는 --initial-controllers로 포맷합니다. 정적/동적은 포맷 시점에 결정되며 나중에 마이그레이션이 필요합니다. 로컬 실습에서는 컨트롤러를 추가·제거할 일이 없으므로, 공식 Docker 예제와 동일한 정적 구성이 재현성이 높습니다. 현재 쿼럼이 어느 쪽인지는 kafka-features.sh describe의 kraft.version 레벨(0이면 정적, 1 이상이면 동적)로 확인합니다.

디렉터리 구조는 다음과 같습니다. 파일 4개가 전부입니다.

docker-compose.yml

.env

CLUSTER_ID는 Base64 URL-safe 로 인코딩된 22자 UUID여야 합니다. 아무 문자열이나 넣으면 포맷 단계에서 실패합니다. 아래 값은 Apache Kafka 공식 Docker 예제가 쓰는 값이며, 직접 만들려면 kafka-storage.sh random-uuid를 씁니다(다음 절에 명령이 있습니다).

create-topics.sh

이후 예제에서 쓰는 토픽을 한 번에 만듭니다. --if-not-exists를 붙였으므로 여러 번 실행해도 안전합니다.

kcli 래퍼

Kafka CLI는 이미지 안 /opt/kafka/bin에 있습니다. 호스트에 tarball을 따로 풀지 않고 컨테이너의 스크립트를 쓰는 래퍼를 두면 버전 불일치를 원천적으로 막을 수 있습니다.

실행 방법

tarball로 직접 설치할 때는 kafka-storage.sh random-uuid → kafka-storage.sh format --cluster-id ... → kafka-server-start.sh 순서를 사람이 직접 밟습니다. apache/kafka 이미지는 기동 스크립트가 로그 디렉터리를 검사해 비어 있으면 자동으로 포맷합니다. 그래서 compose에서는 CLUSTER_ID만 넘기면 됩니다. 단일 노드를 tarball로 직접 띄우는 절차는 1장에 있습니다.

검증 방법

네 가지를 순서대로 확인합니다. 하나라도 어긋나면 다음 예제가 동작하지 않습니다.

1. 컨트롤러 쿼럼이 정상인가

확인 포인트는 CurrentVoters에 3개가 모두 있는지와 MaxFollowerLag가 0에 가까운지입니다. 투표자가 2개만 보이면 한 노드가 쿼럼에 참여하지 못한 것이고, MaxFollowerLag가 계속 커지면 메타데이터 복제가 밀리는 것입니다. combined 모드에서 브로커 3대는 컨트롤러 쿼럼의 투표자이므로 CurrentObservers는 비어 있는 것이 정상입니다.

2. 브로커 3대가 모두 등록되었는가

isFenced: false가 셋 다 나와야 합니다. isFenced: true는 브로커가 아직 메타데이터를 따라잡지 못해 파티션 리더가 될 수 없는 상태라는 뜻입니다. 기동 직후 몇 초간은 정상적으로 나타날 수 있습니다.

3. 토픽의 리더와 ISR이 3대에 분산되었는가

Isr의 원소가 3개이고 리더가 세 브로커에 골고루 퍼져 있으면 정상입니다. Isr: 1처럼 하나만 남아 있으면 복제가 따라가지 못하는 중입니다. Configs:에 min.insync.replicas=2가 보이는지도 확인하세요 — 이 값이 없으면 예제 3의 무손실 설정이 의도대로 동작하지 않습니다.

4. 호스트에서, 컨테이너에서 각각 읽고 쓸 수 있는가

(C)가 성공하면 advertised.listeners의 PLAINTEXT_HOST://localhost:29092가 제대로 광고되고 있다는 뜻입니다. 여기서 Connection to node -1 could not be established 또는 무한 재시도가 나오면 광고 주소 설정을 다시 보세요. 이후 예제의 Java 코드는 모두 bootstrap.servers=localhost:29092,localhost:39092,localhost:49092를 씁니다.

클러스터가 정상임을 확인했으면 일부러 한 대를 죽여 보세요. 이것이 3노드로 만든 이유입니다.

이 실패가 유실보다 나은 동작이라는 점이 핵심입니다. 자세한 이유는 예제 3과 케이스 6에서 다룹니다.

프로덕션 고려사항

이 compose는 학습·개발용입니다. 실제 운영 클러스터와 다른 점을 정리합니다. 운영 관점의 상세는 3장 KRaft와 클러스터 메타데이터와 11장 운영 기초를 보세요.

로컬 예제와 프로덕션의 차이
항목 이 예제 프로덕션 이유
노드 롤 broker,controller combined 3대 컨트롤러 3대 + 브로커 N대로 분리(isolated) combined는 브로커의 GC 정지·디스크 포화가 컨트롤러 쿼럼까지 흔듭니다. 메타데이터 장애가 데이터 장애와 함께 오면 복구가 훨씬 어려워집니다
보안 전 리스너 PLAINTEXT SASL_SSL + ACL, 컨트롤러 리스너도 별도 인증 평문은 인증도 암호화도 없습니다. 설정 예시는 보안 치트시트에 있습니다
장애 도메인 한 호스트의 Docker 3컨테이너 서로 다른 랙·AZ에 분산 + broker.rack 설정 지금 구성은 호스트가 죽으면 3대가 동시에 죽습니다. RF=3의 의미가 없습니다
스토리지 Docker named volume 전용 디스크, log.dirs를 여러 디바이스로 분리, RAID 대신 JBOD 페이지 캐시와 순차 I/O가 성능을 좌우합니다. 컨테이너 오버레이 FS는 지연 특성이 다릅니다
group.initial.rebalance.delay.ms 0 기본값 3000 유지 또는 더 크게 0이면 컨슈머가 하나씩 붙을 때마다 리밸런스가 일어납니다. 배포 시 리밸런스 스톰의 원인이 됩니다
JVM 힙 -Xmx512m 보통 6GB 내외로 고정하고 남은 메모리는 페이지 캐시에 양보 Kafka는 힙보다 페이지 캐시로 성능을 냅니다. 힙을 키우는 것이 항상 유리하지 않습니다
모니터링 없음 JMX → Prometheus → Grafana, UnderReplicatedPartitions·OfflinePartitionsCount·ActiveControllerCount 알림 URP가 0이 아닌 상태를 모르고 지나가면 다음 장애에서 유실이 발생합니다. 예제 10에서 구성합니다
쿼럼 방식 정적(controller.quorum.voters) 동적(controller.quorum.bootstrap.servers, KIP-853) 정적 쿼럼은 컨트롤러를 무중단으로 교체할 수 없습니다
  • 컨트롤러 쿼럼 크기는 3 또는 5입니다. 3은 1대, 5는 2대 손실을 견딥니다. 짝수는 내결함성이 같은데 커밋 지연만 늘어 의미가 없습니다.
  • process.roles가 broker,controller인 combined 모드는 개발·소규모 용도입니다. 프로덕션은 분리를 권장합니다.
  • controller.listener.names로 지정한 리스너는 클라이언트에게 광고하지 않습니다.
  • 같은 클러스터의 모든 노드는 같은 클러스터 ID를 공유합니다. 다르면 노드가 서로를 거부합니다.

자주 하는 실수

KAFKA_ADVERTISED_LISTENERS에 PLAINTEXT://kafka-1:19092만 적으면, 호스트에서 돌리는 IDE 애플리케이션은 부트스트랩은 성공하고 그 다음에 멈춥니다. 메타데이터로 받은 kafka-1을 호스트가 해석할 수 없기 때문입니다. 증상은 max.block.ms(기본 60000) 만료 후의 TimeoutException이라 원인이 리스너라는 걸 알아채기 어렵습니다. 호스트용 리스너를 따로 두고 localhost:29092를 광고하세요.

단일 노드 예제를 복사해 오면 KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1이 함께 따라옵니다. 그 상태로 노드를 3대로 늘려도 이미 만들어진 __consumer_offsets의 복제 계수는 자동으로 올라가지 않습니다. 그 브로커 한 대가 죽으면 컨슈머 그룹 오프셋이 통째로 사라져 auto.offset.reset에 따라 전체 재처리 또는 전체 스킵이 일어납니다 (케이스 1). 클러스터를 처음 포맷할 때 제대로 넣거나, 이미 만들어졌다면 kafka-reassign-partitions.sh로 올려야 합니다.

공식 Docker 예제는 KAFKA_LOG_DIRS=/tmp/kraft-combined-logs를 쓰고 볼륨을 붙이지 않습니다. 학습용으로는 그게 정상이지만, docker compose down 한 번에 토픽·오프셋·메타데이터가 전부 사라집니다. 이 예제처럼 named volume을 붙이면 재시작 후에도 상태가 남습니다. 반대로 "클러스터를 깨끗하게 초기화"하려면 down -v로 볼륨까지 지워야 합니다. 볼륨만 남긴 상태에서 CLUSTER_ID를 바꾸면 기존 로그 디렉터리의 ID와 충돌해 브로커가 기동하지 못합니다.

CLUSTER_ID를 노드별로 생성하면 각 노드가 서로 다른 클러스터라고 판단하고 쿼럼이 구성되지 않습니다. 로그에는 Inconsistent cluster id 계열 오류가 남습니다. ID는 클러스터당 하나이며, 이 예제는 .env에서 한 번만 정의해 세 서비스가 공유합니다.

bootstrap.servers에 컨트롤러 포트(9093)를 적는 실수가 흔합니다. 컨트롤러 리스너는 클라이언트 요청을 처리하지 않습니다. 클라이언트는 브로커 리스너(9092/19092)로 붙어야 합니다. 다만 kafka-metadata-quorum.sh처럼 컨트롤러를 직접 다루는 도구는 --bootstrap-controller로 컨트롤러에 붙을 수 있습니다.

공식 문서 출처

이 페이지의 설정명·기본값·명령 형식은 Apache Kafka 4.3.1 문서와 공식 Docker 예제에서 확인했습니다.

  • Quickstart — kafka-storage.sh random-uuid / format --standalone -t <id> -c <config> / kafka-server-start.sh 순서, Java 17+ 요구
  • Docker — apache/kafka 이미지, Docker 20.10.4 이상 요구, 환경변수 → 프로퍼티 변환 규칙, apache/kafka-native가 실험적이라는 명시
  • KRaft — controller.quorum.bootstrap.servers와 controller.quorum.voters의 관계, 정적/동적 쿼럼이 포맷 시점에 결정된다는 점, kafka-metadata-quorum.sh describe --status 출력 형식
  • Broker Configs — offsets.topic.replication.factor=3, transaction.state.log.replication.factor=3, transaction.state.log.min.isr=2, min.insync.replicas=1, num.partitions=1, default.replication.factor=1, group.initial.rebalance.delay.ms=3000, unclean.leader.election.enable=false, share.coordinator.state.topic.replication.factor=3
  • Java Version — Java 17 · 21 · 25 완전 지원, Java 8은 4.0에서 제거
  • apache/kafka · docker/examples — combined / isolated 모드 compose 예제와 환경변수 조합
